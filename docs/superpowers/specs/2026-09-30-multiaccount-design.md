# Мультиаккаунт: дизайн

Дата: 30.09.2026. Статус: согласован в обсуждении, ждёт ревью спеки.

Документ описывает целевую архитектуру мультиаккаунта и три этапа её внедрения. Каждый этап
получает свой план реализации и заканчивается работающей системой.

## 1. Цель

Одна установка pyrobot обслуживает:

1. **Несколько аккаунтов одного человека.** Владелец держит несколько игровых аккаунтов и
   переключается между ними в админке.
2. **Несколько пользователей на одном сервере.** У каждого свой вход в админку и свои аккаунты;
   чужие аккаунты не видны.

Оба сценария — одна модель: пользователь → список аккаунтов, лимит аккаунтов задаёт владелец
сервера.

### 1.1. Требования (сказано владельцем)

- Одна общая установка на сервер: один бот, одна админка, у каждого пользователя свой логин.
- Пользователь может держать несколько аккаунтов в пределах лимита. Лимит задаёт владелец
  сервера, по умолчанию 1.
- Новые пользователи приходят по одноразовой ссылке-приглашению со сроком и лимитом аккаунтов;
  логин и пароль задают сами. Забытый пароль восстанавливают сами; владелец сервера чужие пароли
  не сбрасывает.
- Владелец сервера видит только служебное: кто заведён, работает ли бот, ошибки. Может завести,
  отключить и удалить. В чужую игру (журнал, состояние, настройки, команды) не заходит.
- Изоляция — как для посторонних людей: лимиты и защита от злоупотреблений.
- Масштаб: 10–50 аккаунтов на сервер, с перспективой больше 50.
- Telegram: по умолчанию общий api_id/api_hash сервера. Пользователь может указать для аккаунта
  свои api_id/api_hash. Прокси в приложении нет: сетевой доступ к Telegram обеспечивает тот, кто
  держит сервер.

### 1.2. Допущения

- Аккаунты в игре независимы. Движки не координируются, даже если аккаунты в одной команде.
- «Не заходит в чужую игру» — это права в приложении. У владельца сервера есть root и доступ к
  базе; приложение от этого не защищает. Шифрование сессий Telegram защищает от утечки дампа базы,
  а не от root.
- Нынешняя установка переезжает без потерь и без перелогина в Telegram.
- Отдельные установки на одном сервере (`COMPOSE_PROJECT_NAME`, README) продолжают работать.

### 1.3. Критерии успеха

- Владелец переключается между своими аккаунтами, и для каждого работает всё, что есть сейчас.
- Пользователь по приглашению заводит аккаунт, входит в Telegram и видит только своё; чужой
  аккаунт для него — 404.
- Падение, перезапуск или перелогин одного аккаунта не затрагивает остальные.
- 50 аккаунтов на одном сервере работают без деградации (задержка цикла p99 < 100 мс); дальше —
  добавлением воркеров.

### 1.4. Чего не делаем

- Координацию аккаунтов в игре.
- Прокси для Telegram.
- Лимиты CPU на отдельный аккаунт.
- Несколько экземпляров шлюза API.
- Воркеры на разных машинах (сессии в базе это позволяют, но это не цель и не тестируется).
- Открытую регистрацию, почту, 2FA для админки, биллинг.
- Смену ключа шифрования без перелогина (см. раздел 9).

## 2. Что есть сейчас

Схема базы уже частично готова: таблица `accounts` есть, во всех таблицах бота есть
`account_id` (FK на `accounts.id`), все уникальности включают `account_id`, чтение и запись в
хранилищах фильтруют по нему. Рантайм при этом рассчитан на один аккаунт:

| Что | Где | Почему мешает |
|---|---|---|
| Аккаунт задаётся из окружения `PYROBOT_ACCOUNT_ID` (по умолчанию 1) | `app/config.py:28`, `app/main.py:104-237` | один аккаунт на процесс; строк `accounts` никто не создаёт, `accounts.tg_user_id` не используется |
| Advisory-блокировка с постоянным ключом | `app/db/lock.py:8` | второй движок на той же базе не стартует, какой бы ни был аккаунт |
| Файл сессии Telegram `/data/pyrobot.session` | `app/engine/transport/kurigram.py:174-194` | два клиента делили бы файл; выход одного удалил бы сессию другого |
| `Container` держит один `facade` и один `DbReads` | `app/api/container.py:17-30` | ни в путях, ни в заголовках нет аккаунта |
| `admin_users`, `auth_sessions` глобальные | `app/db/models.py:35-54` | нет ролей и связи учётки с аккаунтами |
| Один `EventStream`, события без аккаунта | `app/main.py:106`, `app/engine/stream.py` | SSE одного аккаунта |
| Токен подтверждения подписывает сессию, но не аккаунт | `app/api/confirm.py:50-55` | подтверждение можно было бы повторить на другом аккаунте |
| Настройки `chats.`, `telegram.` требуют перезапуска процесса | `app/engine/settings.py:281-285` | перезапускались бы все аккаунты |
| `Supervisor._tasks` по фиксированным именам | `app/engine/supervisor.py:21-25` | имена задач двух движков совпали бы |
| Фронтенд: один `EventSource`, глобальные хранилища | `admin/src/lib/app.svelte.ts:11-21` | нет понятия аккаунта |

Модульного изменяемого состояния в коде движка нет (реестры и таблицы — только для чтения):
несколько движков в одном процессе упираются только в перечисленное выше.

## 3. Архитектура

```
                браузер
                   │  cookie-сессия, CSRF
            ┌──────▼──────────────────────────┐
            │ шлюз API (роль api или all)     │
            │  вход, учётки, приглашения,     │
            │  консоль, чтение из базы,       │
            │  EngineClient ──────────────┐   │
            └─────────────────────────────┼───┘
                                          │ этап 1–2: вызов в процессе
                                          │ этап 3: HTTP к воркеру
            ┌─────────────────────────────▼───┐
            │ хост движков (роль worker/all)  │
            │  EngineHost                     │
            │   ├ AccountRuntime #1 ── kurigram│
            │   ├ AccountRuntime #2 ── kurigram│
            │   └ …                           │
            └──────────────┬──────────────────┘
                           │
                       Postgres
         данные по account_id, сессии Telegram,
         advisory-блокировки (pyrobot, account_id)
```

- **`AccountRuntime`** — всё, что сейчас «один движок», для одного аккаунта.
- **`EngineHost`** — запускает, останавливает и перезапускает `AccountRuntime`, держит аренду
  аккаунтов.
- **`EngineClient`** — интерфейс шлюза к движку аккаунта. На этапах 1–2 это вызов внутри процесса,
  на этапе 3 — HTTP к воркеру. Маршруты API от реализации не зависят.

Этапы:

1. **Мультиаккаунт у владельца** (раздел 4): реестр аккаунтов, хост движков в процессе, сессии
   Telegram в базе, API и SSE с аккаунтом в пути, переключатель в админке, перенос установки.
2. **Пользователи и доступ** (раздел 5): роли, приглашения, лимиты, консоль владельца, своё
   приложение Telegram, границы опасных настроек, журнал действий.
3. **Воркеры** (раздел 6): вынос хоста движков в отдельные процессы, распределение аккаунтов,
   маршрутизация, масштабирование.

## 4. Этап 1. Мультиаккаунт у владельца

### 4.1. Модель данных

**`accounts`** — реестр аккаунтов:

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | int PK | есть |
| `owner_id` | int NULL, FK `admin_users.id` ON DELETE RESTRICT | чей аккаунт; NULL — аккаунт без владельца, никому не виден, при старте его получает первая учётка (раздел 4.7) |
| `name` | varchar(64) NOT NULL | имя в переключателе; UNIQUE (`owner_id`, `name`) |
| `status` | varchar(16) NOT NULL, CHECK in (`enabled`, `disabled`, `error`, `deleting`) | движок крутится только у `enabled` |
| `status_reason` | text NULL | почему `disabled` или `error` (например `crash_loop:gateway`) |
| `tg_user_id` | bigint NULL | есть; становится источником правды для привязки к Telegram; частичный UNIQUE WHERE NOT NULL |
| `engine_generation` | bigint NOT NULL, по умолчанию 0 | желаемое поколение движка: перезапуск увеличивает его (раздел 4.2) |
| `lease_holder` | text NULL | id хоста, держащего аренду (uuid процесса); NULL — аренда свободна |
| `lease_epoch` | bigint NOT NULL, по умолчанию 0 | номер аренды: растёт при каждом захвате |
| `lease_expires_at` | timestamptz NULL | до какого момента (по часам базы) аренда действует без продления; NULL — освобождена |
| `created_at` | timestamptz | есть |
| `updated_at` | timestamptz NOT NULL | новое |

- Секция `telegram` (единственное поле `expected_user_id`) удаляется из `Settings`: привязка —
  `accounts.tg_user_id`. Уникальность не даёт привязать одного пользователя Telegram к двум
  аккаунтам; попытка входа под уже привязанным пользователем отклоняется, сессия закрывается,
  ошибка `tg_user_taken`.
- **Привязка — на всю жизнь аккаунта.** Первый успешный вход записывает `tg_user_id`, и больше он
  не меняется: выход из Telegram его не очищает, отвязки нет. Иначе вход другим пользователем
  Telegram смешал бы журнал и состояние двух персонажей в одном аккаунте. Повторный вход тем же
  пользователем — как сейчас; другим — отказ `unexpected_user` (как сейчас), сессия закрывается.
  Другой персонаж — новый аккаунт. Чтобы освободить пользователя Telegram для другого аккаунта,
  прежний аккаунт удаляют вместе с данными; до этого вход им в другой аккаунт — `tg_user_taken`.
- Новый аккаунт создаётся `enabled` и получает строку `settings` со значениями по умолчанию
  (`engine.mode = dry_run`); его движок работает без Telegram до первого входа, как сейчас
  после выхода.
- **Сессии Telegram** — две новые таблицы (раздел 4.3):
  - `tg_sessions`: `account_id` PK FK, `dc_id`, `api_id`, `test_mode`, `auth_key` bytea
    (зашифрован), `date`, `user_id`, `is_bot`, `server_address`, `port`, `updated_at`;
  - `tg_peers`: PK (`account_id`, `id`), `access_hash`, `type`, `username`, `phone_number`,
    `updated_at` — только пиры чатов из настроек аккаунта и пользователя `swinfo_user_id`.
- **`tg_chat_marks`**: PK (`account_id`, `chat_id`, `from_id`), `from_id` bigint NOT NULL —
  0 для чтения всего чата, иначе id отправителя; `msg_id` bigint, `updated_at` — отметки
  сверки истории (раздел 4.3). Принадлежат
  журналу: выход из Telegram их не удаляет.
- **`server_meta`** (`key` text PK, `value` bytea): контрольная запись ключа шифрования
  (`key_check`, раздел 4.3).
- Индексы, которых не хватает: `notifications (account_id, id)`,
  `settings_history (account_id, id)`.
- Внешние ключи `account_id` остаются без каскада: удаление аккаунта — фоновая чистка (раздел
  4.2), а FK страхуют от удаления строки `accounts` с оставшимися данными.

### 4.2. Хост движков

Нынешний `Runtime` (`app/main.py`) делится на две части:

- **Процесс:** база и пул, вход в админку и сессии, `Container` и HTTP, `EngineHost`, задачи
  процесса — очистка истёкших сессий админки и монитор задержки цикла.
- **`AccountRuntime(account_id)`:** хранилища с `account_id` (`DbSettingsStore`, `DbJournal`,
  `DbActionStore`, `DbPlannerStore`, `DbMetroRunStore`, `DbNotifier`),
  `EventStream`, `Pipeline`, транспорт kurigram, `ActionGateway`, `TgAuthManager`, `Reconciler`,
  `PlannerLoop`, `RobberyDefense`, `TeamForward`, `EngineFacade` и свой `Supervisor`. Задачи
  аккаунта: `pipeline`, `gateway`, `reconcile`, `reactions`, `team-forward`, `planner`,
  `tg-probe`.
- **Retention — задача процесса**, а не аккаунта: раз в 6 ч (первый проход через 5 минут после
  старта, как сейчас) она проходит по всем аккаунтам, кроме `deleting`, — включая выключенные
  и упавшие — и чистит каждый по его политике (этап 1 — `settings.retention` аккаунта, этап 2 —
  политика сервера, раздел 5.4).

**`EngineHost`:**

- `start(account_id)`, `stop(account_id, reason)`, `restart(account_id)`, `get(account_id)`,
  `running()`.
- При старте процесса поднимает все `enabled` аккаунты с паузой `PYROBOT_ENGINE_START_GAP_S`
  (по умолчанию 3 с) между ними, чтобы не было залпа подключений к Telegram с одного IP.
- Ёмкость — `PYROBOT_MAX_ENGINES`, по умолчанию 20: сколько аккаунтов может быть `enabled`
  одновременно. Значение пересматривается по замеру (раздел 4.8). Создание аккаунта (он
  создаётся `enabled`) или включение, после которых `enabled` аккаунтов стало бы больше
  ёмкости, — 409 `capacity_reached`; выключенные, упавшие и удаляемые не считаются.
- **Аренда аккаунта** исключает два действующих движка одного аккаунта, в том числе в
  промежутке после обрыва соединения: Postgres отпускает advisory-блокировку сразу, а прежний
  хост узнаёт об обрыве не сразу. Блокировка только упорядочивает захват, а действует аренда с
  ограниченным сроком (TTL = 15 с, продление каждые 5 с). Все запросы аренды идут по выделенному
  соединению блокировок хоста, каждый — отдельной транзакцией (`now()` в Postgres — время начала
  транзакции); ожидания — вне транзакций.
  1. **Блокировка.** `pg_try_advisory_lock(0x7079726F, account_id)` (двухключевая форма вместо
     глобального ключа; все блокировки хоста — на одном соединении). Не взял — аккаунт у
     другого хоста, повтор через 30 с. Блокировки Postgres повторно входимы в пределах
     соединения (каждый захват требует своего снятия), поэтому хост держит не больше одной
     блокировки на аккаунт и учитывает их в памяти: уже взятую не берёт снова.
  2. **Захват аренды** — условный запрос:
     `UPDATE accounts SET lease_holder = <хост>, lease_epoch = lease_epoch + 1,
     lease_expires_at = now() + TTL WHERE id = <аккаунт> AND (lease_holder IS NULL OR
     lease_expires_at < now() OR lease_holder = <хост>) RETURNING lease_epoch`.
     Ноль строк — аренда прежнего держателя ещё действует: ждать до её `lease_expires_at` + 1 с
     и повторить.
  3. **Свой прежний пользователь аренды.** На одном хосте аккаунтом в каждый момент занят
     кто-то один: `AccountRuntime` или задача чистки удаляемого аккаунта. Новый (перезапуск,
     переподключение после обрыва, чистка после остановки движка) начинает только после того,
     как прежний полностью остановился; условие `lease_holder = <хост>` в п. 2 без этого
     правила пропустило бы его сразу.
  4. **Продление** — каждые 5 с одним запросом по всем аккаунтам хоста:
     `lease_expires_at = now() + TTL WHERE lease_holder = <хост> AND (id, lease_epoch) IN (…)
     RETURNING id, lease_epoch`. Ответ разбирается по парам (аккаунт, эпоха) запроса, а не по
     аккаунтам: пара действует на движок, только если его текущая эпоха равна эпохе пары.
     - Пара из запроса не вернулась, и движок всё ещё в этой эпохе, — аренда потеряна,
       аварийная остановка (п. 6).
     - Движок уже в другой эпохе (между сборкой запроса и ответом аккаунт штатно остановлен и
       захвачен снова) или его нет — ответ по старой эпохе игнорируется: он не останавливает
       новый движок и не сдвигает его местный срок (п. 5).
     Продление идёт по соединению блокировок: оборвалось оно — продлений нет, и срок
     наступает сам. Аренды принадлежат одному экземпляру соединения: после переподключения
     хост не продлевает прежние эпохи, а ждёт аварийной остановки своих движков и захватывает
     аккаунты заново по пп. 1–3. Продление идёт и во время штатной остановки. Запрос продления
     ждёт короткие ограждённые транзакции (п. 6), поэтому идёт с `lock_timeout = 2 с`; не
     прошёл — повтор через 1 с.
  5. **Местный срок.** Перед захватом (п. 2) и перед каждым продлением хост запоминает
     монотонное время `t`; после успеха срок аккаунта — `t + TTL − 3 с` (у продления — только
     для пар, эпоха которых совпадает с текущей эпохой движка). Он всегда наступает
     раньше `lease_expires_at` в базе: запрос уходит до того, как база поставит `now()`.
  6. **Ограда после срока.**
     - Telegram: все вызовы Telegram аккаунта — отправки шлюза, нажатия, пересылка, чтение,
       проба, служебные сообщения этапа 2 — идут через один помощник. Он не начинает вызов
       после срока и ограничивает его `asyncio.wait_for(срок − сейчас)`: `invoke` kurigram сам
       может ждать запуска сессии до 15 с (`Session.WAIT_TIMEOUT`).
     - Переподключение клиента после перегрузки (`connect()`, `go_online()`) — тоже вызовы
       Telegram и идут через помощник.
     - База: хранилища аккаунта проверяют местный срок перед каждой пишущей транзакцией и после
       него не пишут. Все пишущие транзакции аккаунта, кроме записи отметок сверки (она
       монотонна, раздел 4.3), начинаются с
       `SELECT 1 FROM accounts WHERE id = <аккаунт> AND lease_epoch = <свой> FOR SHARE`: нет
       строки — аренда потеряна (ошибка `LeaseLost`, не конфликт версии настроек). Это и
       `DbJournal.append` — он пишет сообщение, снимок состояния и леджер одной транзакцией, —
       поэтому ограждённые транзакции держатся короткими: без сетевых вызовов внутри. Блокировка
       строки упорядочивает такую запись с захватом аренды: захват (п. 2) ждёт её коммита и
       видит новую эпоху только после него.
     - `LeaseLost` и отказ записи после срока прерывают цикл повторов `Pipeline._append` (сейчас
       он повторяет любую ошибку бесконечно) и запускают аварийную остановку.
     - Аварийная остановка — по сроку или при потере в продлении, по порядку:
       1. `client.session.stop()` — сессия больше не принимает и не переподключается;
       2. отмена `client.dispatcher.handler_worker_tasks` вместо `terminate()`: тот сохраняет
          хранилище и дорабатывает всю очередь диспетчера в конвейер, который после срока
          писать не может, — остановка бы не закончилась;
       3. закрытие хранилища без `save()`;
       4. отмена задач аккаунта без доработки конвейера и без финальных записей.

       Что не успело в журнал, вернёт сверка истории у следующего держателя (раздел 4.3).
     - Допущение: пауза цикла событий короче запаса в 3 с. Монитор задержки цикла (задача
       процесса) при задержке больше 1 с шлёт предупреждение хоста.
  7. **Штатная остановка** (выключение, перезапуск, остановка хоста): движок останавливается как
     сейчас, с доработкой конвейера, пока идёт продление. Затем, если местный срок не наступил,
     аккаунт убирается из набора продления, и аренда освобождается:
     `UPDATE accounts SET lease_holder = NULL, lease_expires_at = NULL WHERE id = <аккаунт> AND
     lease_holder = <хост> AND lease_epoch = <свой>` — и снимается блокировка; следующий
     держатель стартует без ожидания. Держатель очищается, поэтому продление, собранное до
     освобождения и выполненное после него, этот аккаунт уже не находит
     (`lease_holder = <хост>` не выполняется) и аренду не возобновляет; ответ по эпохе, которой
     уже нет, игнорируется (п. 4). Срок наступил посреди остановки — она становится аварийной и
     освобождения нет: после срока хост в базу не пишет, следующий держатель ждёт
     `lease_expires_at`.

  Итог: прежний держатель прекращает писать в Telegram и в базу не позже чем за 3 с до того, как
  новый может захватить аренду. Пока аккаунт у другого хоста, это не пишется в `status`: статус
  аккаунта отдаёт `running: false`, `host_reason: locked_elsewhere`.
- **Изоляция падений.** Сбой задачи перезапускается супервизором своего аккаунта, как сейчас.
  5 сбоев за 10 минут — хост останавливает `AccountRuntime`, ставит `status = error`,
  `status_reason = crash_loop:<задача>` и шлёт уведомление аккаунта `account_crash_loop` (error).
  Ошибка при старте аккаунта (невалидные настройки и т. п.) — тоже `error` с причиной.
  Пользователь возвращает аккаунт кнопкой «включить».
- **Перезапуск одного аккаунта.** `PATCH settings` возвращает `restart_required` (как сейчас),
  админка предлагает «перезапустить аккаунт» — `POST /accounts/{id}/engine/restart`. Процесс
  целиком больше не перезапускается.
- **Желаемое состояние сохраняется, а не передаётся командой.** Включение, выключение и удаление
  меняют `accounts.status`, перезапуск увеличивает `accounts.engine_generation`. Хост сверяет
  желаемое с фактическим — по уведомлению и раз в 30 с: движок идёт не того поколения —
  перезапустить, статус не `enabled` — остановить. Пропущенное уведомление задерживает действие
  не больше чем на 30 с, но не теряет его.
- **Удаление.** `DELETE /accounts/{id}` ставит `deleting`, хост штатно останавливает движок и
  закрывает сессию Telegram (`log_out`). Фоновая задача чистки сначала сама захватывает аренду
  аккаунта по пп. 1–3: ждёт полной остановки движка на своём хосте и срока аренды чужого. Если движок не был запущен, а сессия в
  базе есть, она поднимает временный клиент только для `log_out` (таймаут 30 с; не вышло —
  предупреждение в лог, сессия остаётся в списке сессий пользователя в Telegram). Затем удаляет
  строки аккаунта пачками по 5000 (порядок — как в `DbRetention`, включая `tg_sessions`,
  `tg_peers`, `tg_chat_marks`, `settings`, `settings_history`, `state_snapshot`) и строку
  `accounts`.
- **Логи.** ContextVar `account_id` задаётся для задач аккаунта (включая задачи клиента kurigram,
  созданные в его контексте); фильтр логирования добавляет `account=<id>` к каждой записи.
- **Пул соединений.** `PYROBOT_DB_POOL_SIZE` (по умолчанию 10) и `PYROBOT_DB_MAX_OVERFLOW`
  (по умолчанию 20) вместо умолчаний SQLAlchemy.
- **Перегрузка.** Очередь конвейера становится ограниченной (`PIPELINE_QUEUE_MAX = 10000`), и
  при заполнении обработчик kurigram ждёт места. Но у kurigram перед ним своя безразмерная
  `updates_queue` (`put_nowait` из сетевого слоя), поэтому поток ограничивается раньше:
  - транспорт подменяет `client.dispatcher.updates_queue` своей очередью с подсчётом (размер
    остаётся безразмерным — сетевой слой kurigram не умеет ждать);
  - когда очередь kurigram и очередь конвейера вместе превышают `OVERLOAD_HIGH = 5000`, транспорт
    перекрывает приём в таком порядке: `client.session.stop()` (сессия перестаёт принимать),
    `client.terminate()` (диспетчер разбирает уже принятое), `client.disconnect()`. Выхода из
    сессии Telegram нет; статус Telegram аккаунта — `overload`, предупреждение аккаунта
    `account_overload`;
  - когда накопленное разобрано ниже `OVERLOAD_LOW = 500`, транспорт создаёт новый объект
    клиента с тем же хранилищем (сессии kurigram одноразовые; хранилище не удаляется), делает
    `connect()` и `go_online()`, после чего идёт сверка истории (раздел 4.3).

  kurigram сам не догоняет пропущенное (`skip_updates=True`, раздел 4.3), поэтому `recover_gaps`
  не запускается и зацикливания при перегрузке нет. Память аккаунта на обновления ограничена
  порогом плюс одной порцией сверки истории (не больше 1050 сообщений на чтение).
- **`/readyz`** — готовность процесса: база доступна, соединение блокировок хоста живо. Готовность
  аккаунта (Telegram онлайн, не kill) — в статусе аккаунта. `deploy/remote-deploy.sh` ждёт
  `/readyz`, как сейчас.

### 4.3. Сессии Telegram

- **Хранилище.** `PgSessionStorage` реализует `pyrogram.storage.Storage` (kurigram 2.2.26,
  параметр `storage_engine` клиента):
  - поля сессии (`dc_id`, `api_id`, `test_mode`, `auth_key`, `date`, `user_id`, `is_bot`,
    `server_address`, `port`) — строка `tg_sessions`, запись при изменении;
  - состояние обновлений — только в памяти: `get/set_update_state` в базу не пишут, потому что
    своя догонка kurigram выключена (ниже), и сохранённое состояние не нужно;
  - пиры и usernames — в памяти; прогрев `get_dialogs(limit=200)` в `go_online` уже есть. Пиры
    чатов из настроек аккаунта (игровой бот, swinfo, смузи, мандарины, приглашения к
    биржевикам, чат команды) и пользователь `swinfo_user_id` дополнительно пишутся в `tg_peers` и
    загружаются при открытии, чтобы эти чаты были доступны и вне первых 200 диалогов, как сейчас
    с SQLite. Пир `swinfo_user_id` нужен поиску по отправителю: kurigram не сохраняет
    min-пользователей из обновлений супергрупп, а `resolve_peer` без `access_hash` для
    произвольного пользователя не работает;
  - `delete()` удаляет строки аккаунта из `tg_sessions` и `tg_peers`;
  - один объект переживает `close()` и повторный `open()`: `disconnect()` kurigram закрывает
    хранилище, а новый клиент после перегрузки открывает его снова.
- Клиент: `Client(f"account-{id}", storage_engine=PgSessionStorage(...), skip_updates=True,
  api_id, api_hash, …)` — сейчас `skip_updates=False`; `workdir` не используется.
- **Сверка истории — гарантия полноты журнала** вместо догонки kurigram. Догонке через
  сохранённое состояние обновлений доверять нельзя:
  - kurigram сохраняет `pts` до того, как кладёт обновление в очередь обработчика
    (`pyrogram/client.py`, `handle_updates`);
  - `handle_updates` запускается отдельной задачей на каждое сообщение MTProto
    (`pyrogram/session/session.py`), и вызовы перемешиваются на своих `await`;
  - после внутреннего переподключения сессии kurigram пропущенное не догоняет.

  Кроме того, с `skip_updates=True` сторож kurigram (`updates_watchdog`) больше не догоняет
  пропуски, когда сервер молча перестаёт слать обновления, а ошибки внутри `handle_updates`
  (например, `GetDifference` для `UpdateShortMessage` — так приходят личные сообщения игрового
  бота) теряют сообщение без следа.

  Поэтому транспорт сам сверяет историю отслеживаемых чатов — проходами от сохранённой отметки:
  - **Чтения.** Чтение — пара (чат, отправитель); у каждой пары своя отметка:
    - (чат, 0) — `messages.getHistory`, все сообщения чата: игровой бот, канал смузи, чат
      приглашений к биржевикам;
    - (swinfo_chat_id, swinfo_user_id) — `messages.search` с `from_id = swinfo_user_id`:
      фильтр берёт там сообщения одного отправителя, и сервер отдаёт только их.

    Если чат приглашений совпадает с чатом swinfo, у этого чата два чтения, и сообщения swinfo
    не вытесняются из лимита чужими сообщениями общего чата. Отправитель входит в чтение,
    поэтому смена `swinfo_user_id` (или чата) даёт новое чтение без отметки — курсор прежнего
    отправителя не применяется к новому.
  - **Отметка** — `msg_id`, до которого включительно всё нужное из чтения уже в журнале: самое
    новое сообщение, прочитанное последним удачным проходом (для чтения по отправителю — самое
    новое его сообщение). Хранится в `tg_chat_marks` (раздел 4.1) и пишется в конце каждого
    удачного прохода; запись только увеличивает отметку (`GREATEST`), поэтому опоздавшая запись
    прежнего держателя аренды её не откатывает. Отметки принадлежат журналу, а не сессии: выход
    из Telegram и сброс ключа их не удаляют, retention журнала на них не влияет. При старте
    движка отметки чтений, которых больше нет в настройках, удаляются: чат, добавленный снова,
    читается с последнего сообщения.
  - **Проход** читает сообщения новее отметки — до 1000, по порядку от старых; если их больше,
    берутся последние 1000 и аккаунт получает предупреждение `history_gap_truncated`. Плюс 50
    сообщений на отметке и перед ней — ловятся правки недавних сообщений. Одним запросом к
    журналу проход отбирает сообщения, которых там нет с тем же `msg_id`, `revision` и
    `content_hash`, и только их передаёт в конвейер — с признаком `recovered` (приход позже даты
    больше чем на 60 с, как сейчас). Проход удачен, когда переданное записано в журнал; тогда
    отметка становится равной самому новому прочитанному `msg_id`. Живые обновления отметку не
    двигают, поэтому сколько бы их ни пришло во время пропуска, следующий проход читает от
    места, до которого журнал проверен.
  - **Нет отметки** (новый аккаунт, чат впервые в настройках): проход ставит отметку на
    последнее сообщение и историю до него не читает — как сейчас, бот не загружает прошлое чата.
  - **Когда.** Проходы идут отдельной задачей аккаунта — только когда аккаунт вошёл, прошёл
    проверку привязки и вышел в онлайн:
    - сразу после `go_online` (старт движка, вход, подключение после перегрузки);
    - при переподключении главной сессии — `connect_handler` с `session is client.session`
      (при первом `connect()` это ещё `None`, его покрывает `go_online`; сессии других DC и
      медиа не в счёт). Обработчик только ставит проход в очередь и не ждёт: kurigram выполняет
      его внутри `Session.start`;
    - при `UpdatesTooLong`, `UpdateChannelTooLong` и ошибке внутри `handle_updates` —
      транспорт перехватывает их в `handle_updates` своего подкласса клиента (kurigram их только
      пишет в лог);
    - раз в 5 минут — от молчаливых пропусков, о которых Telegram не сообщает.

    Проход, запрошенный во время идущего, выполняется сразу после него. Неудачный проход
    (FloodWait, таймаут, ограда аренды, потеря входа) отметку не меняет и повторяется через
    30 с, 1, 2, 5 минут.

  Гарантия: сообщение отслеживаемого чата, не попавшее в журнал по любой причине — сбой
  процесса, обрыв связи, перегрузка, разрыв обновлений или молчаливый пропуск, — попадает в
  журнал не позже чем через 5 минут онлайна, а при известном событии — сразу. Не ловятся: правка
  сообщения глубже 50 перед отметкой (игра правит свежие сообщения, а сообщения открытых
  действий перечитывает сверка шлюза, как сейчас) и разрыв больше 1000 сообщений — с
  предупреждением. Цена — запрос на чтение раз в 5 минут и при событиях; после долгого простоя —
  до 10 страниц по 100.
- **Шифрование.** Новая зависимость `cryptography`, AES-256-GCM. Ключ — `PYROBOT_SECRET_KEY`
  (32 байта, urlsafe base64), обязателен. Формат шифротекста: байт версии, 12 байт nonce,
  шифротекст с тегом. AAD — `pyrobot:<назначение>:<account_id>`, чтобы блоб нельзя было
  подставить другому аккаунту.
- **Проверка ключа.** При первом старте в `server_meta.key_check` пишется зашифрованная
  известная строка (AAD `pyrobot:key_check:0`). При каждом старте:
  - ключа нет или он не 32 байта в base64 — процесс не стартует, в логе ошибка с командой
    генерации ключа;
  - ключ не расшифровывает `key_check` (не тот ключ) — процесс не стартует, в логе «ключ не
    подходит к базе»;
  - `PYROBOT_SECRET_KEY_RESET=1` при неподходящем ключе — осознанный сброс: удаляются все
    `tg_sessions`, `tg_peers` (и на этапе 2 — `accounts.tg_api_hash`),
    `key_check` пишется новым ключом, все аккаунты входят в Telegram заново. Флаг убирают после
    старта; при подходящем ключе он ничего не делает.
- **Сбой расшифровки у одного аккаунта** (повреждённый блоб при подходящем ключе): строки сессии
  аккаунта удаляются, движок стартует без Telegram, уведомление аккаунта `tg_session_unreadable`
  (error) — нужен вход заново.
- **Вход.** `TgAuthManager` у каждого аккаунта свой; попытка входа привязана к сессии админки
  внутри своего `AccountRuntime`. Привязка проверяется **до** `go_online` (сейчас `_accept`
  сначала выходит в онлайн, а ошибку привязки глушит): другой пользователь Telegram —
  `unexpected_user`, пользователь, привязанный к другому аккаунту, — `tg_user_taken`; в обоих
  случаях выход из сессии, обновления не обрабатываются. Первый успешный вход записывает
  `accounts.tg_user_id`.
- **Свой чат в настройках запрещён.** «Избранное» аккаунта (раздел 5.2) никогда не попадает в
  журнал:
  - правка настроек, в которой поле `chats.*` совпадает с `accounts.tg_user_id`, — 422
    `chat_is_self`;
  - пока аккаунт не привязан (`tg_user_id` NULL), сравнить не с чем, поэтому та же проверка
    идёт при входе — после получения пользователя Telegram и проверки привязки, до
    `go_online`, — и перед каждым выходом в онлайн. Совпало — привязка записывается, но в
    онлайн аккаунт не выходит и обновления не обрабатываются: статус Telegram `chat_is_self`,
    предупреждение аккаунта с именем поля. После исправления настроек (теперь его проверяет
    422) — перезапуск аккаунта.
- **Коды входа.** Не больше `PYROBOT_TG_CODES_PER_HOUR` (по умолчанию 10) запросов кода на хост
  и 3 в час на аккаунт; сверх — 429 `tg_code_rate_limited` с `Retry-After`.

### 4.4. API

Все пути, относящиеся к аккаунту, переезжают под `/api/v1/accounts/{account_id}/`:

| Было | Стало |
|---|---|
| `/engine/status`, `/engine/kill`, `unkill`, `pause`, `resume`, `reconciled` | `/accounts/{id}/engine/…` + новый `POST /accounts/{id}/engine/restart` |
| `/tg/status`, `/tg/login/start`, `code`, `password`, `/tg/logout` | `/accounts/{id}/tg/…` |
| `/state`, `/settings`, `/settings/history`, `/planner/outlook` | `/accounts/{id}/…` |
| `/journal`, `/decisions/{id}`, `/actions/{id}`, `/scenario-runs`, `/scenario-runs/{id}` | `/accounts/{id}/…` |
| `/commands/send`, `/commands/click`, `/scenarios/{name}/run` | `/accounts/{id}/…` |
| `/metrics`, `/metro/runs`, `/metro/runs/{id}`, `/unrecognized`, `/unrecognized/ack`, `/notifications`, `/notifications/read`, `/daily`, `/events` | `/accounts/{id}/…` |

Глобальные: `/auth/*`, `GET /scenarios` (каталог), `/healthz`, `/readyz`, и новые:

- `GET /accounts` — аккаунты текущей учётки: `id`, `name`, `status`, `status_reason`,
  `tg` (`user_id`, `online`), `mode`, `paused`, `killed`, `last_action_at`,
  `unread` (`warn`, `error`).
- `POST /accounts` `{name}` → 201, аккаунт `enabled`; 409 `name_taken`, 409 `capacity_reached`.
- `PATCH /accounts/{id}` `{name?, enabled?}`; 409 `name_taken`, 409 `capacity_reached`.
- `DELETE /accounts/{id}` `{confirm_name}` → 202; несовпадение имени — 422
  `confirm_name_mismatch`.
- `GET /host/status` — здоровье процесса и хоста: блокировки, задачи процесса, задержка цикла,
  запущенные движки. Поля здоровья процесса уходят из статуса аккаунта.

Правила:

- **Доступ** — одна зависимость `account_scope`: загрузить аккаунт, проверить
  `owner_id == текущая учётка`; чужой и несуществующий — одинаково 404 `account not found`.
  Отдаёт `DbReads(db, account_id)` и `EngineClient` аккаунта (или `None`, если движок не
  запущен).
- **Движок не запущен** (аккаунт `disabled`, `error`, `deleting` или блокировка у другого
  хоста). Из базы работают:
  - `engine/status` — `running: false`, `status`, `status_reason`, `host_reason`, режим, пауза и
    kill из настроек;
  - `state` — из `state_snapshot`;
  - `settings` — чтение и правка: запись в базу напрямую с оптимистической версией и проверкой
    модели `Settings`, применяется при следующем старте движка (так исправляется настройка,
    из-за которой аккаунт падает при старте). Прямая запись и старт движка упорядочены арендой
    (раздел 4.2):
    - прямая запись — одна транзакция: `SELECT lease_holder, lease_expires_at FROM accounts
      WHERE id = <аккаунт> FOR SHARE`, и только если аренды нет (`lease_holder` NULL или
      `lease_expires_at` в прошлом) — запись настроек с проверкой версии;
    - аренда есть — прямой записи нет: правка идёт через движок (`EngineClient`); движок ещё не
      зарегистрирован в хосте — API ждёт его до 5 с, затем 503 `engine_starting` с
      `Retry-After: 2`;
    - движок читает настройки только после того, как захват аренды закоммичен. Захват
      (`UPDATE accounts`) ждёт коммита прямых записей, державших строку `FOR SHARE`, поэтому
      движок видит каждую запись, начатую до захвата, а запись, начатая после, видит аренду и
      уходит в движок.

    Так настройки аккаунта в каждый момент пишет кто-то один — держатель аренды или прямая
    запись без аренды, — и кэш движка не устаревает (раздел 6.4);
  - `settings/history`, журнал, запуски, метрики, метро, нераспознанные, уведомления, итоги;
  - `tg/status` — `state: stopped` и привязка.

  Остальные — `engine/kill|unkill|pause|resume|reconciled|restart`, `tg/login/*`, `tg/logout`,
  `planner/outlook`, `commands/*`, `scenarios/{name}/run`, `events` — 503 `engine not running`.
  `engine/restart` у `error`-аккаунта не нужен: его включают (`PATCH enabled: true`).
- **Токен подтверждения** подписывает и `account_id`.
- Старых путей нет: API и админка выкатываются вместе. `tools/login.py` получает `--account`.
- `openapi.json` и `schema.d.ts` пересобираются; CI проверяет их, как сейчас.

### 4.5. События (SSE)

- `GET /accounts/{id}/events` — поток `EventStream` своего `AccountRuntime`; формат событий,
  `Last-Event-ID` и причины `reset` не меняются. Перепроверка сессии каждые 15 с — как сейчас.
- Движок не запущен — 503; клиент переподключается с нарастающей паузой и показывает «движок не
  запущен».
- Общего потока нет: список аккаунтов со статусами админка перечитывает раз в 30 с и при
  возвращении на вкладку.

### 4.6. Админка

- **Маршруты.** Все нынешние экраны — под `/a/[account]/…` (главная, журнал, управление, метро,
  итоги, метрики, настройки, уведомления, Telegram). Глобальные: `/login`, `/password`,
  `/accounts`. `/` ведёт в последний открытый аккаунт (`localStorage` `pyrobot.account`) или на
  `/accounts`, если аккаунтов нет. Старые ссылки (`/journal` и т. п.) перенаправляются в
  `/a/<последний>/…`. Сервер отдаёт `index.html` для путей без расширения, как сейчас.
- **Переключатель.** На ПК — вверху бокового меню: имя, точка статуса, счётчик непрочитанных
  warn/error. На телефоне — плашка с именем вверху экрана и список аккаунтов в «Ещё».
- **Контекст аккаунта.** `startApp()` делится на общую часть (сессия, тема, тикер) и
  `startAccount(id)`: клиент API аккаунта, SSE, статус движка, персонаж, непрочитанные.
  Переключение закрывает SSE и пересоздаёт контекст; постраничные хранилища пересоздаются вместе
  с маршрутом. Все потребители уже перечитывают данные по `reset`.
- **Клиент API аккаунта** сам подставляет `account_id` в пути `/accounts/{account_id}/…`; типы —
  из `openapi.json`.
- **Экран `/accounts`.** Имя, пользователь Telegram, статус и причина, `dry_run`/`live`, пауза и
  kill, Telegram онлайн, последнее действие, warn/error; создание, переименование,
  включение/выключение, удаление с вводом имени.
- **Экран Telegram** показывает, к какому пользователю Telegram аккаунт привязан навсегда, и
  объясняет, что другой персонаж — это новый аккаунт. Экраны аккаунта без движка показывают
  данные из базы и плашку «движок не запущен: причина» с кнопкой «включить».
- **Новый аккаунт:** создать → экран Telegram, вход → настройки (`dry_run`) → включить `live`
  прежним путём.

### 4.7. Перенос нынешней установки

Миграция Alembic:

1. Колонки `accounts` из 4.1: `owner_id` — id первой (по `id`) строки `admin_users` или NULL,
   если учёток нет; `name = 'Основной'`, `status = 'enabled'`. При каждом старте, после
   `ensure_admin`, аккаунты с `owner_id` NULL получают первую учётку (на этапе 2 — первого
   `owner`). Так переживается новая установка без учётки и учётка, удалённая до обновления;
   после обновления удалить учётку с аккаунтами не даст FK.
2. `tg_user_id` ← `settings.data->'telegram'->>'expected_user_id'`; ключ `telegram` удаляется
   из JSON настроек.
3. Таблицы `tg_sessions`, `tg_peers`, `tg_chat_marks`, `server_meta`, индексы.
4. `setval('accounts_id_seq', max(id))`: миграция 0001 вставила `id = 1` явно, счётчик не
   сдвинут, и первое `POST /accounts` упало бы на дубле ключа.
5. `tg_chat_marks` аккаунта 1 — по журналу, чтобы сверка вернула сообщения, пришедшие за время
   обновления: (чат игры, 0) и (канал смузи, 0) — наибольший `msg_id` чата в журнале;
   (чат swinfo, `swinfo_user_id`) — наибольший `msg_id` сообщений этого отправителя в чате. Эти
   чтения журнал берёт целиком, поэтому отметка по нему точна. Для (чат приглашений, 0)
   отметка не ставится
   (журнал берёт из него не всё, и отметка отстала бы от чата): её поставит первый проход на
   последнее сообщение — в том числе когда это тот же чат, что swinfo.

При старте:

- Если у аккаунта 1 нет строки `tg_sessions`, а файл `<data_dir>/pyrobot.session` есть, поля
  сессии, пиры чатов из настроек аккаунта и пир `swinfo_user_id` читаются из файла
  (`SQLiteStorage` kurigram),
  записываются в `PgSessionStorage`, файл переименовывается в `pyrobot.session.migrated`.
  Состояние обновлений не переносится: пропущенное за время обновления вернёт сверка истории
  при первом выходе в онлайн (раздел 4.3). Ошибка переноса —
  предупреждение аккаунта `tg_session_import_failed`, файл остаётся, аккаунт требует входа.
- `PYROBOT_SECRET_KEY` обязателен; `deploy/render-env.sh` и `.env.example` получают его; первый
  старт пишет `key_check`.
- `PYROBOT_ACCOUNT_ID` больше не читается; если задан — предупреждение в лог.
- **Пароль админки.** Совет README «`DELETE FROM admin_users`» после миграции не работает (FK), его
  заменяет `python -m app.tools.users set-password <login>`: спрашивает новый пароль, закрывает
  сессии учётки. CLI появляется на этапе 1; на этапе 2 к нему добавляется `promote`.
- **Проверка после выкатки** (ручная, в README): `/readyz` больше не отражает Telegram, поэтому
  после обновления смотрят в админке, что аккаунт 1 онлайн в Telegram без перелогина.

Откат: откат миграции (возвращает `telegram.expected_user_id` в настройки) и переименование
`pyrobot.session.migrated` обратно.

### 4.8. Тесты этапа 1

- `EngineHost`: запуск, остановка, перезапуск одного аккаунта не трогает остальные; два хоста
  на одной базе не запускают один аккаунт; 5 сбоев за 10 минут — `error` и уведомление.
- `PgSessionStorage`: общий набор проверок интерфейса `Storage`, который проходит и
  `SQLiteStorage` (без сохранения состояния обновлений и пиров вне настроенных чатов между
  открытиями — их `PgSessionStorage` держит в памяти); `close()` и повторный `open()` того же
  объекта; шифрование туда и обратно, чужой AAD, отсутствующий и неверный ключ; импорт
  из файла — поля сессии и пиры чатов из настроек, без состояния обновлений.
- Матрица доступа: список путей аккаунта собирается из приложения автоматически; для каждого
  чужой аккаунт — 404.
- Токен подтверждения не принимается на другом аккаунте.
- Удаление аккаунта: остановка, выход из Telegram (в том числе временным клиентом у
  выключенного), чистка всех таблиц, строки `accounts` нет.
- Аккаунт без движка: `engine/status`, `state`, чтение и правка `settings` работают из базы,
  правка применяется при старте; «живые» пути — 503.
- Прямая запись настроек и старт движка: запись, начатая до захвата аренды, видна движку при
  старте (захват ждёт её коммита); начатая после — уходит в движок; движок, ещё не
  зарегистрированный в хосте, — ожидание до 5 с, затем 503 `engine_starting`.
- Привязка: выход не снимает `tg_user_id`; вход другим пользователем — `unexpected_user`; вход
  пользователем, привязанным к другому аккаунту, — `tg_user_taken`; в обоих случаях `go_online`
  не вызывается и ни одно обновление не доходит до конвейера. Поле `chats.*`, равное
  `tg_user_id`, — 422 `chat_is_self`; у непривязанного аккаунта свой id, заранее вписанный в
  `chats.game_chat_id`, обнаруживается при первом входе: привязка записана, `go_online` не
  вызван, статус `chat_is_self`.
- **Аренда** (два хоста на одной базе, подменённые часы):
  - обрыв соединения блокировок (`pg_terminate_backend`) во время отправок: продлений нет,
    прежний держатель останавливается по местному сроку, новый захватывает аренду не раньше
    `lease_expires_at`; вызовов Telegram и пишущих транзакций двух держателей одновременно не
    бывает ни в одной точке сценария;
  - условный захват: при действующей чужой аренде — ноль строк и ожидание до её срока; своя
    аренда (тот же хост) захватывается сразу;
  - продление одним запросом по `(id, lease_epoch)`: аккаунт с чужой эпохой не продлевается и
    останавливается аварийно — без доработки конвейера и без финальных записей;
  - ограда Telegram: вызов, начатый до срока, прерывается `wait_for` на сроке, в том числе
    `invoke`, ждущий запуска сессии; после срока вызов не начинается;
  - ограда базы: запись `state_snapshot`, `settings` и создание действия с устаревшей
    `lease_epoch` — ноль строк, аренда считается потерянной;
  - перезапуск на том же хосте: новый `AccountRuntime` не стартует, пока прежний не
    остановился; задача чистки удаляемого аккаунта на том же хосте ждёт полной остановки
    движка; блокировка аккаунта не берётся хостом повторно;
  - запись с проверкой эпохи (`FOR SHARE`), начатая до захвата аренды другим хостом, коммитится
    раньше захвата; начатая после — `LeaseLost`, в `settings` — не `version_conflict`;
  - аварийная остановка идёт по порядку из п. 6 и заканчивается при полной очереди конвейера и
    очереди диспетчера: клиент не принимает обновлений и не переподключается, хранилище не
    сохраняется; `LeaseLost` прерывает повторы `Pipeline._append`;
  - штатная остановка очищает `lease_holder` и `lease_expires_at`: другой хост захватывает
    сразу, без ожидания TTL; продление идёт, пока дорабатывает конвейер; продление, собранное до
    освобождения и выполненное после него, аренду не возобновляет, и следующий хост не ждёт TTL; освобождение с чужой эпохой или после местного
    срока не трогает аренду нового держателя;
  - продление, упёршееся в `lock_timeout` из-за ограждённой транзакции, повторяется через 1 с
    и успевает до местного срока;
  - быстрый перезапуск между сборкой продления и разбором ответа: продление собрано для эпохи 7,
    аккаунт остановлен и захвачен с эпохой 8, ответ по эпохе 7 без строки аккаунта — новый
    движок не останавливается и его местный срок не меняется;
  - переподключение соединения блокировок: прежние эпохи не продлеваются, аккаунты
    захватываются заново после аварийной остановки своих движков.
- **Сверка истории** (фейковый Telegram с историей чатов):
  - падение после того, как kurigram сохранил `pts`, но до записи в журнал: после рестарта
    сообщение попадает в журнал ровно один раз;
  - переподключение главной сессии с сообщениями, пропущенными за время обрыва, и живыми
    сообщениями после него, записанными раньше прохода: пропущенные в журнале;
  - `UpdatesTooLong`, `UpdateChannelTooLong` и ошибка внутри `handle_updates` запускают проход;
  - молчаливый пропуск без события находится периодическим проходом не позже чем через 5 минут;
  - проход, запрошенный во время идущего, выполняется после него; неудачный проход не двигает
    отметку и повторяется; сбой процесса посреди прохода — после рестарта проход от прежней
    отметки;
  - чат, где фильтр берёт не всё (приглашения к биржевикам в чате команды): отметка — самое новое
    сообщение чата, короткий обрыв — один запрос без `history_gap_truncated`;
  - swinfo читается поиском по отправителю; если чат приглашений — тот же чат, у него два чтения,
    и сообщения swinfo не вытесняются из лимита 1000 чужими;
  - в конвейер уходят только сообщения, которых нет в журнале с тем же `msg_id`, `revision` и
    `content_hash`; правка среди 50 перед отметкой — новая ревизия;
  - больше 1000 новых сообщений — последние 1000 и предупреждение `history_gap_truncated`;
  - нет отметки — она ставится на последнее сообщение, старая история не читается; отметки
    чтений, убранных из настроек, удаляются при старте;
  - проходов нет до входа, до проверки привязки и для сессий других DC и медиа;
    `connect_handler` не ждёт прохода;
  - запись отметки только увеличивает её: опоздавшая запись прежнего держателя не откатывает;
  - пир `swinfo_user_id` переживает перезапуск, поиск по отправителю работает сразу после старта;
  - миграция: отметки аккаунта 1 по журналу для чатов игры и смузи и для отправителя swinfo;
  - смена `swinfo_user_id` в том же чате: новое чтение начинается с последнего сообщения нового
    отправителя, отметка прежнего удаляется и к новому не применяется;
  - восстановленное помечено `recovered`.
- **Перегрузка.** Выше `OVERLOAD_HIGH` остановка идёт в порядке `session.stop()` →
  `terminate()` → `disconnect()`, принятое до остановки разобрано; ниже `OVERLOAD_LOW` создаётся
  новый объект клиента с тем же хранилищем, без повторного входа; пропущенное приходит сверкой
  истории; повторного входа в перегрузку от самой сверки нет.
- **Желаемое состояние.** Пропущенное уведомление о перезапуске отрабатывается сверкой за 30 с по
  `engine_generation`.
- Ключ: нет ключа, битый, не тот (`key_check`), `PYROBOT_SECRET_KEY_RESET`; повреждённый блоб
  одного аккаунта — `tg_session_unreadable`.
- `tg_peers`: пиры настроенных чатов переживают перезапуск.
- `capacity_reached` считает только `enabled`; `setval` счётчика — второй аккаунт создаётся.
- `app.tools.users set-password` меняет пароль и закрывает сессии.
- Миграция: upgrade/downgrade на данных, похожих на прод, включая перенос `expected_user_id`.
- Админка: переключатель, префиксы маршрутов, перенаправление старых ссылок, пересоздание
  контекста при переключении, экран `/accounts`.
- **Замер** (`tools/bench_engines.py`, не в CI): N движков на фейковом транспорте
  воспроизводят записанный трафик фикстур; память, CPU, задержка цикла p50/p99 для N = 5, 10,
  20, 40. По результату выставляется `PYROBOT_MAX_ENGINES` по умолчанию и решается, когда нужен
  этап 3; результат записывается в README.

### 4.9. Готово, когда

- Нынешняя установка обновилась без перелогина в Telegram, всё работает на аккаунте 1.
- Владелец создал второй аккаунт, вошёл в Telegram, переключается между аккаунтами.
- Перезапуск, падение и выход из Telegram одного аккаунта не трогают другой.
- Замер выполнен, ёмкость по умолчанию выставлена.

## 5. Этап 2. Пользователи и доступ

### 5.1. Учётки и роли

`admin_users` переименовывается в `users` (FK `auth_sessions`, `accounts.owner_id` — вслед):

| Колонка | Тип | Смысл |
|---|---|---|
| `role` | varchar(8) NOT NULL, CHECK in (`owner`, `user`), по умолчанию `user` | владелец сервера или пользователь |
| `max_accounts` | int NOT NULL, по умолчанию 1 | лимит аккаунтов |
| `disabled_at`, `disabled_reason` | timestamptz / text NULL | отключён владельцем |
| `invited_by` | int NULL, FK `users.id` ON DELETE SET NULL | кто пригласил |
| `last_login_at` | timestamptz NULL | последний вход |
| `deleting_at` | timestamptz NULL | учётка удаляется (раздел 5.3) |

- Миграция делает `owner` все нынешние учётки (сейчас каждая из них — полный админ; несколько
  строк бывает, если менялся `PYROBOT_ADMIN_LOGIN`) с `max_accounts` = число их аккаунтов или
  10, что больше.
- `ensure_admin` создаёт учётку из окружения с ролью `owner`, если владельцев нет (новая
  установка); если владелец есть — ничего не делает, как сейчас.
- Второго владельца назначает только `python -m app.tools.users promote <login>`; экрана нет.
  Последнего владельца нельзя отключить, удалить или понизить — 409 `last_owner`.
- `SessionContext` получает `user_id` и `role`; `resolve` отклоняет сессию отключённой учётки
  (401). Вход обновляет `last_login_at`. `/auth/me` отдаёт `role`.
- **Правило доступа без исключений:** пути `/accounts/{id}/…` открыты только хозяину аккаунта;
  роль `owner` его не обходит.
- Отключение учётки: закрыть её сессии, остановить движки её аккаунтов (`status = disabled`,
  `status_reason = user_disabled`); включение возвращает прежний статус аккаунтов не
  автоматически — пользователь включает аккаунты сам.

### 5.2. Приглашения и восстановление пароля

Таблица `invites`:

| Колонка | Смысл |
|---|---|
| `id` | PK |
| `token_hash` | bytea UNIQUE — sha256 токена; сам токен (32 байта, urlsafe) показывается один раз |
| `created_by` | FK `users.id` ON DELETE SET NULL |
| `created_at`, `expires_at` | срок: по умолчанию 72 ч, не больше 30 дней |
| `max_accounts` | лимит новой учётки |
| `note` | varchar(128), «кому» |
| `used_at`, `used_by`, `revoked_at` | использование и отзыв |

- Ссылка: `/invite/<токен>`.
- `GET /api/v1/invites/{token}` (без входа) → `expires_at`. Неизвестный токен — 404
  `invite_not_found`; использованный, отозванный, истёкший — 410 `invite_gone`.
- `POST /api/v1/invites/{token}/accept` `{login, password}` → учётка `user` с `max_accounts` из
  приглашения и `invited_by`, сразу открывается сессия; 409 `login_taken`. Пароль — от 12
  символов, как сейчас. Ограничение попыток — тем же лимитером по IP, что и вход.
- Ответ на регистрацию содержит коды восстановления (ниже) — они показываются один раз.

**Восстановление пароля — только самим пользователем.** Владелец сервера чужие пароли в
приложении не сбрасывает: иначе он мог бы воспользоваться сбросом сам и войти в чужую игру.
Способы:

- **Код в «Избранное» Telegram.** `POST /api/v1/auth/recover/start` `{login}`: если у учётки есть
  аккаунт, онлайн в Telegram, бот отправляет одноразовый код из 8 цифр в «Избранное» (`me`)
  Telegram этого аккаунта — один и тот же код во все такие аккаунты учётки.
  - Отправляет движок аккаунта через помощник вызовов Telegram с оградой аренды (раздел 4.2),
    мимо шлюза игровых команд; на этапе 3 шлюз просит об этом воркер через внутренний API
    (раздел 6.3). Ответ пользователю не ждёт отправки.
  - «Избранное» — не отслеживаемый чат, и указать его в настройках нельзя (`chat_is_self`,
    раздел 4.3): код не попадает ни в журнал, ни в админку.
  - Запрос хранится в таблице `recovery_requests`: `user_id` PK FK ON DELETE CASCADE,
    `code_hash` (HMAC-SHA256 кода; ключ выводится из `PYROBOT_SECRET_KEY` через HKDF с
    назначением `recovery`), `expires_at` (10 минут), `attempts` (не больше 5). У учётки один
    действующий запрос: новый `recover/start` заменяет прежний. Удачное использование,
    исчерпанные попытки или истёкший срок удаляют строку.
  - Ответ всегда одинаковый («если у учётки есть аккаунт в Telegram, код отправлен»), чтобы по
    нему нельзя было узнать, есть ли такой логин.
- **Коды восстановления.** 10 одноразовых кодов выдаются при регистрации.
  - Таблица `recovery_codes`: `id` PK, `user_id` FK ON DELETE CASCADE, `code_hash` (argon2),
    `used_at`.
  - Код несёт номер своей строки: `<id>-<секрет>`, секрет — 10 символов base32 (50 бит),
    например `412-K7QM2-XH9TD`. Проверка — одна строка по `id` и учётке из логина и одна
    проверка argon2; чужой, несуществующий или использованный код — тот же 403 `invalid_code`.
  - Перевыпуск: `POST /api/v1/auth/recovery-codes` `{password}` (с входом) → 10 новых кодов,
    показываются один раз, прежние строки удаляются. Неверный пароль — 403 `invalid_password`,
    ограничение — лимитером входа. Пишется в журнал действий.
- `POST /api/v1/auth/recover/finish` `{login, code | recovery_code, password}` → новый пароль,
  все сессии учётки закрываются, открывается новая; во все аккаунты учётки — уведомление
  `password_recovered` (warn) с временем и способом. Неверный код — 403 `invalid_code`.
- Ограничения: `recover/start` — 3 в час на логин и лимитер по IP; `recover/finish` — лимитер по
  IP, 5 попыток на код из «Избранного» и 10 неверных кодов восстановления в час на логин.
- Нет ни аккаунта онлайн, ни кодов восстановления — владелец может только удалить учётку и
  выдать новое приглашение; данные прежней учётки не переносятся.
- Потерявший доступ владелец сервера и любой, у кого есть доступ к серверу,
  пользуется `python -m app.tools.users set-password <login>` (этап 1). Это уровень root, а не
  права в приложении: команда пишет в журнал действий (`actor_login = "cli"`), а у
  пользователя во всех аккаунтах появляется уведомление `password_set_by_cli` (warn).

### 5.3. Консоль владельца

Экран `/admin` с вкладками; API `/api/v1/admin/*`, доступен только `owner`, остальным — 404.
Ответы консоли содержат только служебные поля: схема ответа не включает состояние персонажа,
журнал, настройки, команды, метрики, метро и тексты уведомлений аккаунтов.

- **Пользователи** (`GET /admin/users`, `PATCH /admin/users/{id}`, `DELETE /admin/users/{id}`
  с `confirm_login`): логин, роль, когда заведён, последний вход, аккаунтов из лимита, отключён
  ли и почему; изменить лимит, отключить или включить, удалить вместе с аккаунтами. Сброса
  чужого пароля нет (раздел 5.2).
  - `DELETE /admin/users/{id}` → 202: учётка сразу отключается (сессии закрыты, вход — 401),
    `deleting_at` ставится, все её аккаунты уходят в `deleting` и чистятся как в разделе 4.2.
    Строку `users` удаляет та же фоновая задача после чистки последнего аккаунта; до этого
    логин занят. Приглашения и записи журнала действий этой учётки остаются (FK SET NULL).
- **Аккаунты** (`GET /admin/accounts`, `PATCH /admin/accounts/{id}`,
  `POST /admin/accounts/{id}/restart`, `DELETE /admin/accounts/{id}` с `confirm_name`): чей,
  имя, статус и причина, заблокирован ли владельцем, работает ли движок, онлайн ли Telegram,
  перезапуски за 24 ч, код последней ошибки и когда, нагрузка (сообщений и действий за час),
  строк в базе по основным таблицам. Действия: заблокировать с причиной, разблокировать,
  перезапустить движок, удалить.
- **Приглашения** (`GET/POST /admin/invites`, `DELETE /admin/invites/{id}`): создать
  (лимит аккаунтов новой учётки, срок, пометка «кому»), список неиспользованных, отозвать.
- **Сервер** (`GET/PATCH /admin/server-settings`): раздел 5.4.
- **Журнал действий** (`GET /admin/audit`): раздел 5.7.
- **Уведомления сервера** (`GET /admin/notifications`, `POST /admin/notifications/read`).
- `GET /host/status` доступен только `owner`.

Блокировка аккаунта владельцем — колонки `accounts.blocked` (bool) и `accounts.blocked_reason`:
движок останавливается, пользователь видит причину в статусе, получает уведомление аккаунта
`account_blocked` и не может включить аккаунт (403 `blocked_by_owner`) до разблокировки.

### 5.4. Настройки сервера

Таблица `server_settings`: одна строка (`id = 1`), `version`, `data` JSONB; модель
`ServerSettings`, правка с оптимистической версией, история — в журнале действий.

| Секция | Поля (по умолчанию) |
|---|---|
| `retention` | переезжает из `Settings.retention` аккаунта: `messages_days` 90, `decisions_days` 30, `metrics_days` 365, `ledger_days` 31; плюс `audit_days` 365 |
| `invites` | `default_ttl_h` 72, `default_max_accounts` 1 |
| `limits` | `max_accounts_total` 50, `sse_per_user` 5, `tg_codes_per_hour` 10, `tg_codes_per_account_hour` 3 |
| `engine_bounds` | `min_request_interval_s_min` 1.6, `antiflood_pause_s_min` 10, `antiflood_retry_max_max` 2, `action_ttl_s_max` 600 |

Retention — задача процесса (раздел 4.2) по политике сервера; кроме данных аккаунтов она чистит
уведомления сервера (`notifications` с `account_id` NULL, по `messages_days`) и `audit_log`
(по `audit_days`).

### 5.5. Лимиты и защита от злоупотреблений

- Три проверки, у каждой своё:
  - `limit_reached` (409) — аккаунтов учётки, кроме `deleting`, стало бы больше
    `users.max_accounts`; проверяется при создании;
  - `server_full` (409) — аккаунтов на сервере, кроме `deleting`, в любом статусе, стало бы
    больше `limits.max_accounts_total`; проверяется при создании;
  - `capacity_reached` (409) — `enabled` аккаунтов стало бы больше ёмкости хоста
    (`PYROBOT_MAX_ENGINES`, на этапе 3 — суммы ёмкостей живых воркеров); проверяется при
    создании и включении.

  `POST /accounts` проверяет их в этом порядке. `max_accounts_total` можно поставить больше
  ёмкости: лишние аккаунты тогда существуют только выключенными.
- **Границы настроек движка.** `PATCH /accounts/{id}/settings` за пределами `engine_bounds` — 422
  `setting_out_of_bounds` с путём и границей. `GET settings` отдаёт границы, админка показывает
  их у полей. Границы действуют для всех, включая владельца сервера. При ужесточении границ
  существующие значения за пределами приводятся к границе при следующем старте движка, с
  записью в историю настроек (`changed_by = "system"`).
- Запрещённые классы команд (`forbidden`, `donate`) — 403, как сейчас.
- Коды входа в Telegram — лимиты из `limits`.
- SSE — не больше `sse_per_user` одновременных потоков на учётку; сверх — 429.

### 5.6. Своё приложение Telegram

- Колонки `accounts.tg_api_id` (int NULL) и `accounts.tg_api_hash` (bytea NULL, зашифрован
  ключом сервера, AAD `pyrobot:tg_api_hash:<account_id>`).
- `PUT /accounts/{id}/tg/app` `{api_id, api_hash}` и `DELETE /accounts/{id}/tg/app` — только
  когда аккаунт вышел из Telegram, иначе 409 `tg_logged_in`. api_id — положительное число,
  api_hash — 32 шестнадцатеричных символа; иначе 422. После изменения движок, держащий аккаунт,
  пересоздаёт клиент kurigram с новыми данными (без перезапуска остального движка; на этапе 3 —
  по вызову внутреннего API, раздел 6.3); движок не запущен — новые данные берутся при старте.
  Следующий вход идёт через новое приложение. Сбой расшифровки `tg_api_hash` — поле очищается, уведомление аккаунта
  `tg_app_unreadable`, используется серверное приложение.
- `GET /accounts/{id}/tg/status` отдаёт `app`: `server` или `{api_id}`; hash не отдаётся никогда.
- Не задано — клиент использует `PYROBOT_TG_API_ID`/`PYROBOT_TG_API_HASH`.
- Экран Telegram получает блок «Своё приложение Telegram».

### 5.7. Журнал действий и уведомления сервера

- Таблица `audit_log`: `id`, `at`, `actor_user_id` (FK ON DELETE SET NULL), `actor_login`
  (копия), `action`, `target_type`, `target_id`, `details` JSONB. Пишутся: создание и отзыв
  приглашений, регистрация, восстановление пароля (кем и каким способом), перевыпуск кодов
  восстановления, `set-password` из CLI, лимиты, отключение/включение учёток, блокировка и удаление аккаунтов, правка настроек
  сервера, назначение владельца. Срок хранения —
  `retention.audit_days`.
- Уведомления сервера — в таблице `notifications` с `account_id` NULL (колонка становится
  nullable), видны только владельцам: аккаунт ушёл в `error`, упёрлись в лимит кодов Telegram,
  использовано приглашение, потеряно соединение блокировок хоста.

### 5.8. Перенос

Миграция: переименование таблицы, новые колонки и таблицы; нынешний админ — `owner`;
`server_settings.retention` ← `retention` настроек аккаунта 1, ключ `retention` удаляется из

### 5.9. Тесты этапа 2

- Матрица доступа: для каждого пути аккаунта чужой аккаунт — 404 и для `user`, и для `owner`;
  `/admin/*` для `user` — 404.
- Первый владелец: новая установка — `ensure_admin` создаёт `owner`; миграция с двумя учётками —
  обе `owner`.
- Удаление учётки: 202, вход закрыт сразу, логин занят до конца чистки, строка удалена после
  последнего аккаунта.
- Лимиты: `limit_reached`, `server_full`, `capacity_reached` — каждый считает своё.
- Retention чистит данные выключенных аккаунтов, уведомления сервера и `audit_log`.
- Ответы консоли сверяются со схемой: запрещённых полей нет.
- Приглашения: срок, повтор (410), отзыв, `login_taken`, лимитер; коды восстановления
  выдаются при регистрации один раз.
- Восстановление: код приходит в «Избранное» каждого аккаунта учётки, онлайн в Telegram, и не
  попадает в журнал; ответ `recover/start` одинаков для существующего и несуществующего логина;
  срок и число попыток кода; код восстановления одноразовый; после восстановления сессии закрыты
  и уведомление `password_recovered` есть во всех аккаунтах; у владельца нет пути сбросить чужой
  пароль через API.
- Запрос кода: повторный `recover/start` заменяет прежний код; 5 неверных попыток и истёкший
  срок удаляют запрос; код не проверяется у другой учётки.
- Коды восстановления: формат `<id>-<секрет>`, одна проверка argon2 на попытку; код другой
  учётки — `invalid_code`; перевыпуск по паролю делает прежние коды недействительными; удаление
  учётки удаляет её коды и запрос.
- `set-password` из CLI: запись в журнале действий с `actor_login = "cli"`, уведомление
  `password_set_by_cli` во всех аккаунтах учётки, сессии закрыты.
- Отключённая учётка: сессии закрыты, вход — 401, движки остановлены.
- Лимиты `limit_reached`, `server_full`; границы `setting_out_of_bounds`; `last_owner`;
  `blocked_by_owner`.
- Своё приложение Telegram: только при выходе, hash не утекает ни в одном ответе.
- Журнал действий пишется для каждого действия из 5.7.
- Админка: страница приглашения (регистрация и показ кодов восстановления), восстановление
  пароля со страницы входа, перевыпуск кодов в профиле, консоль.

### 5.10. Готово, когда

- Приглашённый пользователь зарегистрировался, завёл аккаунт, вошёл в Telegram и видит только
  своё.
- Владелец видит в консоли его учётку и аккаунт без игровых данных, может заблокировать,
  перезапустить, удалить.
- Лимиты и границы настроек работают.
- Пользователь восстановил пароль кодом из «Избранного» Telegram; у владельца пути сбросить
  чужой пароль нет.

## 6. Этап 3. Воркеры

### 6.1. Роли процессов

`PYROBOT_ROLE`:

- `all` (по умолчанию) — шлюз и хост движков в одном процессе; поведение этапов 1–2.
- `api` — шлюз: HTTP, админка, вход, учётки, консоль, чтение из базы, задачи процесса
  (retention, чистка удаляемых аккаунтов и учёток, очистка истёкших сессий);
  `EngineClient` — HTTP к воркеру.
- `worker` — `EngineHost` и внутренний HTTP на `PYROBOT_INTERNAL_PORT` (8081), наружу не
  публикуется.

Шлюз — один экземпляр (лимитер входа в его памяти). Секрет токенов подтверждения выводится из
`PYROBOT_SECRET_KEY` (HKDF, назначение `confirm`), а не генерируется при старте процесса.

### 6.2. Распределение аккаунтов

- Таблица `workers`: `id` (uuid), `url` (внутренний адрес), `capacity`, `engines`,
  `loop_lag_ms`, `rss_mb`, `started_at`, `heartbeat_at`, `draining`. Пульс — каждые 10 с;
  воркер без пульса 30 с считается мёртвым.
- Таблица `account_hosts`: `account_id` PK, `worker_id` FK ON DELETE CASCADE, `since` —
  подсказка для маршрутизации. Истина — аренда (раздел 4.2): умер воркер — его блокировки
  освобождаются сразу, а аккаунты подхватываются после `lease_expires_at`.
- Живые поля аккаунта для `GET /accounts` и консоли (`running`, `tg_online`, `restarts_24h`,
  `last_error_code`, `last_error_at`) воркер пишет в строку `account_hosts` с каждым пульсом;
  шлюз читает их из базы, без опроса воркеров. Нет строки или пульс воркера старше 30 с —
  `running: false`. На этапах 1–2 те же поля хост отдаёт из памяти.
- Воркер слушает `LISTEN pyrobot_accounts` (payload: `account_id`) и раз в 30 с сверяет сам:
  свои аккаунты — со статусом и `engine_generation` в базе, свободные `enabled` — для захвата.
- Воркер берёт свободный `enabled` аккаунт, если `engines < capacity` и его загрузка
  `engines / capacity` не больше наименьшей среди живых воркеров без `draining`, у которых
  есть свободное место (`engines < capacity`). Заполненные воркеры в минимуме не участвуют:
  при 5/5 и 6/20 аккаунт берёт второй. Порядок — по возрастанию `account_id`; одновременный
  захват двумя воркерами разрешает блокировка аккаунта.
- Автоматического перераспределения нет. Перераспределение — кнопка «перераспределить» в
  консоли (воркеры с загрузкой `engines / capacity` выше средней отдают лишние аккаунты по
  одному) и остановка
  воркера. При остановке воркер ставит `draining`, останавливает движки, отпускает блокировки;
  остальные подхватывают. Простой аккаунта при выкатке — время остановки и старта движка.
- Управление аккаунтом из шлюза: включить, выключить, удалить — шлюз меняет `accounts.status`;
  перезапустить — увеличивает `accounts.engine_generation`. Затем шлёт
  `NOTIFY pyrobot_accounts`. Воркер, держащий аккаунт, сверяет желаемое состояние (раздел 4.2):
  по уведомлению сразу, при пропущенном уведомлении — на ближайшей сверке раз в 30 с. Команда
  не теряется, потому что хранится в базе, а не только в уведомлении.
- Чистку удаляемого аккаунта выполняет задача шлюза. Статус `deleting` не даёт воркерам его
  взять; задача захватывает блокировку и аренду аккаунта по пп. 1–3 раздела 4.2 (в роли `all`
  чистка и движки — один хост, и п. 3 ждёт полной остановки движка), то есть ждёт
  `lease_expires_at` прежнего держателя, даже если его блокировка уже освободилась: прежний
  воркер мог потерять соединение и ещё дорабатывать до своего срока.

### 6.3. Внутренний API

- Пути `/internal/accounts/{id}/…` повторяют методы `EngineClient` — ровно те методы
  `EngineFacade`, которыми пользуются маршруты этапа 1: статус, kill/unkill/pause/resume/
  reconciled/restart, вход и выход в Telegram, состояние, чтение и правка настроек, план,
  команды, запуск сценария, события. Плюс операции этапа 2:
  - `POST /internal/accounts/{id}/tg/recovery-code` `{code}` — отправить код восстановления в
    «Избранное» (раздел 5.2); шлюз вызывает его у каждого онлайн-аккаунта учётки и не ждёт
    результата;
  - `POST /internal/accounts/{id}/tg/app` — пересоздать клиент kurigram после смены своего
    приложения Telegram (раздел 5.6).
- Авторизация — `Authorization: Bearer ${PYROBOT_INTERNAL_TOKEN}`; кто действует — заголовки
  `X-Pyrobot-User-Id`, `X-Pyrobot-Login`, `X-Pyrobot-Session` (для журнала действий, токенов
  подтверждения и привязки попытки входа в Telegram).
- Команды и сценарии ждут результат до 30 с, как сейчас; таймаут шлюза — 35 с.
- SSE: шлюз проксирует поток воркера байт в байт и передаёт `Last-Event-ID`.
- Маршрутизация: шлюз берёт воркер из `account_hosts` (кэш 5 с); нет воркера — 503
  `engine not running`. Повтор — только когда запрос точно не выполнен:
  - ответ воркера 404 `not_hosted` (воркер отказал, ничего не сделав) или отказ в соединении
    до отправки запроса — обновить кэш и повторить один раз;
  - чтения (`GET`, SSE) — повтор и при обрыве после отправки;
  - изменяющие запросы (вход в Telegram — `login/start`, `code`, `password`; выход; команды,
    сценарии, kill/pause/restart, код восстановления, `tg/app`), у которых соединение
    оборвалось после отправки или истёк таймаут, не повторяются: результат неизвестен, а
    повторный `login/start` отправил бы второй код и заменил попытку входа. Ответ — 502
    `engine_result_unknown`; админка перечитывает статус (`tg/status`, `engine/status`,
    действие по его id) и предлагает повторить вручную.
- Попытка входа в Telegram живёт в памяти воркера. Если аккаунт переехал посреди входа,
  попытка теряется и вход начинается заново.

### 6.4. Настройки между процессами

- Настройки аккаунта пишет держатель аренды — воркер (через свой кэш и подписчиков) — или,
  когда аренды нет, шлюз прямой записью; оба пути упорядочены арендой (раздел 4.4). Поэтому
  кэш воркера не устаревает, и уведомление о записи настроек между процессами не нужно:
  потерять его нечего.
- Конфликт версий в `DbSettingsStore.update`:
  - **`PATCH /settings` от пользователя** передаёт `version` (как сейчас): не совпала с версией
    — 409 `version_conflict` с текущей версией.
  - Условная запись в базу не прошла, хотя кэш совпадал (строку изменили в обход правила,
    например вручную), — хранилище перечитывает настройки из базы. Пользовательский `PATCH`
    после этого сравнивается с версией в базе: равна — запись повторяется один раз, иначе 409.
    Внутренняя запись без условия версии (kill, пауза, приведение к границам, флаги движка)
    применяет ту же функцию изменения к свежим настройкам один раз.
  - Потеря аренды (`LeaseLost`, раздел 4.2) — не конфликт: запись не повторяется, движок
    останавливается аварийно.

### 6.5. Ресурсы, наблюдаемость, деплой

- Пул воркера: `2 + ceil(engines/4)`, переполнение — столько же, плюс одно соединение
  блокировок; пул шлюза — 10. Три воркера и шлюз — около 60 соединений при стандартных 100 у
  Postgres. PgBouncer не используется: advisory-блокировкам уровня сессии нужен сессионный
  режим.
- `GET /host/status` в шлюзе: воркеры (пульс, движки, задержка цикла, память), кто какие
  аккаунты держит, включённые аккаунты, которые никто не держит.
- Логи: `account=<id> worker=<id>` в каждой записи.
- `compose.yml` — прежний один сервис в роли `all`. `compose.scale.yml` добавляет `api` (порт
  наружу) и `worker` (`--scale worker=N`, `mem_limit` на воркер из замера этапа 1), общий
  `PYROBOT_INTERNAL_TOKEN`.
- Цель: 50 аккаунтов на 2–3 воркерах, задержка цикла p99 < 100 мс, память в пределах лимитов.

### 6.6. Тесты этапа 3

Интеграционные тесты в CI (сервис Postgres уже есть), два процесса `worker` на фейковом
транспорте:

- распределение аккаунтов по правилу 6.2, в том числе при заполненном воркере (5/5 и 6/20 —
  берёт второй);
- изменяющий запрос с обрывом после отправки не повторяется (502 `engine_result_unknown`,
  второго кода входа нет); `not_hosted` и отказ в соединении — повтор;
- убитый воркер: аккаунты подхватывает второй;
- шлюз: 503 без воркера;
- SSE через шлюз с `Last-Event-ID`;
- настройки: правка через шлюз у выключенного аккаунта видна воркеру после включения; прямая
  запись шлюза, начатая одновременно с захватом аренды воркером, не теряется — она либо видна
  воркеру при старте, либо уходит в воркер; `PATCH` с устаревшей `version` — 409;
- перезапуск при потерянном `NOTIFY` выполняется сверкой по `engine_generation`;
- два воркера и обрыв соединения блокировок одного из них: прежний держатель останавливается по
  сроку аренды раньше, чем новый стартует (раздел 4.2);
- остановка воркера отдаёт аккаунты;
- чистка удаляемого аккаунта ждёт `lease_expires_at` прежнего воркера, даже когда его
  блокировка уже свободна;
- операции этапа 2 через внутренний API: код восстановления уходит в «Избранное» аккаунта на
  воркере, смена своего приложения Telegram пересоздаёт клиент на воркере.

### 6.7. Готово, когда

- Установка с `compose.scale.yml` и тремя воркерами держит 50 аккаунтов на фейковом транспорте
  с задержкой цикла p99 < 100 мс.
- Остановка любого воркера — его аккаунты поднимаются на остальных.
- Установка с одним сервисом `all` работает как на этапе 2.

## 7. Безопасность

- **Изоляция.** Пути аккаунта — только хозяину; чужой аккаунт — 404 для всех ролей. Консоль
  владельца отдаёт только служебные поля. Токены подтверждения подписывают аккаунт.
- **Секреты.** `PYROBOT_SECRET_KEY` шифрует `auth_key` сессий и `tg_api_hash`; AAD привязывает
  блоб к аккаунту. `PYROBOT_INTERNAL_TOKEN` закрывает внутренний API воркеров. Токены
  приглашений хранятся хэшами sha256, коды восстановления — хэшами argon2, коды из «Избранного» —
  HMAC с ключом, выведенным из `PYROBOT_SECRET_KEY`.
- **Вход и сессии** — как сейчас: argon2, cookie HttpOnly/SameSite=Strict, CSRF, лимитер;
  плюс проверка отключённой учётки.
- **Общий IP.** Плавный старт движков, лимиты кодов входа, нижние границы интервалов движка.
- **Журнал действий** владельца сервера виден владельцам.
- **Восстановление пароля** — только самим пользователем: код в «Избранное» его Telegram или
  код восстановления. Владелец сервера чужой пароль в приложении не сбрасывает. CLI
  `set-password` — уровень root: оставляет след в журнале действий и уведомление у пользователя.
- **Ограничение.** Root на сервере и доступ к базе с ключом дают всё; это не цель защиты.

## 8. Выкатка

1. Этап 1 → выкатка → ручная проверка: аккаунт 1 онлайн в Telegram без перелогина (раздел
   4.7) → второй аккаунт владельца.
2. Этап 2 → выкатка → первое приглашение.
3. Этап 3 — когда замер или число аккаунтов упрётся в ёмкость одного процесса.

README обновляется на каждом этапе: окружение (`PYROBOT_SECRET_KEY`, `PYROBOT_MAX_ENGINES`,
`PYROBOT_ROLE` и др.), модель аккаунтов и доступа, перенос и откат.

## 9. Риски

| Риск | Что делаем |
|---|---|
| Telegram ограничивает аккаунты с одного IP | плавный старт, лимиты кодов, нижние границы интервалов; сеть — ответственность хостера |
| Один event loop не тянет N движков | замер на этапе 1, ёмкость по умолчанию из замера, этап 3 |
| Потерян `PYROBOT_SECRET_KEY` | процесс со старой базой не стартует (`key_check`); осознанный сброс `PYROBOT_SECRET_KEY_RESET=1` — все аккаунты входят в Telegram заново, свои api_hash вводятся заново; README требует хранить ключ отдельно от бэкапов базы |
| Перенос сессии из файла не удался | файл остаётся, предупреждение `tg_session_import_failed`, вход заново |
| Рост базы при 50 аккаунтах | retention — политика сервера; индексы по `account_id` |
| Потеря соединения блокировок | продлений нет — движки хоста останавливаются по местному сроку; хост переподключается и, когда свои движки остановлены, берёт аккаунты заново (свою аренду — сразу, чужую — после `lease_expires_at`); этап 3 — подхватывают другие воркеры |
| Правка настроек теряется при старте движка или между процессами | настройки пишет либо держатель аренды, либо прямая запись без аренды; прямая запись держит строку аккаунта `FOR SHARE`, захват аренды её ждёт, движок читает настройки после захвата (раздел 4.4); пользовательский `PATCH` с устаревшей версией — 409 |
| Два движка одного аккаунта после обрыва соединения | аренда с TTL, продление по соединению блокировок, ограда вызовов Telegram и записей в базу по местному сроку, освобождение только своей эпохи; новый держатель ждёт `lease_expires_at` (раздел 4.2). Ограда Telegram — местная: пауза цикла событий дольше 3 с может её нарушить; монитор задержки цикла предупреждает |
| Потеря сообщения: kurigram сохраняет `pts` раньше, чем обновление дойдёт до журнала, и не догоняет пропущенное после переподключения | своя догонка kurigram выключена (`skip_updates=True`); проходы сверки истории от сохранённой отметки — при выходе в онлайн, переподключении, разрыве обновлений, ошибке в `handle_updates` и раз в 5 минут (раздел 4.3); разрыв больше 1000 сообщений — предупреждение `history_gap_truncated` |
| Перегрузка обновлениями | остановка приёма выше порога, новый клиент ниже порога, пропущенное — сверкой истории, без повторной догонки kurigram (раздел 4.2) |
