# Мультиаккаунт: дизайн

Дата: 30.09.2026. Статус: согласован в обсуждении, ждёт ревью спеки.

Документ описывает целевую архитектуру мультиаккаунта и три этапа её внедрения. Каждый этап
получает свой план реализации и заканчивается работающей системой.

## 1. Цель

Одна установка pyrobot обслуживает:

1. **Несколько аккаунтов одного человека.** Владелец держит несколько игровых аккаунтов и
   переключается между ними в админке.
2. **Несколько пользователей на одном сервере.** У каждого свой вход в админку и свои аккаунты;
   чужие аккаунты не видны.

Оба сценария — одна модель: пользователь → список аккаунтов, лимит аккаунтов задаёт владелец
сервера.

### 1.1. Требования (сказано владельцем)

- Одна общая установка на сервер: один бот, одна админка, у каждого пользователя свой логин.
- Пользователь может держать несколько аккаунтов в пределах лимита. Лимит задаёт владелец
  сервера, по умолчанию 1.
- Новые пользователи приходят по одноразовой ссылке-приглашению со сроком и лимитом аккаунтов;
  логин и пароль задают сами.
- Владелец сервера видит только служебное: кто заведён, работает ли бот, ошибки. Может завести,
  отключить и удалить. В чужую игру (журнал, состояние, настройки, команды) не заходит.
- Изоляция — как для посторонних людей: лимиты и защита от злоупотреблений.
- Масштаб: 10–50 аккаунтов на сервер, с перспективой больше 50.
- Telegram: по умолчанию общий api_id/api_hash сервера. Пользователь может указать для аккаунта
  свои api_id/api_hash. Прокси в приложении нет: сетевой доступ к Telegram обеспечивает тот, кто
  держит сервер.

### 1.2. Допущения

- Аккаунты в игре независимы. Движки не координируются, даже если аккаунты в одной команде.
- «Не заходит в чужую игру» — это права в приложении. У владельца сервера есть root и доступ к
  базе; приложение от этого не защищает. Шифрование сессий Telegram защищает от утечки дампа базы,
  а не от root.
- Нынешняя установка переезжает без потерь и без перелогина в Telegram.
- Отдельные установки на одном сервере (`COMPOSE_PROJECT_NAME`, README) продолжают работать.

### 1.3. Критерии успеха

- Владелец переключается между своими аккаунтами, и для каждого работает всё, что есть сейчас.
- Пользователь по приглашению заводит аккаунт, входит в Telegram и видит только своё; чужой
  аккаунт для него — 404.
- Падение, перезапуск или перелогин одного аккаунта не затрагивает остальные.
- 50 аккаунтов на одном сервере работают без деградации (задержка цикла p99 < 100 мс); дальше —
  добавлением воркеров.

### 1.4. Чего не делаем

- Координацию аккаунтов в игре.
- Прокси для Telegram.
- Лимиты CPU на отдельный аккаунт.
- Несколько экземпляров шлюза API.
- Воркеры на разных машинах (сессии в базе это позволяют, но это не цель и не тестируется).
- Открытую регистрацию, почту, 2FA для админки, биллинг.
- Смену ключа шифрования без перелогина (см. раздел 9).

## 2. Что есть сейчас

Схема базы уже частично готова: таблица `accounts` есть, во всех таблицах бота есть
`account_id` (FK на `accounts.id`), все уникальности включают `account_id`, чтение и запись в
хранилищах фильтруют по нему. Рантайм при этом рассчитан на один аккаунт:

| Что | Где | Почему мешает |
|---|---|---|
| Аккаунт задаётся из окружения `PYROBOT_ACCOUNT_ID` (по умолчанию 1) | `app/config.py:28`, `app/main.py:104-237` | один аккаунт на процесс; строк `accounts` никто не создаёт, `accounts.tg_user_id` не используется |
| Advisory-блокировка с постоянным ключом | `app/db/lock.py:8` | второй движок на той же базе не стартует, какой бы ни был аккаунт |
| Файл сессии Telegram `/data/pyrobot.session` | `app/engine/transport/kurigram.py:174-194` | два клиента делили бы файл; выход одного удалил бы сессию другого |
| `Container` держит один `facade` и один `DbReads` | `app/api/container.py:17-30` | ни в путях, ни в заголовках нет аккаунта |
| `admin_users`, `auth_sessions` глобальные | `app/db/models.py:35-54` | нет ролей и связи учётки с аккаунтами |
| Один `EventStream`, события без аккаунта | `app/main.py:106`, `app/engine/stream.py` | SSE одного аккаунта |
| Токен подтверждения подписывает сессию, но не аккаунт | `app/api/confirm.py:50-55` | подтверждение можно было бы повторить на другом аккаунте |
| Настройки `chats.`, `telegram.` требуют перезапуска процесса | `app/engine/settings.py:281-285` | перезапускались бы все аккаунты |
| `Supervisor._tasks` по фиксированным именам | `app/engine/supervisor.py:21-25` | имена задач двух движков совпали бы |
| Фронтенд: один `EventSource`, глобальные хранилища | `admin/src/lib/app.svelte.ts:11-21` | нет понятия аккаунта |

Модульного изменяемого состояния в коде движка нет (реестры и таблицы — только для чтения):
несколько движков в одном процессе упираются только в перечисленное выше.

## 3. Архитектура

```
                браузер
                   │  cookie-сессия, CSRF
            ┌──────▼──────────────────────────┐
            │ шлюз API (роль api или all)     │
            │  вход, учётки, приглашения,     │
            │  консоль, чтение из базы,       │
            │  EngineClient ──────────────┐   │
            └─────────────────────────────┼───┘
                                          │ этап 1–2: вызов в процессе
                                          │ этап 3: HTTP к воркеру
            ┌─────────────────────────────▼───┐
            │ хост движков (роль worker/all)  │
            │  EngineHost                     │
            │   ├ AccountRuntime #1 ── kurigram│
            │   ├ AccountRuntime #2 ── kurigram│
            │   └ …                           │
            └──────────────┬──────────────────┘
                           │
                       Postgres
         данные по account_id, сессии Telegram,
         advisory-блокировки (pyrobot, account_id)
```

- **`AccountRuntime`** — всё, что сейчас «один движок», для одного аккаунта.
- **`EngineHost`** — запускает, останавливает и перезапускает `AccountRuntime`, держит аренду
  аккаунтов.
- **`EngineClient`** — интерфейс шлюза к движку аккаунта. На этапах 1–2 это вызов внутри процесса,
  на этапе 3 — HTTP к воркеру. Маршруты API от реализации не зависят.

Этапы:

1. **Мультиаккаунт у владельца** (раздел 4): реестр аккаунтов, хост движков в процессе, сессии
   Telegram в базе, API и SSE с аккаунтом в пути, переключатель в админке, перенос установки.
2. **Пользователи и доступ** (раздел 5): роли, приглашения, лимиты, консоль владельца, своё
   приложение Telegram, границы опасных настроек, журнал действий.
3. **Воркеры** (раздел 6): вынос хоста движков в отдельные процессы, распределение аккаунтов,
   маршрутизация, масштабирование.

## 4. Этап 1. Мультиаккаунт у владельца

### 4.1. Модель данных

**`accounts`** — реестр аккаунтов:

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | int PK | есть |
| `owner_id` | int NULL, FK `admin_users.id` ON DELETE RESTRICT | чей аккаунт; NULL — аккаунт без владельца, никому не виден, при старте его получает первая учётка (раздел 4.7) |
| `name` | varchar(64) NOT NULL | имя в переключателе; UNIQUE (`owner_id`, `name`) |
| `status` | varchar(16) NOT NULL, CHECK in (`enabled`, `disabled`, `error`, `deleting`) | движок крутится только у `enabled` |
| `status_reason` | text NULL | почему `disabled` или `error` (например `crash_loop:gateway`) |
| `tg_user_id` | bigint NULL | есть; становится источником правды для привязки к Telegram; частичный UNIQUE WHERE NOT NULL |
| `created_at` | timestamptz | есть |
| `updated_at` | timestamptz NOT NULL | новое |

- Секция `telegram` (единственное поле `expected_user_id`) удаляется из `Settings`: привязка —
  `accounts.tg_user_id`. Уникальность не даёт привязать одного пользователя Telegram к двум
  аккаунтам; попытка входа под уже привязанным пользователем отклоняется, сессия закрывается,
  ошибка `tg_user_taken`.
- Новый аккаунт получает строку `settings` со значениями по умолчанию (`engine.mode = dry_run`).
- **Сессии Telegram** — две новые таблицы (раздел 4.3):
  - `tg_sessions`: `account_id` PK FK, `dc_id`, `api_id`, `test_mode`, `auth_key` bytea
    (зашифрован), `date`, `user_id`, `is_bot`, `server_address`, `port`, `updated_at`;
  - `tg_update_state`: PK (`account_id`, `id`), `pts`, `qts`, `date`, `seq`.
- Индексы, которых не хватает: `notifications (account_id, id)`,
  `settings_history (account_id, id)`.
- Внешние ключи `account_id` остаются без каскада: удаление аккаунта — фоновая чистка (раздел
  4.2), а FK страхуют от удаления строки `accounts` с оставшимися данными.

### 4.2. Хост движков

Нынешний `Runtime` (`app/main.py`) делится на две части:

- **Процесс:** база и пул, вход в админку и сессии, `Container` и HTTP, `EngineHost`, задачи
  процесса — очистка истёкших сессий админки и монитор задержки цикла.
- **`AccountRuntime(account_id)`:** хранилища с `account_id` (`DbSettingsStore`, `DbJournal`,
  `DbActionStore`, `DbPlannerStore`, `DbMetroRunStore`, `DbNotifier`, `DbRetention`),
  `EventStream`, `Pipeline`, транспорт kurigram, `ActionGateway`, `TgAuthManager`, `Reconciler`,
  `PlannerLoop`, `RobberyDefense`, `TeamForward`, `EngineFacade` и свой `Supervisor`. Задачи
  аккаунта: `pipeline`, `gateway`, `reconcile`, `reactions`, `team-forward`, `planner`,
  `retention`, `tg-probe`.

**`EngineHost`:**

- `start(account_id)`, `stop(account_id, reason)`, `restart(account_id)`, `get(account_id)`,
  `running()`.
- При старте процесса поднимает все `enabled` аккаунты с паузой `PYROBOT_ENGINE_START_GAP_S`
  (по умолчанию 3 с) между ними, чтобы не было залпа подключений к Telegram с одного IP.
- Ёмкость — `PYROBOT_MAX_ENGINES`, по умолчанию 20. Значение пересматривается по замеру (раздел
  4.8). Создание или включение аккаунта сверх ёмкости — 409 `capacity_reached`.
- **Аренда аккаунта** — `pg_try_advisory_lock(0x7079726F, account_id)` (двухключевая форма)
  вместо глобального ключа. Все блокировки хоста держит одно выделенное соединение; проверка
  каждые 10 с (как нынешний `lock-watch`). Потеря соединения — остановить все движки хоста,
  переподключиться, взять блокировки заново. Не взял блокировку аккаунта — движок не
  запускается, в статусе аккаунта причина `locked_elsewhere`.
- **Изоляция падений.** Сбой задачи перезапускается супервизором своего аккаунта, как сейчас.
  5 сбоев за 10 минут — хост останавливает `AccountRuntime`, ставит `status = error`,
  `status_reason = crash_loop:<задача>` и шлёт уведомление аккаунта `account_crash_loop` (error).
  Ошибка при старте аккаунта (невалидные настройки и т. п.) — тоже `error` с причиной.
  Пользователь возвращает аккаунт кнопкой «включить».
- **Перезапуск одного аккаунта.** `PATCH settings` возвращает `restart_required` (как сейчас),
  админка предлагает «перезапустить аккаунт» — `POST /accounts/{id}/engine/restart`. Процесс
  целиком больше не перезапускается.
- **Удаление.** `DELETE /accounts/{id}` ставит `deleting`, хост останавливает движок и закрывает
  сессию Telegram (`log_out`). Фоновая задача процесса удаляет строки аккаунта пачками по 5000
  (порядок — как в `DbRetention`, включая `tg_sessions`, `tg_update_state`, `settings`,
  `settings_history`, `state_snapshot`), затем строку `accounts`.
- **Логи.** ContextVar `account_id` задаётся для задач аккаунта (включая задачи клиента kurigram,
  созданные в его контексте); фильтр логирования добавляет `account=<id>` к каждой записи.
- **Пул соединений.** `PYROBOT_DB_POOL_SIZE` (по умолчанию 10) и `PYROBOT_DB_MAX_OVERFLOW`
  (по умолчанию 20) вместо умолчаний SQLAlchemy.
- **Очередь конвейера** становится ограниченной (`PIPELINE_QUEUE_MAX = 10000`); при
  переполнении — предупреждение аккаунта `pipeline_overflow` и ожидание места (обратное давление
  на транспорт), а не рост памяти.
- **`/readyz`** — готовность процесса: база доступна, соединение блокировок хоста живо. Готовность
  аккаунта (Telegram онлайн, не kill) — в статусе аккаунта. `deploy/remote-deploy.sh` ждёт
  `/readyz`, как сейчас.

### 4.3. Сессии Telegram

- **Хранилище.** `PgSessionStorage` реализует `pyrogram.storage.Storage` (kurigram 2.2.26,
  параметр `storage_engine` клиента):
  - поля сессии (`dc_id`, `api_id`, `test_mode`, `auth_key`, `date`, `user_id`, `is_bot`,
    `server_address`, `port`) — строка `tg_sessions`, запись при изменении;
  - состояние обновлений — `tg_update_state`, запись не чаще раза в секунду на аккаунт и при
    остановке. Отставание на секунду безопасно: после рестарта клиент перечитает несколько уже
    обработанных обновлений, а сообщения дедуплицируются уникальным ключом `messages`;
  - пиры и usernames — только в памяти; прогрев `get_dialogs(limit=200)` в `go_online` уже есть;
  - `delete()` удаляет строки аккаунта из обеих таблиц.
- Клиент: `Client(f"account-{id}", storage_engine=PgSessionStorage(...), api_id, api_hash, …)`;
  `workdir` не используется.
- **Шифрование.** Новая зависимость `cryptography`, AES-256-GCM. Ключ — `PYROBOT_SECRET_KEY`
  (32 байта, urlsafe base64), обязателен. Формат шифротекста: байт версии, 12 байт nonce,
  шифротекст с тегом. AAD — `pyrobot:<назначение>:<account_id>`, чтобы блоб нельзя было
  подставить другому аккаунту. Без ключа или с неверным ключом процесс не стартует и пишет в лог
  ошибку с командой генерации ключа.
- **Вход.** `TgAuthManager` у каждого аккаунта свой; попытка входа привязана к сессии админки
  внутри своего `AccountRuntime`. Первый успешный вход записывает `accounts.tg_user_id`
  (нарушение уникальности — `tg_user_taken`, выход из сессии).
- **Коды входа.** Не больше `PYROBOT_TG_CODES_PER_HOUR` (по умолчанию 10) запросов кода на хост
  и 3 в час на аккаунт; сверх — 429 `tg_code_rate_limited` с `Retry-After`.

### 4.4. API

Все пути, относящиеся к аккаунту, переезжают под `/api/v1/accounts/{account_id}/`:

| Было | Стало |
|---|---|
| `/engine/status`, `/engine/kill`, `unkill`, `pause`, `resume`, `reconciled` | `/accounts/{id}/engine/…` + новый `POST /accounts/{id}/engine/restart` |
| `/tg/status`, `/tg/login/start`, `code`, `password`, `/tg/logout` | `/accounts/{id}/tg/…` |
| `/state`, `/settings`, `/settings/history`, `/planner/outlook` | `/accounts/{id}/…` |
| `/journal`, `/decisions/{id}`, `/actions/{id}`, `/scenario-runs`, `/scenario-runs/{id}` | `/accounts/{id}/…` |
| `/commands/send`, `/commands/click`, `/scenarios/{name}/run` | `/accounts/{id}/…` |
| `/metrics`, `/metro/runs`, `/metro/runs/{id}`, `/unrecognized`, `/unrecognized/ack`, `/notifications`, `/notifications/read`, `/daily`, `/events` | `/accounts/{id}/…` |

Глобальные: `/auth/*`, `GET /scenarios` (каталог), `/healthz`, `/readyz`, и новые:

- `GET /accounts` — аккаунты текущей учётки: `id`, `name`, `status`, `status_reason`,
  `tg` (`user_id`, `online`), `mode`, `paused`, `killed`, `last_action_at`,
  `unread` (`warn`, `error`).
- `POST /accounts` `{name}` → 201; 409 `name_taken`, 409 `capacity_reached`.
- `PATCH /accounts/{id}` `{name?, enabled?}`; 409 `name_taken`, 409 `capacity_reached`.
- `DELETE /accounts/{id}` `{confirm_name}` → 202; несовпадение имени — 422
  `confirm_name_mismatch`.
- `GET /host/status` — здоровье процесса и хоста: блокировки, задачи процесса, задержка цикла,
  запущенные движки. Поля здоровья процесса уходят из статуса аккаунта.

Правила:

- **Доступ** — одна зависимость `account_scope`: загрузить аккаунт, проверить
  `owner_id == текущая учётка`; чужой и несуществующий — одинаково 404 `account not found`.
  Отдаёт `DbReads(db, account_id)` и `EngineClient` аккаунта (или `None`, если движок не
  запущен).
- Движок не запущен (аккаунт `disabled`, `error`, `deleting`) — «живые» пути отвечают 503
  `engine not running`; чтение из базы работает.
- **Токен подтверждения** подписывает и `account_id`.
- Старых путей нет: API и админка выкатываются вместе. `tools/login.py` получает `--account`.
- `openapi.json` и `schema.d.ts` пересобираются; CI проверяет их, как сейчас.

### 4.5. События (SSE)

- `GET /accounts/{id}/events` — поток `EventStream` своего `AccountRuntime`; формат событий,
  `Last-Event-ID` и причины `reset` не меняются. Перепроверка сессии каждые 15 с — как сейчас.
- Движок не запущен — 503; клиент переподключается с нарастающей паузой и показывает «движок не
  запущен».
- Общего потока нет: список аккаунтов со статусами админка перечитывает раз в 30 с и при
  возвращении на вкладку.

### 4.6. Админка

- **Маршруты.** Все нынешние экраны — под `/a/[account]/…` (главная, журнал, управление, метро,
  итоги, метрики, настройки, уведомления, Telegram). Глобальные: `/login`, `/password`,
  `/accounts`. `/` ведёт в последний открытый аккаунт (`localStorage` `pyrobot.account`) или на
  `/accounts`, если аккаунтов нет. Старые ссылки (`/journal` и т. п.) перенаправляются в
  `/a/<последний>/…`. Сервер отдаёт `index.html` для путей без расширения, как сейчас.
- **Переключатель.** На ПК — вверху бокового меню: имя, точка статуса, счётчик непрочитанных
  warn/error. На телефоне — плашка с именем вверху экрана и список аккаунтов в «Ещё».
- **Контекст аккаунта.** `startApp()` делится на общую часть (сессия, тема, тикер) и
  `startAccount(id)`: клиент API аккаунта, SSE, статус движка, персонаж, непрочитанные.
  Переключение закрывает SSE и пересоздаёт контекст; постраничные хранилища пересоздаются вместе
  с маршрутом. Все потребители уже перечитывают данные по `reset`.
- **Клиент API аккаунта** сам подставляет `account_id` в пути `/accounts/{account_id}/…`; типы —
  из `openapi.json`.
- **Экран `/accounts`.** Имя, пользователь Telegram, статус и причина, `dry_run`/`live`, пауза и
  kill, Telegram онлайн, последнее действие, warn/error; создание, переименование,
  включение/выключение, удаление с вводом имени.
- **Новый аккаунт:** создать → экран Telegram, вход → настройки (`dry_run`) → включить `live`
  прежним путём.

### 4.7. Перенос нынешней установки

Миграция Alembic:

1. Колонки `accounts` из 4.1: `owner_id` — id первой (по `id`) строки `admin_users` или NULL,
   если учёток ещё нет; `name = 'Основной'`, `status = 'enabled'`. При каждом старте, после
   `ensure_admin`, аккаунты с `owner_id` NULL получают первую учётку (на этапе 2 — первого
   `owner`). Так переживается и новая установка без учётки, и учётка, удалённая по старому совету
   README.
2. `tg_user_id` ← `settings.data->'telegram'->>'expected_user_id'`; ключ `telegram` удаляется
   из JSON настроек.
3. Таблицы `tg_sessions`, `tg_update_state`, индексы.

При старте:

- Если у аккаунта 1 нет строки `tg_sessions`, а файл `<data_dir>/pyrobot.session` есть,
  сессия и состояние обновлений читаются из файла (`SQLiteStorage` kurigram), записываются в
  `PgSessionStorage`, файл переименовывается в `pyrobot.session.migrated`. Ошибка переноса —
  предупреждение аккаунта `tg_session_import_failed`, файл остаётся, аккаунт требует входа.
- `PYROBOT_SECRET_KEY` обязателен; `deploy/render-env.sh` и `.env.example` получают его.
- `PYROBOT_ACCOUNT_ID` больше не читается; если задан — предупреждение в лог.

Откат: откат миграции (возвращает `telegram.expected_user_id` в настройки) и переименование
`pyrobot.session.migrated` обратно.

### 4.8. Тесты этапа 1

- `EngineHost`: запуск, остановка, перезапуск одного аккаунта не трогает остальные; два хоста
  на одной базе не запускают один аккаунт; 5 сбоев за 10 минут — `error` и уведомление.
- `PgSessionStorage`: общий набор проверок интерфейса `Storage`, который проходит и
  `SQLiteStorage`; шифрование туда и обратно, чужой AAD, отсутствующий и неверный ключ; импорт
  из файла.
- Матрица доступа: список путей аккаунта собирается из приложения автоматически; для каждого
  чужой аккаунт — 404.
- Токен подтверждения не принимается на другом аккаунте.
- Удаление аккаунта: остановка, выход из Telegram, чистка всех таблиц, строки `accounts` нет.
- Миграция: upgrade/downgrade на данных, похожих на прод, включая перенос `expected_user_id`.
- Админка: переключатель, префиксы маршрутов, перенаправление старых ссылок, пересоздание
  контекста при переключении, экран `/accounts`.
- **Замер** (`tools/bench_engines.py`, не в CI): N движков на фейковом транспорте
  воспроизводят записанный трафик фикстур; память, CPU, задержка цикла p50/p99 для N = 5, 10,
  20, 40. По результату выставляется `PYROBOT_MAX_ENGINES` по умолчанию и решается, когда нужен
  этап 3; результат записывается в README.

### 4.9. Готово, когда

- Нынешняя установка обновилась без перелогина в Telegram, всё работает на аккаунте 1.
- Владелец создал второй аккаунт, вошёл в Telegram, переключается между аккаунтами.
- Перезапуск, падение и выход из Telegram одного аккаунта не трогают другой.
- Замер выполнен, ёмкость по умолчанию выставлена.

## 5. Этап 2. Пользователи и доступ

### 5.1. Учётки и роли

`admin_users` переименовывается в `users` (FK `auth_sessions`, `accounts.owner_id` — вслед):

| Колонка | Тип | Смысл |
|---|---|---|
| `role` | varchar(8) NOT NULL, CHECK in (`owner`, `user`), по умолчанию `user` | владелец сервера или пользователь |
| `max_accounts` | int NOT NULL, по умолчанию 1 | лимит аккаунтов |
| `disabled_at`, `disabled_reason` | timestamptz / text NULL | отключён владельцем |
| `invited_by` | int NULL, FK `users.id` ON DELETE SET NULL | кто пригласил |
| `last_login_at` | timestamptz NULL | последний вход |

- Нынешний админ становится `owner` с `max_accounts` = число его аккаунтов или 10, что больше.
- Второго владельца назначает только `python -m app.tools.users promote <login>`; экрана нет.
  Последнего владельца нельзя отключить, удалить или понизить — 409 `last_owner`.
- `SessionContext` получает `user_id` и `role`; `resolve` отклоняет сессию отключённой учётки
  (401). Вход обновляет `last_login_at`. `/auth/me` отдаёт `role`.
- **Правило доступа без исключений:** пути `/accounts/{id}/…` открыты только хозяину аккаунта;
  роль `owner` его не обходит.
- Отключение учётки: закрыть её сессии, остановить движки её аккаунтов (`status = disabled`,
  `status_reason = user_disabled`); включение возвращает прежний статус аккаунтов не
  автоматически — пользователь включает аккаунты сам.

### 5.2. Приглашения и сброс пароля

Таблица `invites`:

| Колонка | Смысл |
|---|---|
| `id` | PK |
| `token_hash` | bytea UNIQUE — sha256 токена; сам токен (32 байта, urlsafe) показывается один раз |
| `kind` | `register` или `reset` |
| `created_by` | FK `users.id` |
| `created_at`, `expires_at` | срок: по умолчанию 72 ч, не больше 30 дней |
| `max_accounts` | лимит новой учётки (для `register`) |
| `target_user_id` | чей пароль сбрасывается (для `reset`) |
| `note` | varchar(128), «кому» |
| `used_at`, `used_by`, `revoked_at` | использование и отзыв |

- Ссылка: `/invite/<токен>`.
- `GET /api/v1/invites/{token}` (без входа) → `kind`, `expires_at`, для `reset` — логин.
  Неизвестный токен — 404 `invite_not_found`; использованный, отозванный, истёкший — 410
  `invite_gone`.
- `POST /api/v1/invites/{token}/accept`:
  - `register` `{login, password}` → учётка `user` с `max_accounts` из приглашения и
    `invited_by`, сразу открывается сессия; 409 `login_taken`;
  - `reset` `{password}` → новый пароль, все сессии учётки закрываются, открывается новая.
  - Пароль — от 12 символов, как сейчас. Ограничение попыток — тем же лимитером по IP, что и
    вход.
- Советы README про `DELETE FROM admin_users` заменяются на сброс по ссылке и
  `python -m app.tools.users reset <login>` (печатает ссылку сброса) на случай, если владелец
  потерял доступ сам.

### 5.3. Консоль владельца

Экран `/admin` с вкладками; API `/api/v1/admin/*`, доступен только `owner`, остальным — 404.
Ответы консоли содержат только служебные поля: схема ответа не включает состояние персонажа,
журнал, настройки, команды, метрики, метро и тексты уведомлений аккаунтов.

- **Пользователи** (`GET /admin/users`, `PATCH /admin/users/{id}`, `DELETE /admin/users/{id}`
  с `confirm_login`, `POST /admin/users/{id}/reset`): логин, роль, когда заведён, последний
  вход, аккаунтов из лимита, отключён ли и почему; изменить лимит, отключить или включить,
  удалить вместе с аккаунтами, выдать ссылку сброса.
- **Аккаунты** (`GET /admin/accounts`, `PATCH /admin/accounts/{id}`,
  `POST /admin/accounts/{id}/restart`, `DELETE /admin/accounts/{id}` с `confirm_name`): чей,
  имя, статус и причина, заблокирован ли владельцем, работает ли движок, онлайн ли Telegram,
  перезапуски за 24 ч, код последней ошибки и когда, нагрузка (сообщений и действий за час),
  строк в базе по основным таблицам. Действия: заблокировать с причиной, разблокировать,
  перезапустить движок, удалить.
- **Приглашения** (`GET/POST /admin/invites`, `DELETE /admin/invites/{id}`): создать
  (`register` с лимитом и сроком), список неиспользованных, отозвать.
- **Сервер** (`GET/PATCH /admin/server-settings`): раздел 5.4.
- **Журнал действий** (`GET /admin/audit`): раздел 5.7.
- **Уведомления сервера** (`GET /admin/notifications`, `POST /admin/notifications/read`).
- `GET /host/status` доступен только `owner`.

Блокировка аккаунта владельцем — колонки `accounts.blocked` (bool) и `accounts.blocked_reason`:
движок останавливается, пользователь видит причину в статусе, получает уведомление аккаунта
`account_blocked` и не может включить аккаунт (403 `blocked_by_owner`) до разблокировки.

### 5.4. Настройки сервера

Таблица `server_settings`: одна строка (`id = 1`), `version`, `data` JSONB; модель
`ServerSettings`, правка с оптимистической версией, история — в журнале действий.

| Секция | Поля (по умолчанию) |
|---|---|
| `retention` | переезжает из `Settings.retention` аккаунта: `messages_days` 90, `decisions_days` 30, `metrics_days` 365, `ledger_days` 31; плюс `audit_days` 365 |
| `invites` | `default_ttl_h` 72, `default_max_accounts` 1 |
| `limits` | `max_accounts_total` — `PYROBOT_MAX_ENGINES` (этап 3 — сумма ёмкостей воркеров), `sse_per_user` 5, `tg_codes_per_hour` 10, `tg_codes_per_account_hour` 3 |
| `engine_bounds` | `min_request_interval_s_min` 1.6, `antiflood_pause_s_min` 10, `antiflood_retry_max_max` 2, `action_ttl_s_max` 600 |

Retention выполняется по-прежнему по каждому аккаунту (задача аккаунта), но по политике сервера.

### 5.5. Лимиты и защита от злоупотреблений

- `POST /accounts`: аккаунтов учётки (кроме `deleting`) < `max_accounts`, иначе 409
  `limit_reached`; всего на сервере < `max_accounts_total`, иначе 409 `server_full`.
- **Границы настроек движка.** `PATCH /accounts/{id}/settings` за пределами `engine_bounds` — 422
  `setting_out_of_bounds` с путём и границей. `GET settings` отдаёт границы, админка показывает
  их у полей. Границы действуют для всех, включая владельца сервера. При ужесточении границ
  существующие значения за пределами приводятся к границе при следующем старте движка, с
  записью в историю настроек (`changed_by = "system"`).
- Запрещённые классы команд (`forbidden`, `donate`) — 403, как сейчас.
- Коды входа в Telegram — лимиты из `limits`.
- SSE — не больше `sse_per_user` одновременных потоков на учётку; сверх — 429.

### 5.6. Своё приложение Telegram

- Колонки `accounts.tg_api_id` (int NULL) и `accounts.tg_api_hash` (bytea NULL, зашифрован
  ключом сервера, AAD `pyrobot:tg_api_hash:<account_id>`).
- `PUT /accounts/{id}/tg/app` `{api_id, api_hash}` и `DELETE /accounts/{id}/tg/app` — только
  когда аккаунт вышел из Telegram, иначе 409 `tg_logged_in`. api_id — положительное число,
  api_hash — 32 шестнадцатеричных символа; иначе 422.
- `GET /accounts/{id}/tg/status` отдаёт `app`: `server` или `{api_id}`; hash не отдаётся никогда.
- Не задано — клиент использует `PYROBOT_TG_API_ID`/`PYROBOT_TG_API_HASH`.
- Экран Telegram получает блок «Своё приложение Telegram».

### 5.7. Журнал действий и уведомления сервера

- Таблица `audit_log`: `id`, `at`, `actor_user_id` (FK ON DELETE SET NULL), `actor_login`
  (копия), `action`, `target_type`, `target_id`, `details` JSONB. Пишутся: создание и отзыв
  приглашений, регистрация, сброс пароля, лимиты, отключение/включение учёток, блокировка и
  удаление аккаунтов, правка настроек сервера, назначение владельца. Срок хранения —
  `retention.audit_days`.
- Уведомления сервера — в таблице `notifications` с `account_id` NULL (колонка становится
  nullable), видны только владельцам: аккаунт ушёл в `error`, упёрлись в лимит кодов Telegram,
  использовано приглашение, потеряно соединение блокировок хоста.

### 5.8. Перенос

Миграция: переименование таблицы, новые колонки и таблицы; нынешний админ — `owner`;
`server_settings.retention` ← `retention` настроек аккаунта 1, ключ `retention` удаляется из
настроек всех аккаунтов; `notifications.account_id` nullable.

### 5.9. Тесты этапа 2

- Матрица доступа: для каждого пути аккаунта чужой аккаунт — 404 и для `user`, и для `owner`;
  `/admin/*` для `user` — 404.
- Ответы консоли сверяются со схемой: запрещённых полей нет.
- Приглашения: срок, повтор (410), отзыв, `login_taken`, сброс закрывает сессии, лимитер.
- Отключённая учётка: сессии закрыты, вход — 401, движки остановлены.
- Лимиты `limit_reached`, `server_full`; границы `setting_out_of_bounds`; `last_owner`;
  `blocked_by_owner`.
- Своё приложение Telegram: только при выходе, hash не утекает ни в одном ответе.
- Журнал действий пишется для каждого действия из 5.7.
- Админка: страница приглашения (регистрация и сброс), консоль.

### 5.10. Готово, когда

- Приглашённый пользователь зарегистрировался, завёл аккаунт, вошёл в Telegram и видит только
  своё.
- Владелец видит в консоли его учётку и аккаунт без игровых данных, может заблокировать,
  перезапустить, удалить.
- Лимиты и границы настроек работают.

## 6. Этап 3. Воркеры

### 6.1. Роли процессов

`PYROBOT_ROLE`:

- `all` (по умолчанию) — шлюз и хост движков в одном процессе; поведение этапов 1–2.
- `api` — шлюз: HTTP, админка, вход, учётки, консоль, чтение из базы, фоновая чистка удаляемых
  аккаунтов; `EngineClient` — HTTP к воркеру.
- `worker` — `EngineHost` и внутренний HTTP на `PYROBOT_INTERNAL_PORT` (8081), наружу не
  публикуется.

Шлюз — один экземпляр (лимитер входа в его памяти). Секрет токенов подтверждения выводится из
`PYROBOT_SECRET_KEY` (HKDF, назначение `confirm`), а не генерируется при старте процесса.

### 6.2. Распределение аккаунтов

- Таблица `workers`: `id` (uuid), `url` (внутренний адрес), `capacity`, `engines`,
  `loop_lag_ms`, `rss_mb`, `started_at`, `heartbeat_at`, `draining`. Пульс — каждые 10 с;
  воркер без пульса 30 с считается мёртвым.
- Таблица `account_hosts`: `account_id` PK, `worker_id` FK ON DELETE CASCADE, `since` —
  подсказка для маршрутизации. Истина — advisory-блокировка `(0x7079726F, account_id)`:
  умер воркер — оборвалось соединение — блокировки свободны.
- Воркер слушает `LISTEN pyrobot_accounts` (payload: `account_id`, операция — `enable`,
  `disable`, `restart`, `delete`, `create`) и раз в 30 с сверяет список сам.
- Воркер берёт свободный `enabled` аккаунт, если `engines < capacity` и его `engines` не больше
  минимума среди живых воркеров без `draining`. Порядок — по возрастанию `account_id`.
- Автоматического перераспределения нет. Перераспределение — кнопка «перераспределить» в
  консоли (воркеры с загрузкой выше среднего отдают лишние аккаунты по одному) и остановка
  воркера. При остановке воркер ставит `draining`, останавливает движки, отпускает блокировки;
  остальные подхватывают. Простой аккаунта при выкатке — время остановки и старта движка.
- Управление аккаунтом из шлюза (включить, выключить, перезапустить, удалить): шлюз меняет
  `accounts.status` и шлёт `NOTIFY pyrobot_accounts`; воркер, держащий аккаунт, выполняет.
- Чистка удаляемого аккаунта выполняется в шлюзе, когда блокировка аккаунта свободна (статус
  `deleting` не даёт воркерам его взять).

### 6.3. Внутренний API

- Пути `/internal/accounts/{id}/…` повторяют методы `EngineClient` — ровно те методы
  `EngineFacade`, которыми пользуются маршруты этапа 1: статус, kill/unkill/pause/resume/
  reconciled/restart, вход и выход в Telegram, состояние, чтение и правка настроек, план,
  команды, запуск сценария, события.
- Авторизация — `Authorization: Bearer ${PYROBOT_INTERNAL_TOKEN}`; кто действует — заголовки
  `X-Pyrobot-User-Id`, `X-Pyrobot-Login`, `X-Pyrobot-Session` (для журнала действий, токенов
  подтверждения и привязки попытки входа в Telegram).
- Команды и сценарии ждут результат до 30 с, как сейчас; таймаут шлюза — 35 с.
- SSE: шлюз проксирует поток воркера байт в байт и передаёт `Last-Event-ID`.
- Маршрутизация: шлюз берёт воркер из `account_hosts` (кэш 5 с); ответ воркера 404
  `not_hosted` или ошибка соединения — обновить кэш и повторить один раз; нет воркера — 503
  `engine not running`.
- Попытка входа в Telegram живёт в памяти воркера. Если аккаунт переехал посреди входа,
  попытка теряется и вход начинается заново.

### 6.4. Настройки между процессами

- Настройки запущенного аккаунта правит воркер, который его держит (кэш и подписчики там).
  Аккаунт никем не поднят — шлюз пишет в базу сам.
- Любая запись настроек шлёт `NOTIFY pyrobot_settings` с `account_id`; воркер, держащий
  аккаунт, перечитывает настройки, если версия в базе новее.
- `DbSettingsStore.update` при конфликте версий перечитывает настройки и повторяет запись один
  раз; повторный конфликт — 409 `settings_conflict`.

### 6.5. Ресурсы, наблюдаемость, деплой

- Пул воркера: `2 + ceil(engines/4)`, переполнение — столько же, плюс одно соединение
  блокировок; пул шлюза — 10. Три воркера и шлюз — около 60 соединений при стандартных 100 у
  Postgres. PgBouncer не используется: advisory-блокировкам уровня сессии нужен сессионный
  режим.
- `GET /host/status` в шлюзе: воркеры (пульс, движки, задержка цикла, память), кто какие
  аккаунты держит, включённые аккаунты, которые никто не держит.
- Логи: `account=<id> worker=<id>` в каждой записи.
- `compose.yml` — прежний один сервис в роли `all`. `compose.scale.yml` добавляет `api` (порт
  наружу) и `worker` (`--scale worker=N`, `mem_limit` на воркер из замера этапа 1), общий
  `PYROBOT_INTERNAL_TOKEN`.
- Цель: 50 аккаунтов на 2–3 воркерах, задержка цикла p99 < 100 мс, память в пределах лимитов.

### 6.6. Тесты этапа 3

Интеграционные тесты в CI (сервис Postgres уже есть), два процесса `worker` на фейковом
транспорте:

- распределение аккаунтов по правилу 6.2;
- убитый воркер: аккаунты подхватывает второй;
- шлюз: повтор запроса при `not_hosted`, 503 без воркера;
- SSE через шлюз с `Last-Event-ID`;
- настройки: правка через шлюз у выключенного аккаунта видна воркеру после включения; конфликт
  версий разрешается перечитыванием;
- остановка воркера отдаёт аккаунты.

### 6.7. Готово, когда

- Установка с `compose.scale.yml` и тремя воркерами держит 50 аккаунтов на фейковом транспорте
  с задержкой цикла p99 < 100 мс.
- Остановка любого воркера — его аккаунты поднимаются на остальных.
- Установка с одним сервисом `all` работает как на этапе 2.

## 7. Безопасность

- **Изоляция.** Пути аккаунта — только хозяину; чужой аккаунт — 404 для всех ролей. Консоль
  владельца отдаёт только служебные поля. Токены подтверждения подписывают аккаунт.
- **Секреты.** `PYROBOT_SECRET_KEY` шифрует `auth_key` сессий и `tg_api_hash`; AAD привязывает
  блоб к аккаунту. `PYROBOT_INTERNAL_TOKEN` закрывает внутренний API воркеров. Токены
  приглашений хранятся хэшами.
- **Вход и сессии** — как сейчас: argon2, cookie HttpOnly/SameSite=Strict, CSRF, лимитер;
  плюс проверка отключённой учётки.
- **Общий IP.** Плавный старт движков, лимиты кодов входа, нижние границы интервалов движка.
- **Журнал действий** владельца сервера виден владельцам.
- **Ограничение.** Root на сервере и доступ к базе с ключом дают всё; это не цель защиты.

## 8. Выкатка

1. Этап 1 → выкатка → проверка на аккаунте 1 → второй аккаунт владельца.
2. Этап 2 → выкатка → первое приглашение.
3. Этап 3 — когда замер или число аккаунтов упрётся в ёмкость одного процесса.

README обновляется на каждом этапе: окружение (`PYROBOT_SECRET_KEY`, `PYROBOT_MAX_ENGINES`,
`PYROBOT_ROLE` и др.), модель аккаунтов и доступа, перенос и откат.

## 9. Риски

| Риск | Что делаем |
|---|---|
| Telegram ограничивает аккаунты с одного IP | плавный старт, лимиты кодов, нижние границы интервалов; сеть — ответственность хостера |
| Один event loop не тянет N движков | замер на этапе 1, ёмкость по умолчанию из замера, этап 3 |
| Потерян `PYROBOT_SECRET_KEY` | сессии не расшифровать — все аккаунты входят в Telegram заново, свои api_hash вводятся заново; README требует хранить ключ отдельно от бэкапов базы |
| Перенос сессии из файла не удался | файл остаётся, предупреждение `tg_session_import_failed`, вход заново |
| Рост базы при 50 аккаунтах | retention — политика сервера; индексы по `account_id` |
| Потеря соединения блокировок | хост останавливает движки и берёт блокировки заново; этап 3 — подхватывают другие воркеры |
| Конфликт настроек между процессами | `NOTIFY` и перечитывание, повтор записи один раз |
