# pyrobot

Userbot для автоматической игры в StartupWars (@StartupWarsBot). Боты в игре официально разрешены.

Один процесс: kurigram (MTProto) + движок + FastAPI в одном asyncio-цикле, Postgres.
Админка (SvelteKit, каталог `admin/`) — SPA поверх `/api/v1` этого сервиса, собранную статику отдаёт
тот же FastAPI с того же домена (см. «Админка»).

## Как начать пользоваться ботом

Раздел для владельца бота, не для разработчика: как включить, проверить и настроить прод. Админки
пока нет, всё управление — через HTTP API.

1. **Что это и где работает.** Бот играет сам на основном аккаунте в StartupWars; прод — контейнер
   на apps, API снаружи — `https://sw.fenicu.com/api/v1/…`. Пароль первого админа задаётся секретом
   `PYROBOT_ADMIN_PASSWORD` при первом выкате (см. «Первый вход»); сами значения секретов в README
   не публикуются.
2. **Вход в API.** `POST /api/v1/auth/login {"login", "password"}` отдаёт `{login, csrf_token}` и
   ставит cookie сессии; изменяющие запросы (`PATCH`/`POST`, кроме входа) требуют заголовок
   `X-CSRF-Token` с этим токеном.

   ```bash
   curl -c cookies.txt -s https://sw.fenicu.com/api/v1/auth/login \
     -H 'Content-Type: application/json' \
     -d '{"login": "admin", "password": "..."}'
   ```

   Дальше запросы идут с тем же `cookies.txt` (`curl -b cookies.txt`) и токеном из ответа в
   заголовке `X-CSRF-Token`.
3. **Первый вход в Telegram** — `uv run python tools/login.py https://sw.fenicu.com`. Скрипт
   интерактивно спрашивает логин и пароль админа (те же, что задал `PYROBOT_ADMIN_PASSWORD` при
   старте), затем, если Telegram ещё не в сети, — телефон, код из Telegram и, если включена 2FA,
   пароль. Ничего из введённого не печатается и на диск не сохраняется.
4. **Проверка, что всё работает:** `GET /readyz` (без авторизации, доступен только изнутри сети —
   снаружи Caddy отдаёт на него 404), `GET /api/v1/engine/status` (`mode`, `paused`, `killed`,
   `tg`), `GET /api/v1/state` (текущий снимок состояния персонажа).
5. **Режимы и управление** (`POST`, CSRF):
   - `dry_run`/`live` — `PATCH /api/v1/settings` с `version` и `changes: {"engine": {"mode":
     "live"}}`; переход в `live` дополнительно требует `confirm_live: true`, иначе 422;
   - пауза и возобновление — `POST /api/v1/engine/pause`, `POST /api/v1/engine/resume`;
   - аварийная остановка — `POST /api/v1/engine/kill {"reason"}`, снять — `POST
     /api/v1/engine/unkill`.
6. **Главные настройки** — меняются тем же `PATCH /api/v1/settings` (`version` + `changes`,
   см. «Управление настройками»):

   | Путь | Что значит | По умолчанию |
   |---|---|---|
   | `strategy.focus` | основные дела, которые планировщик чередует первыми и делит 🔥 поровну | `harvest`, `dconv` (добыча и переработка) |
   | `strategy.deeds` | дела, из которых планировщик выбирает запасное по оценке | `harvest`, `job`, `learn`, `dconv`, `walk` |
   | `daily.personal_order` | порядок личных ежедневных заданий (hard) от самого дешёвого для бота | `convDets`, `robPro`, `jobMoney`, `materials`, `learnKnows`, `walkMoney`, `confKnows` |
   | `lottery.tickets.{money,knowledge,raw,details}` | сколько билетов брать за тираж по валютам (число или `"max"`) | `"max"` у всех |
   | `lottery.keep.{money,knowledge,raw,details}` | сколько ресурса не тратить на билеты | `0` у всех |
   | `features.<механика>` | включение/выключение механики (`lottery`, `robbery_defense`, `daily_tasks`, `casino`, …) | см. `app/engine/settings.py: FeaturesSection` |
   | `battle.target`, `battle.overrides.<час>` | цель взлома/защиты по умолчанию и по часу битвы (0–23 МСК) | 📯Pied Piper, без переопределений |
   | `sleep.duration_h`, `sleep.lead_min`, `sleep.hotel_if_cash_after_reserve_ge` | длительность сна, за сколько минут до дедлайна ложиться, порог денег для отеля | 7 ч, 120, цена отеля с экрана |
   | `stocks.cash_floor`, `stocks.min_dump`, `stocks.sell_cap_margin`, `stocks.dump_lead_min` | слив налички в акции перед битвой | 150, 200, 5, 5 |

   Пример:

   ```bash
   curl -b cookies.txt -s -X PATCH https://sw.fenicu.com/api/v1/settings \
     -H 'Content-Type: application/json' -H 'X-CSRF-Token: <токен из /auth/login>' \
     -d '{"version": 3, "changes": {"lottery": {"tickets": {"money": 5}}}}'
   ```

   `version` — версия настроек, увиденная перед изменением (`GET /api/v1/settings`); устаревшая —
   409.
7. **Что смотреть:** журнал `GET /api/v1/journal`, решения `GET /api/v1/decisions/{id}`,
   уведомления `GET /api/v1/notifications`, нераспознанное `GET /api/v1/unrecognized`, поток
   `GET /api/v1/events` (SSE).
8. **Ручные действия:**
   - `POST /api/v1/commands/send` (текст) / `POST /api/v1/commands/click` (кнопка) — с
     идемпотентным ключом; `risky`-команды требуют подтверждения (`confirm_token`), `forbidden` и
     `donate` — никогда;
   - ручной запуск сценария — `POST /api/v1/scenarios/{name}/run`, каталог сценариев —
     `GET /api/v1/scenarios`.
9. **Новая версия** — тег `vX.Y.Z` → CI выкатывает сам (см. «CI/CD»); после выката, если появились
   новые флаги, — `PATCH /api/v1/settings`.

## Конфигурация

Все параметры загружаются через переменные окружения с префиксом `PYROBOT_`. Пример: `cp .env.example .env && vi .env`.

| Переменная | Назначение |
|---|---|
| `PYROBOT_DATABASE_URL` | Connection string к PostgreSQL (по умолчанию localhost:55432). |
| `PYROBOT_DATA_DIR` | Путь к директории для хранения игровых данных. |
| `PYROBOT_TG_API_ID` | Telegram API ID (из my.telegram.org). При `PYROBOT_TRANSPORT=kurigram` обязателен и больше 0, иначе процесс не стартует (ошибка валидации конфигурации). |
| `PYROBOT_TG_API_HASH` | Telegram API hash (из my.telegram.org). При `PYROBOT_TRANSPORT=kurigram` обязателен и не пуст. |
| `PYROBOT_ADMIN_LOGIN` | Логин для доступа в админку. |
| `PYROBOT_ADMIN_PASSWORD` | Пароль для админки (если не задан, доступ отключён). |
| `PYROBOT_COOKIE_SECURE` | Использовать флаг Secure для cookies (true в боевой, false в локальной разработке). |
| `PYROBOT_TRANSPORT` | Транспорт Telegram: `kurigram` (боевой MTProto) или `fake` (для тестов). |
| `PYROBOT_LOG_LEVEL` | Уровень логирования (DEBUG, INFO, WARNING, ERROR). Логгер `pyrogram` никогда не опускается ниже INFO: в DEBUG kurigram печатает код входа в Telegram. |
| `PYROBOT_HTTP_HOST` | IP для привязки HTTP сервера. |
| `PYROBOT_HTTP_PORT` | Порт для HTTP API. |
| `PYROBOT_FORWARDED_ALLOW_IPS` | Адреса обратного прокси через запятую, чьим `X-Forwarded-For`/`X-Forwarded-Proto` доверяет uvicorn (`--proxy-headers`), по умолчанию `127.0.0.1`; в боевой — Caddy `10.10.40.3`. Без этого лимитер входа видит всех клиентов одним адресом прокси, а заголовок от чужого адреса игнорируется. |
| `PYROBOT_ACCOUNT_ID` | Внутренний `accounts.id` в базе pyrobot (по умолчанию 1), не ID игрока в игре. |
| `PYROBOT_ADMIN_DIR` | Каталог собранной админки (`admin/build`), её отдаёт тот же FastAPI (по умолчанию `/app/admin` — так в образе). Нет каталога или `index.html` в нём — `/` отвечает 404 (разработка, тесты). |
| `PYROBOT_PLANNER` | Планировщик принимает решения сам (по умолчанию `true`); `false` — движок только принимает сообщения и выполняет ручные команды и ручные запуски сценариев (цикл планировщика работает без собственных решений). |

## База данных

Postgres для разработки и тестов поднимается через `compose.dev.yml`:

```bash
docker compose -f compose.dev.yml up -d
```

Контейнер слушает `127.0.0.1:55432` и создаёт три базы: `pyrobot` (основная база для разработки),
`pyrobot_test` (юнит- и интеграционные тесты, фикстуры `db`/`clean_db`) и `pyrobot_migtest`
(тест миграций `tests/db/test_migrations.py`). Список тестовых баз задаётся в
`docker/initdb/10-test-dbs.sql`, который накатывается только при первой инициализации volume.

Схема версионируется через Alembic (`app/db/migrations`). Применить миграции:

```bash
uv run alembic upgrade head
```

Новую миграцию генерировать через `uv run alembic revision --autogenerate -m "..."`. Alembic читает
только `PYROBOT_DATABASE_URL` (`DbConfig`), Telegram-параметры для миграций не нужны.

Миграция `0002` добавляет таблицы `metrics` (временной ряд ключевых полей состояния — `money`,
`level`, `stamina` и т.д., строка пишется только при изменении значения, момент — `msg.date`) и
`unrecognized` (нераспознанные сообщения игрового чата, `first_line` для быстрого просмотра, флаг
`acked` для разбора). Обе таблицы пишутся в той же транзакции, что и запись сообщения в журнал
(`JournalStore.append`), поэтому не могут разойтись с журналом.

Миграция `0004` добавляет `decisions` (журнал решений планировщика: момент, `act`/`wait`, сценарий и
параметры, причина, `until` ожидания, кандидаты с оценками и причинами отказа) и `scenario_runs`
(запуски сценариев: решение, параметры, начало и конец, итог и его причина).

Миграция `0005` добавляет `metro_runs` (забеги метро, `DbMetroRunStore`, `app/db/metro.py`): запуск
сценария, начало и конец, статус и исход (`finished`, `paused`, `timeout`, `unexpected_screen`, …),
шаги, длительность, время шага, купленные бафы, итог «Получено», карта (клетки и посещённые), путь,
события с координатами, 🔋 и аптечки по шагам и сводка (выход, причина ухода к выходу, сигналы,
жетоны, id сообщения забега).

Миграция `0006` добавляет индекс `actions (account_id, created_at)` — по нему идёт лента журнала API.
Миграция `0007` добавляет в `scenario_runs` поля ручного запуска из админки: `requested_by` (логин),
`idempotency_key` (уникален в пределах аккаунта) и `requested_params` (присланные параметры до
слияния с реестром); у запусков планировщика все три `NULL`. Миграция `0008` добавляет индексы под
внешние ключи `unrecognized.message_id`, `scenario_runs.decision_id` и `metro_runs.scenario_run_id`:
без них каждое удаление сообщения, решения или запуска (ретеншн) проверяло бы `ON DELETE` полным
просмотром ссылающейся таблицы. Миграция `0009` добавляет `actions.scenario_run_id` (внешний ключ
на `scenario_runs`, `ON DELETE SET NULL`, индекс `ix_actions_scenario_run_id`): запуск сценария,
шагом которого было действие; его ставит `ScenarioContext` (`run_id` запуска из `PlannerLoop` →
`ActionRequest.scenario_run_id`, в отпечаток идемпотентности не входит), у ручных команд, реакций и
сверки — `NULL`. Запуск удаляется ретеншном раньше несверенного шага — ссылка обнуляется. Старые
действия миграция связывает с запусками задним числом: запуски исполняет один `PlannerLoop` строго
по очереди, поэтому действие, созданное внутри окна `[started_at, finished_at]` ровно одного
завершённого запуска, — его шаг (плановый запуск — действия `scenario`, ручной — `manual` без ключа
идемпотентности); ручные команды (с ключом `manual:…`, запреты `forbidden`/`donate`), реакции
(`urgent`), действия вне окон, в нескольких окнах сразу и во время незавершённого запуска остаются
`NULL`. Сверка шлёт от имени `scenario`, и её действие внутри окна планового запуска будет приписано
ему — это хвост упавшего запуска: пока траты заблокированы, новые плановые запуски не стартуют. Тест
миграций (`tests/db/test_migrations.py`) после `upgrade head` сверяет схему с моделями
(`compare_metadata` пуст), `test_0009_backfills_run_of_old_steps` проверяет перенос на данных.

Пул соединений (`app/db/base.py`) задаёт asyncpg `command_timeout=30` — ни один запрос не висит
дольше 30 секунд; проверка single-instance лока (`SingleInstanceLock.check`) ограничена 5 секундами,
таймаут считается потерей лока.

## Фикстуры

Тесты парсеров игровых сообщений используют реальные записи из `~/pyrobot-research` (выгрузка истории
игровой переписки, собранная прототипами парсеров). Загрузчик фикстур (`tests.fixtures.game()`,
`tests.fixtures.game_msg()`) читает из `tests/fixtures/game/*.jsonl` — JSONL-файлы по семействам
сообщений (profile, battle, activities, и т.д.). Переменная окружения `PYROBOT_RESEARCH` переопределяет
путь к выгрузке (по умолчанию `~/pyrobot-research`).

Добавить новые фикстуры:

```bash
uv run python tools/fixtures.py <семейство> <id> [<id> ...]
```

Команда извлекает сообщения из выгрузки в `tests/fixtures/game/<семейство>.jsonl`, дедублирует и
сортирует по id. По умолчанию берутся входящие сообщения игрового чата; `--chat <id>` — другой чат
(SWINFO в общем чате, канал смузи), `--include-out` — и исходящие (единственный образец инвайта
биржевиков — пересылка самого игрока), `--versions` — каждая правка сообщения из живой записи
отдельной строкой (экран варки смузи меняется после каждого фрукта; `game_versions(семейство, id)`
отдаёт их по порядку, `game()` — последнюю). Правки одной секунды `edit_date` с разным содержимым —
разные версии: вторая и следующие получают порядковый номер `seq` (экран метро правится чаще раза в
секунду: «Идёшь Вниз.» и новое окно). Отправитель сохраняется в поле `from`: разбор SWINFO
пропускает только сообщения пользователя SWINFO. Ожидаемые значения в тестах парсеров берутся
из прогона прототипов на этих же сообщениях; если значение в тесте расходится с текстом
фикстуры, истина — текст фикстуры.

## Парсеры

### Маршрутизация и семейства

Входящие сообщения разбирают распознаватели — чистые функции `IncomingMessage → list[Event]` без
I/O, по модулю на семейство в `app/engine/parsing/`. `default_parser(chats)` — маршрутизатор по
чату (`ChatRouter`): у игрового чата свои распознаватели, у общего чата — разбор SWINFO (только
сообщения пользователя SWINFO), у канала смузи — рецепт, у чата инвайтов биржевиков (если задан) —
инвайт; сообщения прочих чатов событий не дают. Семейства игрового чата:

- `profile` — компакт-профиль (`😎Я`, `◀️Назад`): уровень, 💡, 💵, 🔋, 🔥 и таймер её прироста,
  📚 🔩 ⚙️, рюкзак, 🍊, навыки 🔨🎓🐿🐢, «Битва через», цель взлома, «🛌 Через» и текущее занятие
  с остатком (включая сон под мостом или в отеле);
- `battle` — ответ на выбор цели битвы или защиты («Ты решил взломать …», «Ты встал на защиту …»);
  если точка в конце названия компании (⚡️Stark Ind., 🎩Wayne Ent.) слилась с точкой предложения,
  название восстанавливается по списку компаний;
- `activities` — старт и итог дел (добыча, работа, учёба, еда, переработка ⚙️→🔩, прогулка с

### SWINFO, антифлуд и итоговые события

SWINFO (`swinfo`): анонс записи на фабрику, итог битвы за фабрику (тег победившей команды), сводка
битвы компаний (цена акций каждой компании после битвы), посты лотереи, дневной рейтинг компаний.
Чат инвайтов биржевиков может совпадать с общим чатом: маршруты чата работают независимо, фильтр
транспорта пропускает и сообщения SWINFO, и сообщения с кнопкой `join_fight_*`.

Антифлуд («Ты шлёшь запросы к боту слишком часто») распознаётся всегда, отдельно от семейств.

Итоговые события — старт дела, награды, траты, засыпание, пробуждение, прочитанная книга и т. п. —
помечены признаком `Event.outcome`: редьюсер применяет их к состоянию один раз на
`(чат, сообщение, вид события)`, даже если игра потом правит сообщение. Экраны выдаются только
целиком: частично разобранный экран не даёт событий, чтобы не затереть известное состояние.
Целостность определяется якорями экрана (у рюкзака — заголовок и «Занято N из M»), а не строками,
которые игра при нуле не показывает. Если в игровом чате ни один распознаватель не сработал,
появляется `Unrecognized` с первой строкой текста.

Всплеск нераспознанного (≥5 сообщений за 10 мин) отправляет уведомление уровня `warn` с кодом `unrecognized_spike` и молчит до конца окна; сами нераспознанные сообщения записываются в таблицу `unrecognized`.

## Состояние

### Модель и правила обновления

`app/engine/state` строит состояние персонажа (`CharacterState`, `app/engine/state/model.py`) из
потока событий парсера — редьюсер `StateReducer.apply` (`app/engine/state/reducer.py`). Каждое поле —
`Obs[T]`: `value`, `at` (момент снимка — время правки сообщения) и `src`: `screen` — значение с
экрана игры, `derived` — вычислено приращением или производным правилом, `doubtful` — значение не
тронуто, но неизвестно, учитывает ли оно уже произошедшее событие.

Правила `_Patch`:

- **снимок только новее** (`snap`) — новый снимок применяется, только если его момент не раньше
  момента уже известного значения; более старая правка игнорируется;
- **приращение только к известному** (`change`/`delta` через `_increment_mode`: числовые поля,
  счётчик апгрейдов ⚪️🔵🔴 в `rewards`, запас фастфуда `food_stock` после съеденного, навык в
  `skills` после шага level-up — основного и дополнительного, +1 к выбранному) — изменить
  можно только уже известное значение; если приращение уже сделано этим же сообщением или базовый
  снимок старше его создания — применяется (`derived`, либо остаётся `doubtful`, если таким было
  базовое значение); если базовый снимок снят между созданием и правкой сообщения (или в ту же
  секунду) — значение не трогаем, но помечаем `doubtful`: следующий снимок экрана его обновит.
  Необязательный `since` — момент, раньше которого событие произойти не могло (для билета Горбушки —
  момент экрана «нужен билет»): базовый снимок новее `since` мог событие уже учесть, и значение тоже
  становится `doubtful`;
- **итог один раз на сообщение** — события с `Event.outcome=True` применяются один раз на `(чат,
  сообщение, вид события)`, правка того же сообщения повторно не начисляет; горизонт хранения ключей
  `OUTCOME_HORIZON` — 14 дней.
- **статус задания за день только растёт** — у `daily_personal` и `team_task` экран или строка с
  меткой не новее сохранённой (в том числе той же секунды, доставленные позже) не понижают `done` до
  `active`/`offers` (`none` у командного) и `active` до `offers`; более новый экран за тот же день —
  по-прежнему полный снимок.

КД фастфуда до 15 минут) и 🧸Соня (растягивает принудительный сон до 120 часов) — обе ошибки в

### Ежедневные задания

Ежедневные задания — значения за день заданий (`tasks_day`: дата по Москве, сброс в 00:00, не в
03:00, как у смузи); день хранится в самом значении, по возрасту они не устаревают, а значение за
другой день планировщик считает неизвестным. `daily_personal` (`PersonalTask`): `day`, `status`
(`offers` — варианты, `active` — выбрано, `done` — выполнено), варианты (тип, сложность, цель, 🏆),
выбранное (тип, сложность, цель, ресурс, дела) и прогресс `current`; `team_task` (`TeamTask`):
прогресс, цель, ресурс, `day`, `status` (`none` — глава не выбрал, `active`, `done`) и дела из
подсказки. Правила: экран заданий — полный снимок обоих значений за день экрана; правка «⏳Выбранное
задание» — личное `active` с прогрессом 0; строка `🔜Личное задание: X из Y<ресурс>` в итоге меняет
только прогресс выбранного задания того же дня с тем же ресурсом, иначе игнорируется;
«Ты завершил задание в команде…» — личное `done` за день сообщения (значения за этот день нет —
`done` без деталей) и награда как итог, один раз; строка `🔜Командное задание: X из Y<ресурс>` к
заданию того же дня и ресурса меняет прогресс и цель, сохраняя статус и дела (экранному заданию с
нераспознанным условием, без ресурса, ещё и дописывает ресурс), иначе создаёт задание этого дня
`active` без дел с `src=derived` (дела неизвестны до экрана); при X ≥ Y — `done`. Снимки прошлых
версий (`team_task` без дня) грузятся, но день не знают.

### Метро и лотерея

Метро: `metro_ready_at` — когда снова можно спуститься (экран входа — «уже можно», момент экрана,
а если 🔥 на нём меньше цены входа — ещё и мотивация: планировщик считал иначе;
отказ «До следующего спуска …» — момент плюс остаток; итог забега — момент выхода плюс 16 часов,
`derived`); `metro_message` — идущий забег (`MetroRunRef`: id сообщения и наблюдение `battle_at`,
известное на первом экране забега, — битва, за 15 минут до которой игра выкинет персонажа; с экрана
бафов и любого экрана забега, момент — последний экран), итог «Получено» ставит `null`; экран бафов после входа списывает 2🔥 один раз на сообщение забега; 🔋 кадров карты,
запроса аптечки, итога боя и ловушки-стрелы (0) — снимок выносливости персонажа (в метро она та же).
Лут и награды боёв идут в копилку забега и начисляются только итогом «Получено» (один раз): 💵, 💡,
📚, ⚙️, 🔩, улучшения ⚪️🔵🔴, фастфуд — к известным запасам `food_stock` (жетоны 🕳 в состоянии не
ведутся).

Лотерея: `lottery` (`LotteryState`) — согласованный снимок одного тиража: номер `draw`, закрытие
продажи `until` (момент экрана плюс «Розыгрыш через» минус 10 минут), по валютам (`money`,
`knowledge`, `raw`, `details` — имена полей самих ресурсов) куплено `bought`, лимиты `limits`, цены
`prices` и нехватка `short` — валюты, на которые при последней попытке не хватило, со значением
ресурса после неё. Экран тиража — полный снимок (нехватку того же тиража сохраняет) и снимок 💵📚🔩⚙️;
ответ «Купить все» того же тиража — итог один раз: прибавляет купленное к `bought`, вычитает
купленное × цену из ресурсов, а валюты ниже лимита после него — нехватка (игра покупает сколько
может); снимок, снятый между созданием ответа и его доставкой (или в ту же секунду), — `doubtful`.
Ответ другого тиража (или без известного экрана) заменяет снимок целиком: номер и срок есть,
куплено/лимиты/цены — неизвестны (`derived`), потраченные ресурсы — `doubtful`. Экран покупки за
валюту номера тиража не показывает: он обновляет свою валюту (куплено, лимит, цена, нехватка), только
если срок продажи по его отсчёту совпадает с известным в пределах 2 минут; куплено больше
известного (правка после клика по количеству) — разница × цена списывается с ресурса по правилу
приращений (вторая правка того же сообщения, снятого после первой, делает ресурс `doubtful`). Как таймеры, по возрасту
снимок не устаревает; прошлый тираж отличает планировщик.

### Статистика дел

`activity_stats` — скользящее среднее наград каждого дела (`ActivityStat`: 💡, 💵, 📚, ⚙️, 🔩 без
цены дела, `count` — число учтённых итогов): каждый `ActivityFinished` сдвигает среднее на 10%
(`STATS_ALPHA`) к наградам итога, начиная со стартовых значений корпуса (`DEED_PRIORS`: добыча 203💡,
работа 117💡 + $25.7 + ⚙️2.3 + 🔩0.8, учёба 235💡 + 📚11, переработка 253💡 + 🔩5, прогулка 173💡 +
$2.6 + 🔩0.7, конфа 112💡 + 📚31 — у прогулки и конфы средние всех итогов 2024–2025 вместе с
провалами). Пока экран цен не виден, цены дел берутся из `DEFAULT_PRICES`.

### Ретеншн

**Ретеншн** (`app/db/retention.py`, `DbRetention`) — фоновая задача `retention` под супервизором:
первый проход через 5 минут после старта (`Runtime.retention_first_s`, чтобы не мешать догону
пропусков), дальше раз в 6 часов (`Runtime.retention_s`). Сроки — секция настроек `retention`:
`messages_days` (90) — журнал: сообщения (их нераспознанные удаляются каскадом), действия, запуски
сценариев и уведомления; `decisions_days` (30) — решения планировщика (у запусков сценариев
`decision_id` обнуляется); `metrics_days` (365) — ряды метрик и забеги метро, кроме последних 20
завершённых (`done`) забегов: по ним считается p90 бюджета метро, сколько бы им ни было лет. Не
удаляются никогда: действия в `intent`/`sent` и несверенные неизвестные исходы трат (`outcome_unknown`,
не `nav`, без `reconciled_at`) — это обязательства сверки; ручные действия и ручные запуски
сценариев с ключом идемпотентности — журнал ключей (иначе повтор старого ключа исполнил бы
команду снова); запуски в `queued`/`running`; история настроек, снимок состояния, админы и сессии
(истёкшие сессии чистит `session-purge`). Удаление идёт пачками по 5000
строк отдельными транзакциями, чтобы не держать долгие блокировки против конвейера. Сбой прохода
не роняет задачу: он логируется, первое в серии неудач уведомление — `warn` `retention_failed`,
следующая попытка — по расписанию.

### Политика шлюза

**Политика шлюза.** Каждая не-`nav` команда относится к механике (`feature_of_text`/
`feature_of_callback` в `app/engine/commands.py`); если механика выключена в `features`, шлюз
отклоняет команду (`REJECTED "feature_off:<механика>"`) для всех источников, кроме ручного. Пауза
(`engine.paused`) отклоняет не-`nav` команды планировщика и сценариев (`REJECTED "paused"`) — в том
числе очередной шаг сценария, начатого до паузы; срочные и ручные — по флагам
`urgent_while_paused`/`manual_while_paused`. Шаг несертифицированного сценария
(`ActionRequest.simulate`) подавляется в любом режиме (`SUPPRESSED "uncertified"`, в `dry_run` —
`"dry_run"`), `nav` уходит. Режим запуска сценария фиксируется на его старте (для плана — в момент
решения): шаги запуска, начатого в `dry_run`, несут `ActionRequest.dry_run` и подавляются
(`SUPPRESSED "dry_run"`) до конца запуска, даже если режим переключили в `live`; следующий запуск
идёт уже в новом режиме. Ожидание может слушать другой чат (`Expectation.chat_id`): шаги
сценариев всегда ждут ответа в чате игры, даже если команда ушла в чат Tangerine (`/gt`). Если игра
отвечает только на ошибку, ожидание помечается `Expectation.silence_confirms` (сейчас — только
`/gt`): тишина до тайм-аута подтверждает действие (`CONFIRMED "silence"`) без блока трат и сверки.

### Сценарии

**Сценарии** (`app/engine/scenarios`) — корутины над `ScenarioContext`: `send`/`click` отправляют шаг
через шлюз от имени `SCENARIO` и ждут семантический предикат (`expect_events` — событие нужного типа
подтверждает, `Refused`/`Busy` — отказ; `expect_button` — сообщение с кнопкой). Многошаговые
сценарии берут аренду шлюза (`lease`) и между шагами проходят безопасную точку (`safe_point`: срочное
действие может пройти, пауза останавливает сценарий). Безопасная точка длится, пока шлюз не выбрал
следующий шаг аренды: срочное и ручное действие, поданное до этого, уходит раньше шага по
приоритету, а после выбора шага ждёт следующей безопасной точки или конца аренды. Итог — `ScenarioResult`: `done`; `nothing`
(делать нечего, например Горбушка ждёт следующего продавана); `refused` (отказ игры с причиной);
`suppressed` (`dry_run` или несертифицированный шаг); `failed` (нет ответа, шлюз отклонил, сбой);
`stopped` (остановка в безопасной точке: пауза или неожиданный ответ). Реестр (`registry.py`,
`SCENARIOS`): `refresh` (экран-источник: профиль, рюкзак, меню еды, подарки, Горбушка — те же, что у
сверщика), `book`, `card`, `prizebox`, `container_small`, `container_medium` (у коробки и

контейнеров 0 — `nothing` без команды открытия), `daily_refresh` (`/crew` → `⏳Задания`: кнопка
заданий работает только из меню команды; итог `done` или неудача `failed` `wrong_screen`, если игра
ответила общей справкой «Если жаждешь общения…», — пауза повтора растёт, как у прочих неудач),
`daily_pick` (параметр `task`, например `convDets_hard`: тот же экран → если личное задание уже
выбрано или выполнено — `nothing` `already_chosen`, варианта нет — `nothing` `offer_gone` →

задуманное по каждой валюте — цель по каждой валюте весь остаток до лимита и на всю цель хватает
сверх запасов и резервов (игра не знает ни целей, ни запасов и купит всё, на что хватит денег в
момент отправки) — срок продажи по экрану сверяется с часами сценария (прошёл — `nothing "sale_closed"`) и
уходит одна команда `/tickets_all`, ответ сверяется с номером тиража экрана (другой — отказ
`draw_changed`, «Куплено 0 билетов.» — `nothing "bought_none"`), «❌Лотерея скоро закончится…» —
конечный отказ `lottery_closed`; иначе — покупка по
валютам `buy_each`: по валютам с билетами по карману `<валюта> => 🤑` → новое сообщение экрана
валюты с inline-кнопками количества `tickets_<валюта>_<n>` (1/3/5/7 и остаток до лимита, «всех»
нет) → остаток считается по «Куплено» самого экрана валюты до абсолютной цели (куплено по экрану
тиража + по карману: покупка с телефона между экранами не даёт перебора) → клик по наибольшей
кнопке не больше остатка (callback — с самой кнопки текущей
ревизии, имена валют не угадываются) → ответа на callback нет, итог — правка того же сообщения с
большим «Куплено» (правка «не хватает» — конец этой валюты) → кнопки перечитываются, следующий клик
без безопасной точки (кнопки привязаны к сообщению); экран валюты «не хватает» или «уже купил все
доступные» — валюта пропускается, без подходящей кнопки количества — `failed "no_quantity_button"`
(пауза повтора растёт, уведомление одно); между валютами — безопасная точка, затем снова `/tickets` со
сверкой номера тиража (другой — `nothing "draw_changed"`) и пересчётом целей; срок продажи
сверяется перед командой валюты и перед каждым кликом; итог — `done "bought_each"`, а если ничего не
куплено — `nothing "cant_afford"` с нехваткой, когда хоть на одну валюту не хватило (по запасам или
по мнению игры), иначе `nothing "target_reached"` (с телефона докупили до цели); параметры
необязательны — без них сценарий берёт все билеты без запаса, но планировщик передаёт их всегда, а
ручной запуск без них получает недостающие из настроек и резервов, как у планировщика
(`lottery_params`); недопустимое значение — `failed "bad_param:<ключ>"`). Выбор акции и размер покупки — общие для сценария и планировщика (`app/engine/market.py`).
Контекст сценария (`ScenarioContext`) несёт часы (`clock`) и уведомления (`notify`), а шаг может
задать свой таймаут ожидания (`click(..., timeout_s=)`); итог сценария может нести подробности
(`ScenarioResult.details`, у метро — запись забега).

### Решение

**Решение** (`app/engine/planner/decide.py`, `decide(state, settings, now, *, certified,
last_refresh, cooldowns, last_done)`; общие помощники — `base.py`, обязательства — `obligations.py`)
— чистая функция: `Act(scenario, params, reason, candidates)` или `Wait(until, reason, candidates)`;
`candidates` — все рассмотренные варианты с оценкой и причиной отказа (`busy`, `no_motivation`,
`no_money`, `battle_window`, `factory_window`, `uncertified`, `cooldown`, `stale:<поле>` и т.д.).
Порядок: level-up → биржевики → цель битвы → 🔋 к битве → слив налички → запись на фабрику →
ежедневные задания → лотерея → сон →
книга → фастфуд (первый вид по `food.order`, у которого нижняя граница выше текущей 🔋; бананы —
только сверх запаса) → карта → контейнеры → призовая коробка → Горбушка (бой при встрече или по
кулдауну, покупка билета при его отсутствии и достатке 💵/📚, неизвестное состояние — открыть экран) →
мандарин → смузи → метро → дело. Дело выбирается среди `strategy.deeds` с вердиктом `ok` (окно
битвы, дедлайн сна, окно фабрики, 🔥, $, ⚙️ и резервы — как ниже): сначала дело личного задания
(`active`, сегодняшнее, прогресс ниже цели; у `materials` — лучшее по оценке из работы и прогулки;
у `robPro` дел нет — Горбушка идёт своим ходом; причина `personal <тип>`), затем командного, пока
команда не дошла до цели (лучшее по оценке из дел подсказки; задание на Горбушку дел не меняет;
причина `team <дело> X/Y`; оба слоя от `features.daily_tasks` не зависят — задание, выбранное с
телефона, бот видит в чате и доделывает), затем основные дела
`strategy.focus` — из них то, что сделано меньше раз за текущий день MSK (граница 00:00), при
равенстве — первое по порядку `focus` (причина в журнале `focus <дело> (N today)`, счётчики — в
параметрах кандидатов); добыча и переработка стоят одинаково — 1🔥, поэтому равное число запусков —
равный расход 🔥. Если ни одно основное дело не проходит — запасное с лучшей оценкой
`(w_xp·💡/exp_scale + w_money·(💵 − цена)/money_scale + w_res·ресурсы/resource_scale) / цена в 🔥`
по `activity_stats` (причина `best score …`); устаревшая (старше 7 дней) цена дела берётся по каждой
составляющей как большее из запомненной и `DEFAULT_PRICES`. Фастфуд и призовая коробка доступны во время дела, остальное (в том числе level-up
и контейнеры — на них игра отвечает «занят») — только когда персонаж свободен; во сне планировщик
ждёт пробуждения и выставляет только цель битвы. Резервы: 1🔥 под бой Горбушки, если он в ближайший
час; 💵 на билет, пока билета нет; цена отеля за 3 часа до окна сна, если к нему выбран отель, — дела
их не тратят, а билет покупается только из денег сверх резерва на отель. Резерв на отель (и здесь, и
в сливе налички) держится, только если сон будет исполнен: механика включена и в `live` сценарий сна
сертифицирован (сертифицирован). Дело не начинается, если
закончится позже чем за 6 минут до битвы (запрет действует до минуты после её начала) или позже
дедлайна сна. Если нужное поле неизвестно, устарело или сомнительно (`stale_fields`; мотивация — ещё
и после тика регенерации, время битвы — после её начала), решение — обновить его экран (`refresh`),
но не чаще `engine.refresh_min_interval_s` на источник; идущее дело считается известным до своего
`until`.

Время битвы планировщик приводит к началу часа (`battle_hour` в `base.py`): битвы начинаются ровно
в начале часа, а отсчёт «Битва через …» игра округляет вниз (до минуты, от суток — в каникулы — до
часа), поэтому берётся ближайшее начало часа не раньше `battle_at` − 2 мин. Точность видна по длине
отсчёта (`battle_at` минус момент наблюдения): у отсчёта от суток запас — 2 с, иначе отсчёт, снятый
в первые минуты часа, указал бы на час раньше. Состояние хранит наблюдение как есть.

### Обязательства

Обязательства (слой 1, время — московское):

- **цель битвы** — перед каждой битвой, в том числе во сне и во время дела: цель из
  `battle.overrides` на час битвы, иначе `battle.target`. Цель уже выставлена, если профиль, снятый
  вместе со временем предстоящей битвы или позже, показывает её, либо (защиту профиль не показывает)
  эта же цель выставлена на эту битву (`battle_target_set`); за минуту до битвы не выставляется;
- **🔋 к битве** — если до битвы ≤ 30 минут и 🔋 на нуле: фастфуд по обычным правилам (`food.order`,
  запас бананов), если он готов или будет готов за 2 минуты до битвы (устаревшие запасы еды и её
  кулдаун сначала обновляются — `refresh` меню еды, а не платное `eat`), иначе — дело `eat`, если
  дела включены и оно закончится не позже чем за 6 минут до битвы;
- **слив налички** — с `battle − dump_lead_min − 10 мин` до минуты до битвы, в часы биржи: если 💵
  минус оставляемое (`cash_floor` + билет Горбушки + на ближайший сон в отеле — большее из цены
  отеля и порога `hotel_if_cash_after_reserve_ge`, чтобы после слива выбор отеля не изменился; но
  не меньше неснижаемого остатка биржи) не меньше `min_dump`, а по котировкам,
  увиденным уже в окне слива (они меняются после каждой битвы), есть подходящая акция;
- **фабрика** — запись с 18:00 до 18:15, если сегодня ещё не записан, не пришёл отказ «пропускаете»
  и команда не выиграла вчерашнюю битву (`factory_won_at`); пока запись нужна, дела, которые
  закончатся после 18:00, не начинаются (`factory_window`);
- **биржевики** — ночью (22:00–08:00) по инвайту не старше 3 минут, если этой ночью ещё не
  побеждал и персонаж свободен;
- **мандарин** — раз в `tangerine.interval_h` от последней успешной отправки (`last_done`, из
  журнала запусков; плюс минута `READY_SLACK` — запуск стартует раньше, чем `/gt` реально уходит),
  не раньше кулдауна из отказа; после отказа «не играет» — пауза на сутки;
- **смузи** — по рецепту из канала, полученному после сегодняшнего сброса (03:00), если сегодня
  ещё не варили (в том числе неудачно — `last_done`) и по известным остаткам хватает ингредиентов;
- **продолжение метро** — первым шагом, до level-up: если `metro_message` указывает на забег,
  последний экран которого не старше 2 часов, а игра его ещё не выкинула (за 15 минут до начала часа
  битвы забега — той, что была известна на его входе; профиль после неё показывает уже следующую), —
  сценарий `metro` с `resume` и моментом битвы забега (без проверок кулдауна, бюджета и 🔥: вход уже
  оплачен). Так забег продолжается после рестарта процесса и после остановки сценария (пауза,
  таймаут — с кулдауном серии неудач);
- **метро** — персонаж не в забеге (до выброса игрой нового входа нет: забег продолжается или, если
  продолжать нельзя — экран старше 2 часов или незнакомый, — ожидание выброса `metro_kick`),
  кулдаун прошёл (`metro_ready_at`; если таймер неизвестен — не раньше 16 ч после
  последнего успешного запуска `metro` из журнала, иначе заход сам покажет экран входа или отказ по
  кулдауну), до битвы (начало её часа, как у всех обязательств) не меньше
  `max(min_budget_min, p90 прошлых забегов × 1.5) + battle_margin_min + extra_margin_min`
  (длительности — из `metro_runs`, `decide(..., metro_durations=)`), забег той же длины не упирается
  в дедлайн сна и в запись на фабрику, персонаж свободен, 🔥 минус резерв Горбушки ≥ 2. Параметры
  сценария — нормированный момент битвы, запас и политики из настроек `metro`. Если спуск станет
  доступен в ближайший час и битва позволит, дела держат 2🔥 на вход;
- **сон** — в ночное окно без битв: с 22:05 (если ждём инвайтов биржевиков и в ту ночь, на которую
  планируется сон, ещё не побеждали — с 00:30) так, чтобы проснуться до 12:45; не раньше разрешения лечь и не позже, чем
  требует дедлайн (`lead_min` до него); сон, накрывающий запись на фабрику, ждёт её конца, если
  после неё до дедлайна остаётся 15 минут. Деньги на отель дела не тратят за 3 часа до начала сна.
- **лотерея** — в окне продажи 19:17–21:05 MSK включительно (продажа закрыта с 21:07, розыгрыш в 21:17; до
  19:17 — пробуждение к старту тиража): снимок неизвестен, снят до 19:17 (прошлый тираж),
  сомнителен или без купленного/лимитов/цен — `lottery_buy` (он сам читает экран); иначе — если
  куплено меньше цели (`lottery.tickets`, не больше лимита) и хотя бы на один билет недостающей
  валюты хватает сверх `lottery.keep` (у 💵 — ещё резервов билета Горбушки и отеля, как у дел);
  неизвестный или устаревший ресурс — тоже запуск (экран его покажет); валюта с нехваткой ждёт,
  пока ресурс не станет больше, чем был после неудачной попытки, и при устаревшем ресурсе
  лотерею не открывает — сначала профиль (`refresh`, с его лимитом), повтор — по новому
  наблюдению; нехватку сверх запасов и резервов, которую снимок тиража не знает, приносит итог
  `cant_afford` сценария — цикл планировщика держит её в памяти до следующего запуска лотереи и
  добавляет к `short` снимка того же тиража; не хватает — кандидат
  `cant_afford`; цель достигнута — до следующего тиража ничего. Во время дела покупка идёт (в
  выгрузке `/tickets_all` дважды прошёл сразу после старта добычи и работы), во сне шаг не решается
  (все 5 отказов «❌Никак нельзя» на `/tickets_all` за 2026 — во сне). Параметры — `tickets_<валюта>`,
  `keep_<валюта>` и `reserve` (резервы 💵);
- **ежедневные задания** — шаг перед сном: выбор занимает секунды, а ночной сон иначе отодвинул бы
  его на утро; во сне не выполняется, занятость делом не мешает (выбор работает и во время дела),
  персонаж в метро — пропуск; `features.daily_tasks` выключен — шага нет. В 23:58–00:02 MSK шаг ждёт
  00:02: команда, ушедшая до сброса, могла бы дойти уже до нового дня; после сброса он будит
  планировщик, чтобы перечитать экран. Нет личного или командного задания за сегодня (вчерашние —
  неизвестны, сколько бы им ни было) или командное `active` известно только по строке прогресса (у
  экранного с незнакомой подсказкой дел просто нет) — `daily_refresh`, но не чаще раза в 10 минут
  (`last_refresh["daily"]`, отметку ставит и неудачный запуск; неудача дальше — обычный кулдаун с
  ростом до 2 ч; первое чтение нового дня заданий лимит не откладывает). Командное `active` ниже
  цели перечитывается, если его наблюдению больше 30 минут: его закрывают и другие игроки, а
  сообщения о выполнении командного нет; так же перечитывается `none` — глава может выбрать задание
  позже, а строки прогресса приходят только в итогах дел по его условию (лимит не дал перечитать —
  выбор личного задания от этого не откладывается). Варианты — `daily_pick` с заданием по правилу:
  только hard (у всех по 90🏆 — больше, чем у medium и easy; нет hard — кандидат `no_hard_offer`,
  задание в этот день не берётся), среди них — первое по `daily.personal_order`, выполнимые — вперёд
  (невыполнимые — кандидаты `not_feasible`), а если не успеть ни одно — всё равно первое по порядку:
  невыполненное задание ничего не стоит. Выполнимо, если выполнимо хотя бы одно дело задания: оно в
  `strategy.deeds`, `deed:<дело>` сертифицирован (в `live`), дела включены — и по грубой оценке
  успевает до крайнего срока — 24:00 или начала сна, если сон будет исполнен, начнётся до 24:00 и
  продлится за полночь (сон, который закончится до полуночи, срок не двигает, а вычитается из
  времени): запусков `ceil(цель / доход за запуск)` (доход — `activity_stats` или `DEED_PRIORS`: 💵 у
  `jobMoney`/`walkMoney`, 📚 у `learnKnows`/`confKnows`, 🔩 у `materials`, 10⚙️ за запуск у
  `convDets`), 🔥 на них не больше текущей плюс прирост до срока (1/ч), время — не больше оставшегося
  без сна и окна ближайшей битвы, 💵 и ⚙️ — не больше имеющихся сверх резервов. `robPro` выполнимо,
  если включена Горбушка и оставшихся до срока боёв (ближайший — сейчас или по таймеру, дальше раз в
  час вне сна, пока жив билет и не наступил срок: бой в сам срок уже не в счёт; не больше оставшихся
  продаванов; билета нет, но он по карману сверх резерва на отель — та же проверка, что у покупки
  билета, — первый бой сейчас, не больше дневного лимита с экрана билета или 4) × 12⚙️ хватает на
  цель. Причина в журнале — `personal <тип>`, а если не выполнимо ни одно —
  `personal <тип> (not feasible)`.
Кулдаун рефреша — свой у каждого источника (`refresh:<источник>`): неудачный рефреш профиля не
откладывает рефреш рюкзака. Игровые таймеры выведены из даты сообщения с точностью до секунды, а
итог приходит в момент таймера + 0–1 с, поэтому таймер считается истёкшим с запасом `TIMER_MARGIN`
(3 с): дело идёт до `until` + 3 с, так же отсчитываются бой и возврат в Горбушку и тик 🔥. Кулдауны
книги, карты, фастфуда, коробки, мандарина и разрешение лечь экраны показывают с точностью до минуты
(с округлением вниз), поэтому к ним добавляется ещё минута (`READY_SLACK`); таймер, истёкший уже на
момент снимка (экран без таймера, встреча с продаваном), готов сразу. В `live` выбираются только
сертифицированные сценарии, в `dry_run` — любые (шлюз их всё равно подавит). Если ничего не подходит
— `Wait` до ближайшего таймера плюс `TIMER_MARGIN` (конец дела, кулдауны книги, фастфуда и коробки,
следующий бой или возврат в Горбушку, тик 🔥, окна обязательств (сон, слив налички, запись на
фабрику, мандарин, полночь заданий), конец битвы, лимит рефреша, кулдаун сценария).

### Цикл

**Цикл** (`app/engine/planner/loop.py`, `PlannerLoop`, фоновая задача `planner`) просыпается по каждой
доставке шины, по `Wait.until` (не реже раза в 30 минут) и по сигналу фасада. Пока движок не готов
(пауза, kill switch, блок трат, конвейер нездоров, нет лока, Telegram не `ONLINE`), он не принимает
решений, не показывает момент пробуждения (`next_wake` пуст) и проверяет готовность раз в 5 секунд.
Каждое решение пишется в `decisions` (одинаковые ожидания подряд — один раз), каждый запуск
сценария — в `scenario_runs`; момент последнего успешного или прерванного рестартом (исход
неизвестен) запуска каждого сценария цикл берёт из `scenario_runs` при первом решении
(`PlannerStore.last_done`) и обновляет после `done` — по нему считаются период мандарина и смузи раз
в день, в том числе после рестарта. Счётчик дел за день (`PlannerStore.done_on_day(день)` — число
запусков `deed:*` со статусом `done`, начатых в этот день MSK; прерванные и прочие не считаются) цикл
держит в памяти вместе с его днём: на каждом решении день вычисляется заново, при смене дня счётчик
перечитывается из `scenario_runs`, а успешный запуск дела увеличивает его, только если начат в
текущий день (сбой чтения логируется, решение идёт с пустым счётчиком, чтение повторяется на
следующем). Запись забега метро (`ScenarioResult.details["metro"]`) цикл
сохраняет в `metro_runs` после записи запуска, в том числе приостановленного (сбой сохранения только
логируется), а длительности
завершённых забегов (последние 20, `MetroRunStore.durations`) берёт при первом решении и дополняет
после каждого `done`, оставляя последние 20, — по ним считается бюджет метро. Отказ «адресат не играет» даёт уведомление
`tangerine_not_player`. Контекст сценария получает `simulate`, если
сценарий не сертифицирован, — независимо от режима, поэтому смена `dry_run` на `live` посреди
сценария не делает его шаг реальным. Итог сценария задаёт кулдаун по ключу — имени сценария, у
рефреша — `refresh:<источник>`: `nothing` и отказ `busy` (конец дела уже известен из отказа) — 1
минута, кроме итогов из `NOTHING_HOLD`, которые скоро не изменятся (закрытая биржа у слива — 30
минут, до конца окна слива; сменившаяся цена входа в метро — 2 часа; у лотереи нет тиража — 30
минут, а в начале окна продажи, 19:17–19:30 MSK, — 2 минуты (тираж мог открыться на секунды позже),
продажа закрыта — 2 часа, до конца окна); прочий отказ — 5 минут, а отказ, общий для всех дел (`battle_soon`, `battle_running`,
`factory_running`, `tired`, `levelup_required`), откладывает на 5 минут все дела; серия неудач
(`failed`/`stopped`) — 5 минут, затем 10, 20 и так далее, но не больше 2 часов, `done` серию
сбрасывает. Первая неудача серии даёт уведомление `scenario_failed`, следующие — нет. Остановка по
паузе неудачей не считается и пишется в журнал как `stopped` с причиной `paused`. Кулдаун ставится до
записи итога в `scenario_runs`: сбой БД не оставляет сценарий без него. Подавленный сценарий
(`dry_run`, несертифицированный шаг) откладывается на 10 минут, подавленное дело — вместе со всеми
делами, а планировщик решает остальное: журнал `dry_run` показывает всё, что бот сделал бы; при
смене `engine.mode` эти отсрочки снимаются. Подавление kill switch или остановкой шлюза
(`kill_switch`, `shutdown`) отсрочки не даёт.

## Метро

### Решатель

**Решатель** (`app/engine/metro/`) — чистый код без I/O, время передаётся аргументом.
`MetroSolver.next(событие, now)` вливает экран в модель и возвращает следующий шаг: `Click(callback,
причина)`, `Done` (итог «Получено») или `Halt(причина)` — дальше без человека нельзя.

- **Карта** (`grid.py`, `Grid`): глобальная сетка в координатах `(строка, столбец)` от входа —
  стена, проход, выход (неизвестное не хранится) и посещённые клетки. Окно 5×5 кадра вливается
  вокруг позиции; позицию двигает подпись прихода («Вниз» — пришли вниз) или экран события на
  новой клетке (лут, NPC, сундук, выход); остальные подписи («Ждёшь», «Остался», «Не бьёшся», «Не
  открываешь», «Стена») — та же клетка. «Стена» в ответ на свой ход в проход по карте — карта
  разошлась с игрой, `Halt("unexpected_wall")`. Экран выхода без ожидаемого хода (ход до рестарта не
  попал в журнал) клетку не трогает: персонаж — на соседнем известном выходе, если он один, иначе
  позицию ищет следующий кадр карты по всей карте. Повторяющиеся окна (прямой коридор) позицию не меняют. Окно,
  противоречащее карте, переобъявляет позицию: единственное место без противоречий с наибольшим
  совпадением (не меньше 12 клеток), при обычном ходе — только среди соседних с ожидаемой клеток
  (ход не состоялся), по всей карте — только для свежего кадра после рестарта (`resync`);
  неоднозначно или далеко — `Halt("lost")`.
- **Обход** (`plan.py`): цель — посетить все достижимые проходы (лут, NPC и сундуки на карте не
  видны). Шаг — к ближайшей непосещённой клетке по известным проходам (на дереве это обход в
  глубину с доведением ветки до конца); выбранная цель держится до прихода (пересчёт на каждом шаге
  качал бы между областями); проход через клетку выхода дороже на 3 шага (диалог «Выходишь?»).
  Известный выход — не цель обхода, ветка выхода откладывается на конец: первыми идут клетки, чьи
  пути ответвляются от пути игрока к выходу ближе к игроку (по дереву кратчайших путей от выхода —
  на графе с циклами порядок ветвей не зависит от точки обзора); на дереве это оптимальный обход с
  концом в выходе. Обходить нечего — идём к выходу.
- **Бюджет** (`budget.py`, `Budget`): от первого кадра карты до битвы минус запас
  (`battle_margin_min` + `extra_margin_min`). Время шага — медиана последних 20 ходов «клик → новый
  кадр» (диалоги событий, очередь между ходами и простой процесса в замер не входят), пока ходов
  меньше 10 — не меньше априорного (5 с с бафом 🏃, иначе 20 с). Выход известен: если путь до него ×
  время шага × 1.5 + запас достигает битвы — обход бросается (`leave deadline`). Выход неизвестен: с
  60% бюджета — режим `frontier` (сначала клетки, шаг в которые открывает неизвестное), с 85% —
  однократный сигнал `late_risk`. Игра выкидывает из метро за 15 минут до битвы с половиной
  найденного (`kick_at`; экрана выброса не видели). Досрочный выход кнопкой 🚪 необратим, поэтому
  решается по оптимистичной оценке: только если за минуту до выброса выход неизвестен или к нему не
  успеть даже при шаге, равном меньшему из недавнего замера и априорного, плюс клик подтверждения
  «Выходишь?». Условие пересчитывается на каждом кадре и ещё раз в диалоге досрочного выхода (не
  нужно — «Остаться»); перед 🚪 решатель долечивается, только если ещё одна аптечка (❤️ и согласие)
  и выход (🚪 и «Выйти») успевают до выброса. Клик с тостом (❤️, «Продолжить») закладывается в 2 с,
  клик без тоста (🚪, «Выйти», «Остаться», согласие на аптечку) — в 6 с: шлюз ждёт ответа на callback
  до `click_answer_timeout_s` (4 с), затем темп 1.6 с; последнему клику цепочки хватает 2 с, чтобы
  дойти до игры.
- **Политики событий** (`Policy`; значения — из настроек `metro` через `policy_of`, это же — единственный
  источник умолчаний): лут, итог боя и исход сундука — `maze_continue` («Продолжить»
  только на экранах известного типа); аптечка на карте при 🔋 ≤ `heal_at`; в режиме выхода — до 100%
  (`heal_before_exit`), пока есть аптечки; слабый NPC — драться (`npc_low`), сильный — отказ, если
  не включён `npc_high`, но без аптечек при 🔋 ниже `npc_min_stamina` (30) — отказ от любого боя
  (лечиться на экране NPC нельзя); поражение в бою — `Halt("fight_lost")` без «Продолжить»; сундук —
  открыть при аптечках ≥ `chest_min_packs`; выход — отказаться, пока идёт обход, и выйти в режиме
  выхода, но если уход решён на самом экране «Выходишь?» (там лечиться нельзя), а `heal_before_exit`
  включён, аптечки есть, 🔋 < 100 и до выброса успеть «Остаться», аптечки до 100%, шаг с клетки и
  обратно и «Выйти», — так и сделать, иначе «Выйти» сразу; диалог досрочного выхода не по решению
  решателя — «Остаться»; незнакомый экран —
  `Halt("unexpected_screen:…")`.
- Запись забега — `snapshot()` (карта, позиция, путь, события с координатами, 🔋 и аптечки по
  шагам, сигналы). Продолжение после рестарта не нуждается в сохранённой карте: правки сообщения
  забега из журнала повторяются через `replay` (см. сценарий): как `observe`, и режим пересчитывается
  на момент каждого кадра, как его пересчитывал решатель до рестарта, — уход к выходу необратим и
  не сменяется обходом оттого, что путь до выхода стал короче; затем режим пересчитывается на
  текущий момент (`update_mode`). Окно, разошедшееся с картой, сверяется `Grid.locate`.

Воспроизведение всех 533 кадров живого забега через решатель восстанавливает его карту, путь (246
шагов) и выход в точности как в записи исследования (`tests/fixtures/metro/run1.json`); второй
живой забег (399 кадров, решатель прототипа, `run2.json`) — 182 шага, 95 клеток, выход (14, −2) и
итог, с отказами от NPC и сундука, ходом в стену и отказом от досрочного выхода.

### Сценарий

**Сценарий** `metro` (`app/engine/scenarios/metro.py`, аренда шлюза на весь забег): `🏢Офис` →
`🚇Метро` → `maze_enter_accept` → бафы за 🕳 из `params.buffs` (по умолчанию все три, покупаются
только предложенные кнопками и пока хватает жетонов; `maze_buf_coins_*` — донат, шлюз их не
пропустит) → `maze_start` → цикл: экран → `MetroSolver.next` → клик. Ответ на `🚇Метро` разбирается
явно: экран входа — дальше, отказ «До следующего спуска …» — `refused metro_cooldown`, незнакомый
экран — сразу `stopped unexpected_screen` с уведомлением `metro_halted`. Если вход стоит не
`ENTRY_COST` (2🔥) или 🔥 меньше цены, «Вхожу» не нажимается: `maze_enter_decline` (ответ на него
живьём не видели, итог от него не зависит) и `nothing` — `entry_cost_changed` с уведомлением
`metro_entry_cost` или `no_motivation`. Каждый клик ждёт новую
правку сообщения забега (`expect_metro`): «Идёшь …» со старым окном не засчитывается, любая другая
правка подтверждает клик, отказ игры отдельным сообщением — отказ шага. Тип экрана разбирается явно
и на входе, и на бафах, и в обходе: незнакомый экран — `stopped unexpected_screen` сразу, без
ожидания таймаута, с уведомлением `metro_halted` (как и любая остановка решателя: поражение,
потерянная позиция, неожиданная стена). Баф, не отмеченный купленным, — уведомление `metro_buff_not_bought`; без 🏃 —
уведомление `metro_slow`, а априорное время шага в бюджете — 20 с. Таймаут тоста клика — не ошибка
(подтверждение — правка сообщения); ожидание кадра без быстрого шага — вчетверо дольше. Перед каждым
кликом — безопасная точка (пауза останавливает забег, срочное проходит); после неё сценарий сверяет
последнюю ревизию сообщения из кэша конвейера с кадром, по которому решал: в обходе сменился кадр
карты — решение пересчитывается (ход не отправлялся, цель и намерение досрочного выхода
сбрасываются), сменился на экран события — остановка `screen_changed`; на входе, бафах и старте
любая смена — остановка `screen_changed`. Каждый клик несёт ревизию и хеш содержимого кадра
(`expect_revision`, `expect_content`): шлюз перед каждой попыткой отправки сверяет их с последней
правкой и не отправит клик, если сообщение уже другое (`stale_revision` / `stale_content` — хеш
различает и правки одной секунды, у kurigram их ревизия одинакова). Сигналы решателя —
уведомления один раз: `late_risk` — `metro_late_risk`, первый незнакомый символ в окне карты
(клетка считается неизвестной) — `metro_unknown_cell`. Параметры: `battle_at` (ISO, момент битвы), `margin_min`
(запас до битвы), `heal_at`, `heal_before_exit`, `chest_min_packs`, `npc_low`, `npc_high`,
`npc_min_stamina`, `buffs`; не заданные — умолчания настроек `metro` (`MetroSection`, запас —
`battle_margin_min + extra_margin_min`). Итог несёт запись забега (`details["metro"]`: карта, путь, события с
координатами, 🔋 и аптечки по шагам, длительности ходов, бафы, итог «Получено», длительность, время
шага, исход).

С `resume` (id сообщения забега) сценарий не входит заново. Карту, позицию, путь и время начала
восстанавливают записанные правки сообщения из журнала (`ScenarioContext.history` →
`DbJournal.revisions`), прогнанные через решатель с моментами кадров (`replay`, режим — как до
рестарта), а решение принимается только по текущему экрану,
прочитанному прямо из Telegram (`ScenarioContext.reread` → `Transport.fetch`, у kurigram —
`get_messages`): клик до рестарта мог дойти до игры, а его правка — не до журнала, и повторять его
по старому кадру нельзя. Прочитанное проходит конвейер (журнал, состояние) и становится текущей
ревизией (`Pipeline.prime`: после рестарта кэш ревизий пуст, и шлюз отклонил бы клик как
`stale_button`); позиция по этому кадру ищется по всей карте (`resync`). Не прочитать —
`resume_unreadable`, незнакомый экран — `resume_unknown_screen` (оба с `metro_halted`, без кликов);
экран бафов — докупить и стартовать; пустой журнал — остановка. «Идёшь …» — ход ещё идёт:
сообщение перечитывается раз в 2 с, до 10 с, и прочитанное «Идёшь …» входит в повтор (это ход к
текущему кадру); нового окна так и нет — остановка `resume_while_moving`.

Сертификация на `FakeGame` настоящими кадрами (`tests/engine/scenarios/test_metro.py`; `FakeGame`

### Симулятор

**Симулятор** (`tests/engine/metro/sim.py`): лабиринт (`Maze`: карта, вход, спрятанные лут, NPC и
сундуки с исходом), генераторы — дерево (`tree_maze`, совершенный лабиринт с коридорами шириной 1,
выход в дальней половине), лабиринт с циклами (`loopy_maze`: дерево без 15% внутренних стен),
прямой коридор с одинаковыми окнами (`corridor_maze`), карта живого забега; игра на лабиринте
(`MazeGame`): клик → правки сообщения, как у игры («Идёшь …» со старым окном и точкой при повторе
направления, затем новое окно или экран события; лут и итоги боёв — в копилку, граната оставляет
половину с округлением вверх, аптечка +50% до 100; отказ от NPC и сундука — кадр «Не бьёшся» / «Не
открываешь», ход в стену — кадр «Стена» без «Идёшь …» (`wall_hits`), 🚪 с карты — диалог досрочного
выхода, «Выйти» — «Получено» с половиной найденного), по желанию — «сбой» (подпись прихода без
сдвига: противоречивое окно). Экраны рендерятся в настоящем текстовом формате игры (`render`) и
разбираются настоящим распознавателем; круговой тест сверяет рендер с кадрами обоих живых забегов
(528 и 394) до символа и кнопки. `drive()` прогоняет решатель по симулятору с модельным временем
(клик — 1.8 с, ход — ещё 2 с). Метрики-тесты: полнота обхода 100% на деревьях и лабиринтах с
циклами, ни одного хода в стену, на деревьях шагов не больше 2(n−1) + путь от входа до выхода и в
среднем не больше 2(n−1), на циклах — не больше 2.5 шага на клетку, уход по бюджету раньше, чем игра
выкинет (за 15 минут до битвы; выход не найден — досрочный выход за минуту до выброса с половиной
найденного), правила аптечек на каждом ходу, без аптечек и 🔋 — без боёв с NPC, переобъявление
позиции после сбоя; на карте живого забега (95 клеток) решатель проходит всё за 162 шага против 246
у жадного BFS исследования.

## Запуск

```bash
uv run alembic upgrade head
uv run python -m app
```

`app/__main__.py` поднимает uvicorn с одним воркером (`workers=1` — единственный процесс держит и
HTTP, и MTProto-клиент, и очередь действий в одном event loop). `create_application` (`app/main.py`)
собирает `Runtime`, порядок старта: настройки → админ (`ensure_admin`, если задан
`PYROBOT_ADMIN_PASSWORD`) → единственный экземпляр (`app/db/lock.py`, `SingleInstanceLock` —
Postgres advisory lock) → если лок не взят, движок не стартует, уведомление `second_instance`,
`/readyz` навсегда 503 для этого процесса → если в БД есть незакрытые обязательства сверки
(`ActionStore.unreconciled()`: строки `outcome_unknown` класса не `nav` без `reconciled_at`, в том
числе переведённые так `mark_unfinished_unknown()` после рестарта), шлюз сразу блокирует траты
(`block_spending("reconcile_required")`) и шлёт уведомление `actions_outcome_unknown` — блок снимает
сам сверщик (`Reconciler`, см. «Шлюз действий»), как только обновит все затронутые экраны, либо
администратор явным `POST /api/v1/engine/reconciled` → шина, конвейер (снимок состояния
восстанавливается из журнала, редьюсер — `StateReducer`, при изменении состояния метрики
(`StateReducer.metrics`) пишутся в ту же транзакцию, что и журнал) → транспорт (`PYROBOT_TRANSPORT=kurigram|fake`) → шлюз действий,
подписанный на шину → `TgAuthManager`
→ сверщик (`Reconciler`) → незавершённые (`running`) запуски сценариев прошлого процесса помечаются
`interrupted` с причиной `restart` (`PlannerStore.close_running`) → планировщик (`PlannerLoop`,
подписан на шину) → фасад → супервизор (`app/engine/supervisor.py`, `Supervisor`) поднимает и
перезапускает с экспоненциальным backoff фоновые задачи конвейера, шлюза, сверки состояния
`reconcile`, реакции на ограбление `reactions`, планировщика `planner` (при выключенном
`PYROBOT_PLANNER` — только ручные запуски), монитора лага event loop, наблюдателя за локом, чистки истёкших сессий админки
`session-purge`, ретеншна `retention` (см. «Планировщик и сценарии») и (для kurigram) пробы сессии Telegram `tg-probe`, уведомляя `task_failed:<имя>` при
падении → `tg.boot()` пытается восстановить существующую сессию Telegram.

Режим по умолчанию — `dry_run` (`settings.engine.mode`): любое действие, кроме `nav`, подавляется
шлюзом ещё до отправки, в игру ничего не уходит. Переключение в `live` — через настройки движка.

`GET /readyz` отдаёт 200, только когда одновременно: лок держится этим процессом, все фоновые задачи
супервизора живы, Telegram в состоянии `ONLINE`, kill switch не активен, блок трат снят и конвейер
здоров. Фоновая задача `lock-watch` каждые 10 секунд перепроверяет, что advisory lock по-прежнему
держит именно текущее backend-соединение — SQLAlchemy может молча переподключиться после разрыва, и
обычный `SELECT 1` прошёл бы на новом соединении, потеряв лок незаметно. При потере —
`kill("lock_lost")` (latch, без сохранения в настройки) и ровно одно уведомление `lock_lost`, после
чего проверка лока не повторяется (задача не завершается и не перезапускается супервизором — она
паркуется, чтобы не слать `lock_lost` повторно на каждом цикле backoff); `/readyz` уходит в 503.
Автоматического восстановления нет, нужен рестарт процесса: `POST /api/v1/engine/unkill` без лока
отвечает 409 `{"detail": "lock_lost"}` и latch не снимает, а шлюз независимо от latch отклоняет
любую отправку, пока лок не держится (предикат `can_send`, см. ниже).

Остановка (`Runtime.stop`) идёт по независимым шагам: остановить планировщик
(`Supervisor.cancel("planner")` — отменить одну задачу и дождаться её; новый шаг сценария не уйдёт
в закрывающийся шлюз, прерванный запуск закроет `close_running` при следующем старте) → закрыть
шлюз → остановить транспорт (новые апдейты больше не приходят) → дождаться, пока конвейер запишет в
журнал всё уже принятое (`Pipeline.drain`, до 10 секунд; если не успел — warning с числом
оставшихся сообщений) → остановить супервизор → освободить lock → закрыть пул БД — сбой одного шага
не мешает остальным. По SIGTERM uvicorn ждёт открытые запросы не дольше 5 секунд
(`timeout_graceful_shutdown`): поток SSE бесконечен и иначе держал бы остановку до SIGKILL, так и не
дойдя до `Runtime.stop`; по истечении срока запросы отменяются и остановка идёт по шагам выше. 5
секунд плюс дренаж конвейера укладываются в `stop_grace_period: 30s` compose.

## Структура

### Каталоги

- `app/engine` — движок: типы сообщений, парсеры, реестр команд, конвейер, шлюз действий, транспорт.
- `app/db` — Postgres: модели, миграции, хранилища.
- `app/api` — HTTP API для админки.

### Транспорт и вход в Telegram

Транспорт kurigram (`app/engine/transport/kurigram.py`; зависимость закреплена
`kurigram>=2.2.26,<2.3` — транспорт опирается на внутреннее поведение SDK 2.2.x, например на то, что
`invoke(retries=1)` при таймауте делает ровно одну попытку) держит `workers=1` — апдейты
обрабатываются строго по порядку — и `skip_updates=False`, чтобы при старте догнать пропуски
(сообщение, правленое до догона, приходит как новое: его время события и ревизия — по дате правки,
`created_at` — по дате создания, как у обычной правки);
identity (`get_me`) проверяется до запуска апдейтов, и полученный в `identify()` пользователь
переиспользуется в `go_online()` (при входе по коду `get_me` вызывается один раз там). Исходящие RPC
(`SendMessage`, `GetBotCallbackAnswer`) — одна попытка без сна и повторов SDK, все повторы и паузы
идут только через шлюз действий. Потеря авторизации (401 от Telegram) обнаруживается при отправке
текста, при клике и пробой `probe()` — `updates.GetState` раз в 60 секунд (фоновая задача
`tg-probe`, `Runtime.tg_probe_s`, пробует только в состоянии `ONLINE`). Во всех трёх случаях клиент
принудительно останавливается (ошибки остановки логируются, но не мешают), файл сессии удаляется и
создаётся новый клиент — повторный вход идёт с чистого состояния, после чего вызывается
`on_auth_lost`; отправка и клик дополнительно поднимают `TransportAuthLost`. Прочие ошибки пробы
только логируются. `log_out()` при любом исходе `auth.LogOut` делает ту же очистку: 401 (сессия уже
отозвана) считается успешным выходом, другая ошибка пробрасывается после очистки. `BadRequest` при
клике — `TransportRejected`; если бот не прислал тост (таймаут ожидания ответа или
`BOT_RESPONSE_TIMEOUT` от Telegram — игра часто выполняет действие без тоста), `click()` возвращает
`None`, и исход проверяется ожиданием шлюза, а не считается отказом. Таймаут тоста
`click_answer_timeout_s` — не больше 30 секунд. Фильтр чатов (`ChatFilter`) пропускает: игровой чат
и канал смузи — любые сообщения; чат SWINFO — только от пользователя SWINFO; чат приглашений в бой —
только сообщения с кнопкой `join_fight_<11 символов>` (один текст без кнопки не считается); если чат
приглашений совпадает с общим чатом SWINFO, правила проверяются независимо; всё остальное
отбрасывается ещё до журнала. Наивные даты pyrogram трактуются как локальные и переводятся
в UTC; сообщение помечается `recovered`, если разрыв между получением и датой сообщения больше 60
секунд.

Вход в Telegram (`app/engine/tg_auth.py`, `TgAuthManager`) сериализует все шаги логина одним
`asyncio.Lock`. `boot()` при уже авторизованной сессии проверяет identity **до** запуска апдейтов:
чужой аккаунт получает `log_out()` и состояние `ERROR "unexpected_user"`, апдейты не стартуют. Если
сессию отозвали, пока процесс был остановлен, `connect()`/`identify()` при старте получают 401
(`TransportAuthLost`): клиент сбрасывается так же, как при потере на лету, `boot()` сам переводит
менеджер в `UNAUTHORIZED "session_revoked"` и шлёт уведомление `tg_auth_lost` — не через
`mark_lost()`/`on_auth_lost`, потому что `boot()` в этот момент уже держит свой `asyncio.Lock`, а
`mark_lost()` тот же лок захватывает повторно. Попытка входа
(`start`/`submit_code`/`submit_password`) привязана к `owner` и `attempt_id` с TTL
(`attempt_ttl_s`, по умолчанию 600 с): активную непросроченную попытку другого владельца отклоняет
`AttemptMismatch`, тот же владелец может начать заново, после истечения TTL попытку может подхватить
кто угодно. Коды и пароли никогда не попадают в текст ошибок и логи. `mark_lost()` (колбэк
`on_auth_lost` транспорта) переводит менеджер в `UNAUTHORIZED` с `error="session_revoked"`, если
сессия отозвана извне; при переходе из `ONLINE` отправляется одно уведомление `error` с кодом
`tg_auth_lost` (повторная потеря без нового входа уведомление не дублирует). Шлюз с этого момента
отклоняет отправку (`tg_offline`); восстановление — повторный вход в Telegram через админку
(`/api/v1/tg/login/*`). `on_online()` регистрирует колбэки, вызываемые после успешного входа.

### Конвейер и шлюз действий

Конвейер входящих (`app/engine/pipeline.py`, `app/engine/bus.py`) обрабатывает обновления строго
последовательно: дедуп по ревизии, журнал и снимок состояния пишутся в одной транзакции, публикация
подписчикам — только после фиксации. Сбой журнала (БД) повторяется с backoff без потери и без
переупорядочивания сообщений; ошибка редьюсера не теряет сообщение. Догнанные старые сообщения
(`recovered`) старше `react_max_age` помечаются `reactable=False` — только журнал и снимки, без
реакций. Подписчики шины не должны ждать результатов действий — только быстро перекладывать доставку
дальше. Публикация идёт по снимку списка подписчиков: подписка, сделанная во время публикации,
начинает получать доставки со следующей. Кэш последних ревизий сообщений (`latest`, для проверки
кнопок) ограничен `latest_capacity` (5000) и вытесняет давно не обновлявшиеся сообщения.

Шлюз действий (`app/engine/gateway`) — единственный путь отправки: любой текст или клик по кнопке
проходит через `ActionGateway`. Команды разбиты на классы (`app/engine/commands.py`): `nav`
(навигация), `action` (игровые действия), `risky` (необратимые), `forbidden`/`donate` (не
отправляются никогда). Любая трата Sw-coin (🌐) — `donate`, включая бафы метро за монеты
(`maze_buf_coins_*`), весенние розыгрыши и смену призов за 🌐 (`spring_roll_coins*`,
`spring_regenerate*`) и весенние призы `/sbN`. Callback метро, сна и весны принимаются только по
белому списку реально встреченных значений (`maze_up`, `maze_exit_accept`, `maze_buf_tokens_*`, …,
`sleep_7`…`sleep_12`, `sleep_Bridge`, `sleep_Hotel`, `spring_roll_smiles`); любое другое значение,
как и неизвестная команда, — `forbidden`. Задания: `⏳Задания` — `nav`, `/t_<задание>` и кнопка
`t_<задание>_confirm` — `action` механики `daily_tasks`, кнопка отказа `tasksel_decline` — `nav`.
Лотерея: `/tickets` и `🤑Лотерея` — `nav`, `/tickets_all`, `<валюта> => 🤑` и кнопки количества
`tickets_<валюта>_<n>` — `action` механики `lottery`, `cancel_inline` — `nav`; кнопка экрана `🤑Купить все` не разрешена — «купить все» шлёт команда `/tickets_all`.
Кнопка «Проснуться» при ограблении `rob_awake_<число>` — `action` механики `robbery_defense`; она
ничего не тратит, поэтому блок трат её не держит (`spends_nothing_callback`). Правила
проверяются при постановке в очередь, при выборе и перед каждой попыткой отправки: отправлять можно
только в разрешённые чаты — игровой, Tangerine и чат приглашений в бой, если он задан
(`settings.chats`), иначе `REJECTED "chat_not_allowed"`; `risky` уходит только при `source=MANUAL` и
подтверждённом `risky_confirmed`, иначе `REJECTED "risky_requires_confirm"`; `action`/`risky` без
`Expectation` отклоняются (`REJECTED "expectation_required"`) — успешный вызов API сам по себе не
подтверждает результат в игре, подтверждает только ответ игры по предикату; только `nav` без
ожидания подтверждается сразу после отправки (`CONFIRMED "sent"`). Kill switch (ручной `kill()` или
`settings.engine.killed`) подавляет всё (`SUPPRESSED "kill_switch"`), `dry_run` подавляет всё, кроме
`nav` (`SUPPRESSED "dry_run"`), блок трат (`block_spending`) отклоняет всё, кроме `nav` (`REJECTED
"blocked:<reason>"`, кроме клика «Проснуться»); выключенная механика и пауза отклоняют команду по правилам раздела «Планировщик
и сценарии», шаг несертифицированного сценария подавляется (`SUPPRESSED "uncertified"`). Предикат
`can_send` (из `Runtime`) проверяется там же, где kill switch и
`dry_run`, и отклоняет любую команду, включая `nav`: без single-instance лока — `REJECTED
"lock_lost"`, если Telegram не в состоянии `ONLINE` — `REJECTED "tg_offline"`. Истёкший TTL —
`REJECTED "expired"`, клик по кнопке вне последней ревизии сообщения — `REJECTED "stale_button"`,
несовпадение `expect_revision` — `REJECTED "stale_revision"`, несовпадение хеша содержимого последней
правки с `expect_content` (правка той же секунды) — `REJECTED "stale_content"`; всё это проверяется
и перед каждой повторной попыткой. Пока действует пауза после FloodWait
или антифлуда, шлюз не выбирает действия и не пишет `INTENT`; TTL стоящих в очереди при этом
продолжает истекать, и они разрешаются как `REJECTED "expired"`.

### Сверка действий

Действие в хранилище (`ActionStore`) проходит `INTENT` (пишется до отправки) → `SENT` → терминальный
статус (`CONFIRMED`/`REFUSED`/`SUPPRESSED`/`OUTCOME_UNKNOWN`/`REJECTED`). Ожидание ответа
регистрируется до отправки вместе с границей журнала (`boundary()` — номер последней записи журнала
на момент отправки): засчитываются только доставки с `journal_id` больше этой границы, с датой не
раньше момента отправки минус 2 секунды, не исходящие и из того же чата. Тайм-аут ожидания даёт
`OUTCOME_UNKNOWN "timeout"` без автоматического повтора, а у ожидания с `silence_confirms` —
`CONFIRMED "silence"`. `MemoryActionStore`
(`app/engine/memory.py`) — реализация для тестов; `DbActionStore` (`app/db/actions.py`) — Postgres,
с уникальным `(account_id, idempotency_key)` для дедупликации повторных отправок (ключ действия,
отклонённого или подавленного до `INTENT`, не расходуется — тем же ключом можно повторить попытку;
кроме ручных `MANUAL`: их итог сохраняется под ключом всегда, повтор возвращает его, а если ключ
записать не удалось — `REJECTED "store_failed"` вместо итога) и
`mark_unfinished_unknown()` для восстановления после рестарта (незавершённые `INTENT`/`SENT`
переводятся в `OUTCOME_UNKNOWN "restart"`). Если выполнение действия прервано внутренней ошибкой или
остановкой шлюза, строка, уже дошедшая до `INTENT`/`SENT`, сразу закрывается как `OUTCOME_UNKNOWN` с
причиной `internal_error` или `cancelled`; строки `cancelled` при следующем старте считаются
незавершёнными наравне с `INTENT`/`SENT` и так же требуют сверки. TTL, темп отправки и паузы шлюз
считает по инжектированным часам (`Clock.monotonic()`, `SystemClock`).

Неизвестный исход траты (класс не `nav`) сразу блокирует новые траты (`spending_blocked =
"reconcile_required"`) — синхронно, до выбора шлюзом следующего действия, и вызывает хук
`on_uncertain(req, action_id)` шлюза (`ActionGateway(..., on_uncertain=...)`), если он назначен;
исключение хука не мешает блокировке. Само обязательство сверки — строка `actions` со статусом
`outcome_unknown`, классом не `nav` и `reconciled_at IS NULL` (`ActionStore.unreconciled()`); она
хранится в БД и переживает любое число рестартов, пока её не закроет сверщик или пока блок трат не
снимут вручную.

Сверщик (`app/engine/reconcile.py`, `Reconciler`) — фоновая задача `reconcile`, супервизор держит её
постоянно: пока блока трат нет, она только ждёт. Как только блок появляется и движок готов (лок
держится, Telegram `ONLINE`, kill switch не активен), сверщик собирает обязательства
(`ActionStore.unreconciled()` плюс те, что успел сообщить хук `on_uncertain`, но ещё не записал в
БД) и обновляет профиль (`😎Я`) плюс экран каждого затронутого поля: фастфуд и `/eat` — меню еды
(`/to_eat`), `/read_exp`/`/use_card`/`/unbox` — рюкзак (`/inv`), `/unbox_*` — подарки (`/gifts`),
callback `gorbushka_*` — экран Горбушки (`/gorbushka`); прочие действия сверяют только профиль
(`sources_for()`). Все эти команды — класс `nav`, поэтому уходят даже в `dry_run` и при активном
блоке трат. Источник считается обновлённым, только если пришло его событие (например,
`ProfileCompact` для профиля) и все его поля состояния (`RefreshSource.fields`: профиль — `money`,
`motivation`, `stamina`; меню еды — `food_stock`; рюкзак — `books`, `cards`; подарки —
`containers_small`, `containers_medium`; Горбушка — `gorbushka`) сняты не раньше момента запроса
минус 2 секунды (`DATE_SKEW` шлюза) и не помечены `doubtful`. Перед закрытием обязательств поля всех
обновлённых источников проверяются ещё раз: экран, пришедший позже, мог сделать сомнительным поле
уже проверенного источника, и тогда попытка считается неудачной. Когда все нужные источники
обновились и новых обязательств за это время не появилось, сверщик закрывает их
(`ActionStore.mark_reconciled()`), снимает блок и шлёт уведомление `info` `reconciled_auto`; если за
время сверки появилось новое обязательство, блок остаётся, и следующая попытка сверяет уже весь
набор целиком. При неудаче (тайм-аут ответа игры или событие, не учтённое состоянием) сверщик ждёт
`engine.refresh_min_interval_s` (по умолчанию 120с), удваивая паузу с каждой подряд неудачей до
`max_backoff_s` (1800с), и на третьей неудаче подряд шлёт одно уведомление `warn` `reconcile_stuck` —
не повторяя его, пока не случится успех. Запрос, подавленный остановкой шлюза (`SUPPRESSED
"shutdown"`), неудачей не считается: сверщик просто ждёт следующего опроса.

`POST /api/v1/engine/reconciled` — не автоматическое снятие, а явное решение администратора: он
закрывает все открытые обязательства в БД (`reconciled_at`) и снимает блок трат, не проверяя
свежесть состояния. Если за это время шлюз сообщил о новом неопределённом действии, закрываются
только обязательства, известные в начале вызова, а блок трат остаётся до сверки. Автоматическое
снятие блока идёт только через сверщика, описанного выше.

### Защита от ограбления

Защита от ограбления (`app/engine/reactions.py`, `RobberyDefense`, флаг `features.robbery_defense`,
по умолчанию включён): грабят только спящих под мостом, грабитель 4 минуты ищет жертву и 4 минуты
грабит; без пробуждения теряешь 30% 💵, в драке — 15% при проигрыше или +50% денег грабителя при
победе, поэтому проснуться выгодно всегда. Подписчик шины (`on_delivery`) только кладёт тревогу
`RobberyAlert` в очередь (шина ждёт подписчиков до 5 с, а клик ждёт итога десятки секунд); клики
шлёт фоновая задача `reactions` под супервизором: срочное действие (`Source.URGENT`) — клик по
кнопке `rob_awake_<n>` того же сообщения с ключом идемпотентности `rob_awake:<чат>:<сообщение>`
(повторная доставка той же тревоги второго клика не даёт), ожиданием итога — только правки этого
сообщения на драку (`RobberyFight`, до 30 с), TTL в очереди шлюза — остаток окна тревоги (но не
больше 4 минут) и `expect_revision`/`expect_content` кадра тревоги. Окно — `ROBBERY_WINDOW_S` = 230 с
от создания самой тревоги: не проснулся — итог «Тебя ограбил …» приходит отдельным сообщением через
~238 с, а кнопка тревоги так и висит. Тревогу старше окна (из догона, из журнала, задержанную) не
перечитывают и не кликают — только запись в лог, без уведомления. Срочное проходит после текущего
действия и в ближайшей безопасной точке аренды (во сне планировщик выставляет только цель битвы —
это секунды). Тревогу из догона
(`recovered`) обрабатывают, только если доставка `reactable` (не старше
`engine.recovered_react_max_age_min`), и перед кликом перечитывают из Telegram через конвейер: уже
прокликанная с телефона — это итог драки, клика нет; не прочиталась — клика нет. Тревогу,
доставленную и записанную прошлым процессом, который упал или перезапустился до клика, задача
поднимает на старте из журнала (`DbJournal.messages_with_event`: последние ревизии сообщений с
тревогой не старше `engine.recovered_react_max_age_min`), как только движок готов слать (лок,
Telegram `ONLINE`): последняя ревизия уже без кнопки (итог в журнале) — пропуск, иначе тревога
перечитывается из Telegram и только живая (с кнопкой) встаёт в очередь; ключ идемпотентности по
сообщению не даёт кликнуть дважды, если та же тревога придёт ещё и догоном. Тревогу, не
доставленную вовсе, бот не видит. Клик разрешён во сне, при паузе — по `urgent_while_paused`, при
блоке трат — всегда (он ничего не тратит); kill switch, проверка чата и `dry_run` действуют как
обычно. Итог драки применяет редьюсер один раз (💡, 💵, 🔋, пробуждение), итог без пробуждения
(`RobberyLoss`) — тоже один раз: 💡 и потеря 💵 точной суммой из строки «💵Деньги: -$N», сон
продолжается; без строки потери 💵 помечаются `doubtful`. Клик не подтвердился — уведомление `warn`
`robbery_defense_failed`, как и тревога из догона, которую не удалось перечитать; отказ шлюза по
устаревшему кадру (`stale_button`/`stale_revision`/`stale_content`), когда в последней ревизии
тревоги кнопки уже нет (прокликали с телефона, итог правкой), — только запись в лог.

## API

### Аутентификация

`app/api` (`create_api(container) -> FastAPI`) — HTTP API админки. Авторизация — сессионная cookie
`pyrobot_session` (`Secure` в боевой конфигурации, `HttpOnly`, `SameSite=Strict`), срок жизни 30
дней со скольжением: если с последнего обращения прошли сутки, срок и сама cookie продлеваются
заново при следующем запросе (перепроверки из открытого потока SSE сессию не продлевают). Пароль хранится как argon2-хэш (`argon2-cffi`), хэширование и проверка
выполняются в threadpool не более чем в 2 параллельных потока (`LoginRateLimiter.slots`). `POST
/api/v1/auth/login` принимает `{login, password}` (логин до 64 символов, пароль до 1024, иначе 422)
и в ответ отдаёт `{login, csrf_token}` вместе с cookie; мутирующие запросы (`POST
/api/v1/auth/logout`, `POST /api/v1/auth/password`) требуют заголовок `X-CSRF-Token` с токеном
текущей сессии, иначе 403. Сессия и CSRF проверяются раньше, чем доступность движка: аноним
получает 401 на любом эндпоинте `/api/v1` (кроме входа), а не 503 «engine not started». Попытки
входа с одного IP сериализуются (`LoginRateLimiter.lock_for`) и
ограничены экспоненциальным backoff: 5 бесплатных попыток, дальше — 429 с заголовком `Retry-After`,
растущим от `base_s` до `max_s`. Счётчик ключа, у которого последняя неудача старше окна `window_s`
(час) и блок истёк, забывается при следующем обращении; при превышении `max_entries` (10 000) ключей
устаревшие записи и свободные блокировки вычищаются целиком. Неверный текущий пароль при смене
пароля троттлится тем же лимитером с ключом по сессии (`session:<id>`) — те же бесплатные попытки и
backoff с 429 и `Retry-After`. Истёкшие `auth_sessions` удаляет фоновая задача `session-purge` раз в
час (`Runtime.session_purge_s`, `AuthRepo.purge_expired`). Смена пароля (`POST
/api/v1/auth/password`, новый пароль не короче 12 и не длиннее 1024 символов, текущий — не длиннее
1024) отзывает все сессии админа, включая текущую. `GET /healthz` — проверка живости, без
авторизации (снаружи, через Caddy, `/healthz` и `/readyz` закрыты — см. «Образ и деплой»). Swagger
UI, ReDoc и `/openapi.json` отключены (404): схема не публикуется, а выгружается офлайн — `uv run
python tools/openapi.py [файл]` (по умолчанию `openapi.json` в корне репозитория, `build_schema` в
`app/api/openapi.py` собирает приложение без БД и движка); из неё генерируются TS-типы админки.
`openapi.json` лежит в репозитории, тест `tests/test_openapi.py` падает, если он отстал от кода.

Ответы с ошибками описаны в схеме (`responses=`, модели — `app/api/errors.py`; форма ответов от
этого не меняется, модели только описывают её для TS-типов): строковые коды — `ErrorOut`
`{"detail": "<код>"}`, в описании ответа перечислены возможные коды (401 `not authenticated` у
всех эндпоинтов с сессией, 403 `csrf token mismatch` у изменяющих, у ручных команд ещё `forbidden`
и `donate`; 503 `engine not started` у эндпоинтов движка, у команд ещё `store_failed`, у запуска
сценария — `planner not started`); 409 ручной команды — `ConfirmRequiredOut` `{"detail":
ConfirmRequired}`, 409 настроек — `VersionConflictOut` `{"detail": {"code": "version_conflict",
"version"}}`, 422 настроек — стандартная `HTTPValidationError` (`{"detail": [{loc, msg, type}]}`).
Клиент различает 403 CSRF (перечитать `/auth/me` и повторить) и 403 запрета, 503 недоступного
движка и 503 `store_failed` по строке кода.

### Статус движка и Telegram

`EngineFacade` (`app/engine/facade.py`) — фасад над `ActionGateway`, `Pipeline` и `TgAuthManager`:
`status()` отдаёт режим, kill switch, блок трат, статус Telegram, длину очереди, текущее действие,
бэклог и здоровье конвейера, `lock_ok`/`workers_ok` и лаг event loop (`LoopLagMonitor`,
`app/engine/lag.py`, максимум лага за скользящее окно 60с); `ready()` — истина, когда лок и воркеры
в порядке, Telegram в состоянии `ONLINE`, нет kill switch, нет блока трат и конвейер здоров. `GET
/api/v1/engine/status` (сессия) отдаёт этот статус целиком (`EngineStatusOut`), включая паузу
`paused`, текущий сценарий планировщика `scenario` и момент его следующего пробуждения `next_wake`
(через `isoformat()`, с `+00:00`, как в прежнем ответе и как `now` в `/state`, а не `Z`). `POST
/api/v1/engine/pause` и `POST /api/v1/engine/resume` (CSRF) сохраняют `engine.paused`, будят
планировщик и пишут аудит `engine_paused`/`engine_resumed` с логином. Успешные `kill`, `unkill` и `reconciled`
пишут аудит-уведомление уровня `info` (`engine_killed`, `engine_unkilled`, `engine_reconciled`) с
логином того, кто это сделал. `POST /api/v1/engine/kill {reason}` (CSRF) сперва латчит
`ActionGateway` и обрывает очередь, затем сохраняет настройку — если сохранение не удалось, latch
остаётся активным. `POST /api/v1/engine/unkill` (CSRF) — в обратном порядке: сначала сохраняет
настройку, затем снимает latch; если сохранение падает, шлюз остаётся выключенным и исключение
уходит наверх; если single-instance лок потерян — 409 `{"detail": "lock_lost"}`, ни настройка, ни
latch не меняются. `POST /api/v1/engine/reconciled` (CSRF) — явное решение администратора: закрывает
все открытые обязательства сверки и снимает блок трат без проверки свежести состояния (см. «Шлюз
действий»); автоматическое снятие блока после проверки — задача сверщика. `GET
/api/v1/tg/status` (сессия) и `POST /api/v1/tg/login/start {phone}`, `.../login/code {attempt_id,
code}`, `.../login/password {attempt_id, password}`, `POST /api/v1/tg/logout` (все — CSRF)
проксируют `TgAuthManager` и отвечают статусом входа `TgStatusOut` (`state`, `user_id`,
`attempt_id`, `error`); несовпадение попытки входа (`AttemptMismatch`) отдаёт 409. Неверный или
истёкший код и неверный пароль 2FA — это 200 с полем `error` (`invalid_code`, `code_expired`,
`invalid_password`). Прочие ошибки входа — наследники `TgAuthError` с кодом: распознанные (например,
`invalid_phone`) — 400 `{"detail": "<код>"}`, сбой Telegram или сети (`TgBackendError`:
`send_code_failed`, `sign_in_failed`, `check_password_failed`) — 502. Отдельно для `send_code`:
`FloodWait` от Telegram — 429 `{"detail": "flood_wait"}` с заголовком `Retry-After`, прочий
`BadRequest` (кроме `invalid_phone`) — 400 с кодом в нижнем регистре из RPC ID Telegram (например
`phone_number_banned`). Сбой `send_code` переводит статус Telegram в `ERROR` с тем же кодом, сбой
`sign_in`/`check_password` оставляет попытку, чтобы код можно было отправить повторно. `GET
/readyz` (без авторизации) — 200 `{"status":"ready"}`, если движок поднят и `ready()` истинна, иначе
503 `{"status":"not_ready"}`.

### Состояние персонажа

`GET /api/v1/state` (сессия, CSRF не нужен) отдаёт снимок состояния персонажа (`StateOut`):
`{"version": int, "now": ISO-UTC, "state": {...}, "stale": [...]}`. `state` в схеме — публичная
модель `PublicState` (`app/api/state_schema.py`): поля `CharacterState` без `applied`, наблюдаемое
поле — `Observed[T]` `{value, at, src}` или `null`, `schema_version` — число, `prices` — словарь
наблюдений цен, `activity_stats` — словарь средних без оболочки; все поля необязательны (до первого
сообщения `state` — `{}`, в снимке прошлой сборки нет полей, появившихся позже). Снимок отдаётся
как есть, без пересборки моделью (`JSONResponse`): порядок ключей, даты и значения — как в
конвейере, из ключей — только поля `PublicState` (поле снимка прошлой сборки, которого уже нет в
модели, и `applied` наружу не уходят); форма ответа с появлением модели не изменилась — это проверяет тест-снимок
`tests/api/test_response_shapes.py` (как и у `/engine/status` и `/tg/*`), а
`tests/api/test_state_schema.py` сверяет `PublicState` с `CharacterState` поле в поле (новое поле
движка без публичного валит тест) и прогоняет через схему реальный снимок с прода
(`tests/fixtures/api/state.json`). `version` и `state` — из `EngineFacade.state()`
(`Pipeline.version`/`Pipeline.state`), служебное поле редьюсера `applied` (ключи применённых итогов)
в ответ не входит; `stale` — список полей, устаревших по политике свежести
(`stale_fields`, `app/engine/state/model.py`): для «летучих» полей (`money`, `stamina`,
`motivation`, `busy`, `exp`, `knowledge`, `raw`, `details`) — старше `engine.state_stale_after_min`
минут (по умолчанию 15), для «медленных» — старше 6 часов, для таймеров и значений за день заданий
(`team_task`, `daily_personal`) — только если значение `doubtful`, для цен — старше 7 дней
(`prices.<ключ>`). Поле, которое ещё не встречалось на экране
(например `books` до `/inv`), есть в `state` со значением `null` и в `stale` не попадает — это не
устаревшее значение, а ненаблюдавшееся. Без запущенного движка — 503, как `/api/v1/engine/status`.

### Управление настройками

`GET /api/v1/settings` (сессия) отдаёт `{version, values, defaults, schema}`: текущие настройки,
дефолты и JSON Schema модели `Settings` (поля `engine.killed`, `engine.kill_reason`,
`engine.paused` помечены `readOnly` — их меняют только `/engine/kill|unkill|pause|resume` с latch
шлюза, проверкой блокировки экземпляра и аудитом). `PATCH /api/v1/settings` (CSRF) принимает
`{version, changes, confirm_live?}`: `changes` — частичный JSON, секции сливаются, листья (списки,
словари вроде `battle.overrides`) заменяются целиком (`apply_patch`, `app/engine/settings.py`).
`version` — версия, которую видел клиент; если настройки успели измениться — 409
`{"detail": {"code": "version_conflict", "version": <текущая>}}`. Незнакомый или read-only путь и
невалидное значение — 422 в формате ошибок валидации FastAPI (`loc` = `["body", "changes", …путь]`,
`type` = `unknown_field`/`read_only`/`section_expected` или тип ошибки pydantic). Переход
`engine.mode` из `dry_run` в `live` требует `confirm_live: true`, иначе 422 с `loc` `["body",
"confirm_live"]` и `type` `live_requires_confirm`; обратно в `dry_run` подтверждение не нужно.
Ответ — `{version, values, changed, restart_required}`: `version` — версия, под которой сохранено
именно это изменение (её возвращает `SettingsProvider.update`; следующее изменение, успевшее следом,
её не подменяет), `changed` — изменённые листья (`путь → [было, стало]`), `restart_required` — те из них, что читаются только при старте процесса
(`chats.*`, `telegram.*`, `engine.recovered_react_max_age_min`). Любое изменение будит шлюз (стоящие
в очереди действия перепроверяются по новым правилам) и планировщик (смена режима сбрасывает
отложенные подавлением сценарии; идущий запуск доигрывает в режиме своего старта, см. «Политика
шлюза»); смена режима пишет аудит `engine_mode` с логином. `GET
/api/v1/settings/history?limit&before` (сессия, работает и без движка) — версии от новых к старым с
автором, моментом и `changes` относительно предыдущей версии (у первой — относительно дефолтов);
`next_before` — курсор следующей страницы. Версии сравниваются в текущей форме модели
(`Settings.model_validate`): у версии, записанной до появления секции, секция считается со
значениями по умолчанию, а не изменённой.

### Журнал и детали

`GET /api/v1/journal` (сессия, работает и без движка) — общая лента журнала: сообщения (`messages`,
момент — `received_at`), действия (`actions`, `created_at`) и решения планировщика (`decisions`,
`at`) от новых к старым, каждая запись с полем `type` (`message`/`action`/`decision`). На одном
моменте порядок — решение, действие, сообщение (по убыванию), дальше по `id`. Параметры: `types`
(через запятую, по умолчанию все), `since`/`until` (полуинтервал `[since, until)`), `chat_id`
(сообщения и действия; решения при нём не выводятся), `status` и `source` (только действия — с ними
лента сужается до действий), `limit` (1–200, по умолчанию 50) и `cursor`. Курсор непрозрачный
(`[момент, ранг типа, id]` в base64url): следующая страница — записи строго старше последней, без
пропусков и повторов при слиянии трёх таблиц (`DbReads.feed`, `app/db/reads.py`); `next_cursor` —
`null` на последней странице, испорченный курсор — 422. Сообщения в ленте — с текстом, разметкой и
событиями парсера; действия — с текстом или `callback_data`, статусом и причиной; решения — без
кандидатов. Подробности — `GET /api/v1/decisions/{id}` (параметры, кандидаты с оценками и причинами
отказа, запуски сценариев по этому решению), `GET /api/v1/actions/{id}` (полная строка `actions`:
payload, попытки, ответ-тост, деталь совпадения ожидания, моменты отправки, завершения и сверки) и
`GET /api/v1/scenario-runs/{id}` (запуск сценария, `metro_run_id`, если это забег метро, и
`actions` — действия его шагов в порядке создания, как в `/actions/{id}`); чужая или
несуществующая запись — 404. У действия в деталях есть `idempotency_key` (`manual:<ключ>` у ручных
команд) и `scenario_run_id`. Список запусков — `GET
/api/v1/scenario-runs?manual&scenario&before&limit` (сессия): от новых к старым, `manual=true` —
только ручные (с `requested_by`), `manual=false` — только плановые, `scenario` — точное имя,
`limit` 1–100 (по умолчанию 20), следующая страница — `before=next_before`; элементы — как
`ScenarioRunOut` (без действий). Админка берёт из него «Последние ручные запуски».

### Ручные команды

Ручные команды (`app/api/routes_commands.py`, CSRF): `POST /api/v1/commands/send {text,
idempotency_key, confirm_token?}` — текст в игровой чат, `POST /api/v1/commands/click {chat_id,
message_id, revision, callback_data, idempotency_key, confirm_token?}` — нажатие кнопки ревизии
`revision` (шлюз отклонит клик, если последняя правка сообщения другая, `stale_revision`, или кнопки
в ней нет, `stale_button`). Обе идут через шлюз от имени `MANUAL` (приоритет выше сценариев и плана;
во время паузы — по `engine.manual_while_paused`; выключенная механика ручную команду не
отклоняет) и отвечают `{action_id, status, reason, answer}` — итог шлюза (`confirmed`, `refused`,
`suppressed`, `rejected`, `outcome_unknown`) с причиной. Смысл ручной команды движку неизвестен,
поэтому не-`nav` подтверждает первый ответ игры в чате, а отказ игры (`Busy`, `Refused`) — отказ
(`any_reply`, `app/engine/manual.py`); `nav` подтверждается отправкой. Запрос ждёт итога до
`Container.command_wait_s` (30 с); не успел — 202 `{"status": "pending", "action_id": null}`,
действие продолжает исполняться, итог отдаёт повтор с тем же ключом. `idempotency_key` — до 64
символов `[A-Za-z0-9_.:-]`, в `actions` хранится как `manual:<ключ>`; повтор с тем же ключом
возвращает прежний итог (в том числе подавление в `dry_run` — новая попытка требует нового ключа),
тот же ключ с другими параметрами — 422, в том числе пока первое действие ещё в очереди (фасад
держит отпечаток запросов в полёте) и когда оно завершилось между этой проверкой и отправкой
второго (итог, который вернул шлюз, сверяется с действием, сохранённым под ключом). Если ключ не удалось записать (сбой БД), итога нет: шлюз
отвечает `REJECTED "store_failed"`, API — 503 `{"detail": "store_failed"}`, повтор тем же ключом
безопасен. `forbidden`/`donate` — всегда 403 `{"detail":
"forbidden"}`/`{"detail": "donate"}`, попытка пишется в `actions` как `rejected` без ключа. `risky`
требует подтверждения: запрос без `confirm_token` или с негодным токеном (в том числе с не-ASCII
символами) — 409 `{"detail": {"code":
"confirm_required", "reason": "missing"|"invalid"|"expired", "confirm_token", "expires_at",
"state_version", "command_class"}}`; клиент показывает подтверждение и повторяет тот же запрос с
токеном. Токен (`ConfirmTokens`, `app/api/confirm.py`) — HMAC над сессией, ключом
идемпотентности, точными параметрами и версией состояния, живёт 120 с, секрет — на процесс: изменилось
состояние персонажа, параметры или сессия — нужен новый токен. Версия и срок токена уходят в шлюз
(`ActionRequest.confirm_version`/`confirm_until`), и он сверяет их с текущей версией состояния перед
каждой попыткой отправки: изменилось, пока действие ждало в очереди, или срок вышел — `REJECTED
"confirm_stale"`, команда не уходит. Повтор уже исполненного или ещё исполняемого ключа
подтверждения не требует.

### Ручной запуск сценариев

Ручной запуск сценария: `GET /api/v1/scenarios` (сессия) — каталог реестра `{name, certified,
params, required}`: `params` — параметры, зафиксированные реестром, `required` — обязательные
параметры `{имя: ParamSpec}`, где `ParamSpec` — `{type: "enum"|"int"|"string", values?, min?, max?,
pattern?}` (отсутствующие ключи не выводятся; `pattern` — в синтаксисе ECMA-262, проверка на сервере
остаётся прежним предикатом реестра, `registry.Param`); `POST /api/v1/scenarios/{name}/run {params, idempotency_key}` (CSRF) — 202
`{scenario_run_id, status: "queued"}`, неизвестный сценарий — 404, больше 16 параметров — 422.
Запуск ставится в очередь цикла планировщика (`PlannerLoop.request`, строка `scenario_runs` со
статусом `queued`, `requested_by` и ключом) и исполняется перед его следующим решением — после
текущего сценария планировщика, если тот идёт (у метро это может быть долго); при выключенном
`PYROBOT_PLANNER` цикл исполняет только такие запуски. Параметры реестра (`activity` дела, `item`
предмета) переопределить нельзя: присланный параметр, противоречащий им, — 422 `fixed params:
<ключи>`, совпадающий или отсутствующий — дополняется из реестра. У `lottery_buy` недостающие
билеты, запасы и резерв 💵 на старте запуска берутся из настроек и резервов, как у планировщика.
Обязательные параметры
(`ScenarioSpec.required`, `app/engine/scenarios/registry.py`: `refresh` — `source` из источников
сверки, `fastfood` — `food`, `sleep` — `hours` 7–12, `battle_target` — `target` из целей настроек,
`stocks_dump` — `keep` и `margin`, `bulls_join` — `code` приглашения, `tangerine` — `chat` и
`reply_to`, `smoothie` — `recipe` из пяти фруктов, `daily_pick` — `task` вида `<тип>_<сложность>`) у решений планировщика есть всегда, а ручной
запуск без них или с недопустимым значением — 422 `invalid params: <ключи>`, в очередь он не
попадает. Шаги идут через шлюз от имени
`MANUAL` (пауза — по `manual_while_paused`), несертифицированный сценарий исполняется как
`simulate` (не-`nav` шаги подавляются `uncertified`), режим запуска фиксируется на его старте (см.
«Политика шлюза»). Итог учитывается планировщиком
как свой (кулдауны, последний успешный запуск — мандарин вручную не повторится через час), кроме
подавленного: ручная симуляция не откладывает рекомендацию планировщика. Повтор с тем же ключом —
200 с текущим статусом того же запуска, тот же ключ с другим сценарием или параметрами — 422
(сравниваются присланные параметры до слияния с реестром — `scenario_runs.requested_params`).
Статус — `GET /api/v1/scenario-runs/{id}` (`queued` → `running` → итог сценария); при рестарте
незавершённые запуски закрываются (`close_running`): начатые — `interrupted`, так и не начатые из
очереди — `cancelled`, обе с причиной `restart`. Сбой ручного запуска не роняет цикл планировщика:
запуск закрывается итогом сценария, даже если упал учёт итога (кулдауны, уведомление о неудаче), а
если не удалось отметить его начало, он закрывается как `failed` с причиной `store_failed`.

### Справочные эндпоинты

Справочное (`app/api/routes_reference.py`, сессия, работает и без движка): `GET
/api/v1/metrics?from&to&fields&limit&cursor` — временной ряд `metrics` в окне `[from, to)` (по
умолчанию последние 24 часа) по ключам `fields` через запятую (по умолчанию все из
`METRIC_FIELDS`, незнакомый — 422): `{series: {ключ: [[момент, значение], …]}, initial, next_cursor}`.
Метрика пишется только при изменении значения, поэтому `initial` — последнее значение каждого ключа
до начала окна (для ступенчатого графика; только на первой странице). Объём ограничен: не больше
`limit` точек (по умолчанию 2000, максимум 5000) на страницу, продолжение — по `next_cursor`. `GET
/api/v1/metro/runs?before&limit` — забеги метро от новых к старым без тяжёлых полей (карта, путь,
события, 🔋 по шагам), `GET /api/v1/metro/runs/{id}` — забег целиком. `GET
/api/v1/unrecognized?acked=false|true|all&before&limit` — нераспознанные сообщения с полным текстом
из журнала, `POST /api/v1/unrecognized/ack {ids}` (CSRF, до 500 id) — отметить разобранными,
отвечает числом отмеченных. `GET /api/v1/notifications?unread&level&before&limit` — уведомления
от новых к старым и общее число непрочитанных `unread`, `POST /api/v1/notifications/read {up_to_id}`
(CSRF) — прочитаны все до этого id включительно. Страницы по `id` — через `next_before`.

### Поток событий (SSE)

`GET /api/v1/events` (сессия) — поток SSE (`text/event-stream`) из `EventStream`
(`app/engine/stream.py`). Каждое событие — `id: <эпоха процесса>:<номер>` (эпоха — момент старта в
мс), `event: <тип>`, `data: <JSON>`. Типы: `message` (каждая запись журнала: `journal_id`,
`chat_id`, `msg_id`, `revision`, вид, дата, текст, события парсера и кнопки `markup` в той же форме,
что у элемента `/journal`, — по ним админка кликает из живой ленты), `state` (`version` и `changed` — изменившиеся поля
состояния, как в `GET /state`, без служебного `applied`), `action` (создание строки `actions` —
статус, источник, текст или `callback_data`, класс; каждый следующий переход — `{id, status,
reason}`), `decision` (решение планировщика без кандидатов), `scenario_run` (`queued`, `running`,
итог), `notification` (`{id, level, code, text}`), `settings` (новая версия настроек с `mode`,
`paused`, `killed`). Источники подключены без изменения движка: подписчик шины `StreamFeed`
(сообщения и состояние, после планировщика), обёртки `PublishingActionStore` и
`PublishingPlannerStore` над хранилищами шлюза и планировщика, слушатели `DbNotifier.listeners` и
`DbSettingsStore.listeners`. Новое подключение и неизвестный, вытесненный или прошлого процесса
`Last-Event-ID` начинаются с события `reset` (`reason`: `new`, `unknown`, `evicted`, `epoch`; `id` —
позиция потока на момент подписки): клиент заново берёт `/state` и нужные списки. Известный
`Last-Event-ID` — досылаются пропущенные события из кольцевой истории (последние 1000; после
досылки подписка их не держит). Публикация
синхронная и никого не ждёт: у подписчика очередь на 256 событий, переполнилась — подписчик снят с
потока, дочитывает накопленное, и соединение закрывается (браузер переподключится с
`Last-Event-ID`); игровой конвейер от медленного клиента не тормозит. Сессия перепроверяется по
часам раз в `Container.sse_heartbeat_s` (15 с) — в тишине, при непрерывном потоке событий и во
время досылки истории; после выхода или смены пароля поток закрывается. Перепроверка только
проверяет сессию (`AuthRepo.resolve(token, slide=False)`) и не продлевает её: открытая вкладка сама
по себе не держит сессию живой. В тишине раз в тот же
интервал уходит комментарий `: ping`. Заголовки `Cache-Control:
no-cache` и `X-Accel-Buffering: no` отключают буферизацию на прокси.

### Отдача админки

Собранную админку (SPA на SvelteKit, `admin/build`) отдаёт то же приложение с того же домена
(`app/api/admin_static.py`, `install_admin` в конце `create_api`): каталог — `PYROBOT_ADMIN_DIR`
(по умолчанию `/app/admin`, в образе туда кладётся сборка); нет каталога или `index.html` —
маршрут не подключается и `/` отвечает 404. Маршрут один и последний (`/{path:path}`, в OpenAPI не
входит), только `GET`/`HEAD`: существующий файл каталога — файл, отсутствующий файл с расширением
(`/_app/immutable/x.js`, `/robots.txt`) — 404 `{"detail": "Not Found"}`, путь без расширения
(навигация SPA: `/journal`, `/metro/1`) — `index.html`. Выход за каталог (`..`) — 404. Пути `/api`,
`/api/…`, `/healthz`, `/readyz` маршрут не обслуживает (`_AdminRoute.matches` для них не
совпадает): неизвестный путь API — прежний 404 JSON, чужой метод известного пути — прежний 405;
изменяющие методы на путях SPA — прежний 404. Кеш: `_app/immutable/*` (имена с хешем содержимого) —
`Cache-Control: public, max-age=31536000, immutable`, `index.html` и прочие файлы — `no-cache`
(браузер перепроверяет по `ETag`/`Last-Modified`). Заголовки на всех ответах админки:
`Content-Security-Policy`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`. CSP
считается при старте по собранному `index.html` (он читается один раз и отдаётся ровно он):
`default-src 'self'; script-src 'self' 'sha256-…'; img-src 'self' data:; style-src 'self'
'unsafe-inline'; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'`,
где `sha256-…` — хеш содержимого каждого встроенного `<script>` без `src` (стартовый скрипт
SvelteKit). Тесты — `tests/api/test_admin_static.py` на временном каталоге и на стартовой странице
настоящей сборки (`tests/fixtures/admin/index.html`).

Веб-админка владельца бота (`admin/`): SvelteKit 2 SPA (`@sveltejs/adapter-static`, `fallback:


Типы API генерируются `openapi-typescript` из `openapi.json` в корне (его выгружает `uv run python
tools/openapi.py`): поменяли API — перевыгрузить схему и `npm run gen:api`, закоммитить оба файла;
CI сверяет, что `schema.d.ts` актуален. Сборка в Docker берёт закоммиченный `schema.d.ts`.
Локально собранную админку отдаёт и dev-сервер бэкенда: `PYROBOT_ADMIN_DIR=admin/build`.

### Устройство

- `src/lib/api/` — клиент `openapi-fetch` (`createApi`): базовый адрес — одно место (`API_ORIGIN`,
  тот же origin), `credentials: 'same-origin'`; на изменяющие запросы middleware ставит
  `X-CSRF-Token`; 401 (кроме входа и `/auth/me`) — сброс сессии и переход на `/login`; 403 `csrf
  token mismatch` — перечитать `/auth/me` и повторить запрос один раз (копия запроса снимается до
  отправки). Ошибки приводятся к одному виду (`normalizeError`, `errors.ts`) по реальным оболочкам:
  строковый `detail`, `{"detail": {"code": "confirm_required", …}}`, `{"detail": {"code":
  "version_conflict", "version"}}`, список ошибок валидации 422; 403 CSRF отличается от 403
  `forbidden`/`donate`, 503 недоступного движка — от 503 `store_failed`, 429 несёт `Retry-After`.
- Сессия (`stores/session.svelte.ts`): cookie `pyrobot_session` httpOnly ставит сервер, CSRF-токен
  живёт только в памяти вкладки (не в `localStorage`/URL), после перезагрузки его отдаёт `GET
  /auth/me`; очищается после выхода, 401 и смены пароля. Выход считается выполненным только при
  204 (или 401 — сессии и так нет): при сбое сети или 403 сессия и токен остаются, окно «Выход не
  выполнен» предлагает повторить (после 403 токен перечитан).
- Поток событий (`live/`): один `EventSource('/api/v1/events')` на вкладку; кадры разбираются в
  дискриминированные типы (`decodeEvent`: `message`, `state`, `action` — создание или обновление,
  `decision`, `scenario_run`, `notification`, `settings`, `reset`), незнакомые и битые кадры
  отбрасываются. Сетевой обрыв браузер переподключает сам (с `Last-Event-ID`); закрытый поток —
  `GET /auth/me`: 401 — выход на `/login`, иначе «нет связи» и новое соединение с растущей паузой
  1 → 30 с. Индикатор связи: зелёный / переподключение / нет связи. На `reset` каждый потребитель
  перечитывает своё.
- Общие компоненты: окно (`Modal` — фокус внутри, Tab по кругу, Esc закрывает, фон на время
  окна — `inert`, кроме всплывающих сообщений), окно подтверждения (`dialogs.confirm`/`prompt`),
  всплывающие сообщения (`toasts`).
- Внешний текст (сообщения игры, уведомления, подписи кнопок, ошибки) выводится только текстом
  Svelte с `white-space: pre-wrap` (`.ext-text`); `{@html}` и присваивание `innerHTML` запрещены —
  это проверяет тест `src/lib/no-html.test.ts`.

## Образ и деплой

### Образ

**Образ** (`Dockerfile`, многостадийный): стадия сборки — `ghcr.io/astral-sh/uv` с Python 3.13 и
компилятором (tgcrypto собирается из исходников), `uv sync --frozen --no-dev` строго по `uv.lock`
(индекс пакетов — devpi хоумлаба из `pyproject.toml`); рантайм — `python:3.13-slim-trixie` без uv и
компилятора, только venv, `app/` и `alembic.ini`. Процесс работает от непривилегированного
пользователя `pyrobot` (uid/gid 10001); том `/data` (`PYROBOT_DATA_DIR`) — сессия Telegram,
принадлежит ему же. `HEALTHCHECK` — `python -m app.healthcheck /healthz` (`app/healthcheck.py`,
код выхода 0 при ответе 200; тем же модулем деплой ждёт `/readyz`), команда по умолчанию — `python -m
app`, миграции — `alembic upgrade head` в том же образе. Локальная сборка (прокси apt хоумлаба —
необязательный `APT_PROXY`):

```bash
docker build --build-arg APT_PROXY=http://10.10.40.23:3142 -t pyrobot:local .
```

### Compose на apps

**Compose на apps** (`compose.yml`, каталог `/home/fenicu/pyrobot` на 10.10.40.20, рядом `.env`):
`pyrobot` — бот из образа `PYROBOT_IMAGE` (по умолчанию `git.fenicu.com/fenicu/pyrobot:latest`,
деплой подставляет тег), том `pyrobot-data` → `/data` (сессия Telegram), порт
`${PYROBOT_BIND:-10.10.40.20}:${PYROBOT_PORT:-8089}` → 8080 (только адрес apps в VLAN — к нему ходит
Caddy с web; 8080–8088 и 8090 на apps заняты другими сервисами), `PYROBOT_FORWARDED_ALLOW_IPS` по
умолчанию `10.10.40.3`, `restart: unless-stopped`, ротация логов 5×10 МБ, лимит памяти `mem_limit:
1g` (предохранитель: при утечке OOM убивает бота, а не соседей по apps, и `restart` поднимает его
заново); `migrate` — тот же образ, профиль `migrate`, `alembic upgrade head`, запускается только
явно (`docker compose run --rm migrate`);
`postgres` — `postgres:17`, том `pgdata`, healthcheck `pg_isready`; `backup` — `pg_dump
--format=custom` при старте и дальше раз в сутки в
`${PYROBOT_BACKUP_DIR:-./backups}/pyrobot-<дата>.dump`, файлы старше 14 дней удаляются. Дампы
пишутся с `umask 077` — `0600`, владелец root контейнера `backup` (в дампе хэши паролей и
CSRF-токены сессий админки); читать и восстанавливать — из этого же контейнера, у него есть том и
параметры подключения: при остановленном боте (`docker compose stop pyrobot`) `docker compose exec
backup pg_restore --clean --if-exists --dbname pyrobot /backups/pyrobot-<дата>.dump`.
`PYROBOT_DATABASE_URL` собирается в compose из `POSTGRES_PASSWORD` (пароль — без символов,
требующих URL-экранирования, например hex), остальное — из `.env`.
Проверка локально:

```bash
docker compose -f compose.yml config          # нужен .env рядом (см. .env.example, POSTGRES_PASSWORD обязателен)
```

### CI/CD

**CI/CD** (`.forgejo/workflows/ci.yml`, Forgejo Actions): на каждый push — `lint` (ruff, mypy) и
`test` (pytest с сервисом Postgres) в контейнере uv, затем `image` на хостовом раннере
(`self-hosted`) собирает образ — поломка `Dockerfile` видна сразу. Сборка — `docker buildx build`
своим builder'ом `builder-pyrobot` (драйвер `docker-container`: BuildKit независимо от настроек
демона; без `--use`, чтобы не переключать общий builder хоста), `--platform linux/amd64
--provenance=false`, как у соседних проектов. Без тега результат остаётся только в кэше builder'а
(`--output type=cacheonly`); по тегу `vX.Y.Z` тот же вызов с `--push` публикует образ в registry
Forgejo как `git.fenicu.com/fenicu/pyrobot:<тег>` и `:latest` (тег другого вида — ошибка), локальных
образов на раннере не остаётся. `deploy` выкатывает его на apps: пишет `.env` из секретов,
копирует по ssh `compose.yml` и `deploy/remote-deploy.sh` в `~/pyrobot` и запускает скрипт —
`docker compose pull pyrobot` → `docker compose run --rm migrate` (ошибка миграции останавливает
выкат, старый бот работает дальше) → `docker compose up -d --remove-orphans` → ожидание `/readyz`
до 5 минут (`python -m app.healthcheck /readyz` внутри контейнера), не дождался — вывод `docker
compose ps` и хвоста логов, job красный. Выкаты не идут параллельно (`concurrency:
deploy-pyrobot`). apps должен быть залогинен в `git.fenicu.com` (как для остальных сервисов на
apps).

Каждый выкат перезаписывает `~/pyrobot/.env` на apps целиком: ручная правка там живёт только до
следующего выката. Постоянное значение — секрет или переменная репозитория плюс строка в шаге
`deploy` в `ci.yml` (переменная в `env` шага и её имя в вызове `render-env.sh`).

Секреты репозитория (`secrets.*`):

| Секрет | Назначение |
|---|---|
| `GITEA_TOKEN` | Клонирование исходников в контейнерных job (`lint`, `test`). |
| `REGISTRY_USER`, `REGISTRY_TOKEN` | Вход в registry `git.fenicu.com` для публикации образа. |
| `DEPLOY_SSH_KEY` | Приватный ключ деплоя на apps (`fenicu@10.10.40.20`; по спеке — ключ `~/.ssh/forgejo-deploy-apps`), как у остальных сервисов на apps. |
| `PYROBOT_DB_PASSWORD` | Пароль Postgres на apps (`POSTGRES_PASSWORD`, hex — без URL-экранирования). |
| `PYROBOT_TG_API_ID`, `PYROBOT_TG_API_HASH` | Telegram API (my.telegram.org). |
| `PYROBOT_ADMIN_PASSWORD` | Пароль первого админа (нужен только первому старту; дальше пароль меняется через `POST /api/v1/auth/password`). |

Переменная репозитория `PYROBOT_SKIP_READY` (`vars.*`, по умолчанию не задана): `true` — выкат ждёт
только `/healthz`. Нужна на первый выкат: `/readyz` отдаёт 200 только при Telegram `ONLINE`, а вход в
Telegram делается через API уже работающего сервиса (см. «Первый вход»); после входа переменную
убрать. С включённым
kill switch или блоком трат `/readyz` тоже 503 — выкат будет красным, пока их не снять.

### Caddy на web

**Caddy на web** — `deploy/Caddyfile.sw.fenicu.com`: блок `sw.fenicu.com` → `http://10.10.40.20:8089`
без Authelia (у админки своя авторизация), `flush_interval -1` для SSE, тело запроса не больше 1 МБ
(`request_body { max_size 1MB }`: запросы API — килобайты, большее тело Caddy отклоняет, не
передавая боту), `/healthz` и `/readyz` — 404 от самого Caddy (состояние сервиса наружу не
раскрывается; деплой и `HEALTHCHECK` проверяют их изнутри контейнера); добавляется в
`/home/fenicu/caddy/Caddyfile` на 10.10.40.3, проверка `caddy validate` и перезапуск контейнера
`caddy`. Caddy сам ставит `X-Forwarded-For` с адресом клиента, бот доверяет ему только от
`10.10.40.3` (`PYROBOT_FORWARDED_ALLOW_IPS`).

`.env` деплой пишет скриптом `deploy/render-env.sh` из переменных окружения шага: каждое значение —
в литеральной форме Compose (`ИМЯ='значение'`, одинарная кавычка внутри — `\'`), поэтому `$` в
паролях не интерполируется; значения с обратным слэшем перед кавычкой или в конце и с переводом
строки Compose так прочитать не может — скрипт их отклоняет (выкат падает, значение не печатается).
Проверка — `tests/test_render_env.py` (круг через `docker compose config` с настоящим `compose.yml`).

### Первый вход

**Первый вход** (админки ещё нет) — `tools/login.py`, интерактивно по API сервиса:

```bash
uv run python tools/login.py https://sw.fenicu.com   # или http://10.10.40.20:8089 внутри сети
```

Скрипт спрашивает логин и пароль админа (`PYROBOT_ADMIN_LOGIN`/`PYROBOT_ADMIN_PASSWORD`), входит
(`POST /api/v1/auth/login` → cookie сессии и CSRF-токен — только в памяти процесса, cookie
передаётся заголовком), проверяет `GET /api/v1/tg/status` и, если Telegram не `online`, ведёт вход:
телефон → `tg/login/start`, код из Telegram → `tg/login/code` (до 3 попыток), при 2FA пароль →
`tg/login/password` (до 3 попыток). Коды и пароли вводятся без эха и нигде не печатаются. В конце
`user_id` аккаунта сверяется с `telegram.expected_user_id` из `GET /api/v1/settings` (сервис и сам
выходит из чужого аккаунта с ошибкой `unexpected_user`), сессия админа закрывается
(`auth/logout`); ошибка — код выхода 1 и причина без секретов: ответ не в JSON (страница ошибки
прокси) — только метод, путь и HTTP-код без тела, из ошибок сервиса печатается только строковый
`detail` (ошибка валидации повторила бы присланные значения), сбой закрытия сессии после ошибки не
подменяет её первопричину. Тесты —
`tests/api/test_login_tool.py` (ASGI-приложение с fake-транспортом: неверный код и пароль 2FA,
уже `online`, чужой аккаунт, неверный пароль админа).

Первый выкат: завести секреты и `PYROBOT_SKIP_READY=true` → тег `vX.Y.Z` (выкат ждёт только
`/healthz`) → добавить блок в Caddy → `tools/login.py` (вход админа и в Telegram) → проверить `GET
/readyz` = 200 изнутри (через Caddy он закрыт): `http://10.10.40.20:8089/readyz` из VLAN или
`docker compose exec pyrobot python -m app.healthcheck /readyz` на apps → убрать
`PYROBOT_SKIP_READY` (следующие выкаты ждут `/readyz`). Режим после выката —
`dry_run` (дефолт настроек), переход в `live` — отдельным решением (спека, «Катовер»).
