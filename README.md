# pyrobot

Userbot для автоматической игры в StartupWars (@StartupWarsBot). Боты в игре официально разрешены.

Один процесс: kurigram (MTProto) + движок + FastAPI в одном asyncio-цикле, Postgres.
Админка (Svelte) — отдельный проект поверх API этого сервиса.

## Разработка

```bash
uv sync
docker compose -f compose.dev.yml up -d   # Postgres для тестов
uv run pytest -q
uv run ruff check . && uv run ruff format --check .
uv run mypy
```

## Конфигурация

Все параметры загружаются через переменные окружения с префиксом `PYROBOT_`. Пример: `cp .env.example .env && vi .env`.

| Переменная | Назначение |
|---|---|
| `PYROBOT_DATABASE_URL` | Connection string к PostgreSQL (по умолчанию localhost:55432). |
| `PYROBOT_DATA_DIR` | Путь к директории для хранения игровых данных. |
| `PYROBOT_TG_API_ID` | Telegram API ID (из my.telegram.org). При `PYROBOT_TRANSPORT=kurigram` обязателен и больше 0, иначе процесс не стартует (ошибка валидации конфигурации). |
| `PYROBOT_TG_API_HASH` | Telegram API hash (из my.telegram.org). При `PYROBOT_TRANSPORT=kurigram` обязателен и не пуст. |
| `PYROBOT_ADMIN_LOGIN` | Логин для доступа в админку. |
| `PYROBOT_ADMIN_PASSWORD` | Пароль для админки (если не задан, доступ отключён). |
| `PYROBOT_COOKIE_SECURE` | Использовать флаг Secure для cookies (true в боевой, false в локальной разработке). |
| `PYROBOT_TRANSPORT` | Транспорт Telegram: `kurigram` (боевой MTProto) или `fake` (для тестов). |
| `PYROBOT_LOG_LEVEL` | Уровень логирования (DEBUG, INFO, WARNING, ERROR). Логгер `pyrogram` никогда не опускается ниже INFO: в DEBUG kurigram печатает код входа в Telegram. |
| `PYROBOT_HTTP_HOST` | IP для привязки HTTP сервера. |
| `PYROBOT_HTTP_PORT` | Порт для HTTP API. |
| `PYROBOT_ACCOUNT_ID` | Внутренний `accounts.id` в базе pyrobot (по умолчанию 1), не ID игрока в игре. |
| `PYROBOT_PLANNER` | Запускать планировщик (по умолчанию `true`); `false` — движок только принимает сообщения и выполняет ручные команды. |

## База данных

Postgres для разработки и тестов поднимается через `compose.dev.yml`:

```bash
docker compose -f compose.dev.yml up -d
```

Контейнер слушает `127.0.0.1:55432` и создаёт три базы: `pyrobot` (основная база для разработки),
`pyrobot_test` (юнит- и интеграционные тесты, фикстуры `db`/`clean_db`) и `pyrobot_migtest`
(тест миграций `tests/db/test_migrations.py`). Список тестовых баз задаётся в
`docker/initdb/10-test-dbs.sql`, который накатывается только при первой инициализации volume.

Схема версионируется через Alembic (`app/db/migrations`). Применить миграции:

```bash
uv run alembic upgrade head
```

Новую миграцию генерировать через `uv run alembic revision --autogenerate -m "..."`. Alembic читает
только `PYROBOT_DATABASE_URL` (`DbConfig`), Telegram-параметры для миграций не нужны.

Миграция `0002` добавляет таблицы `metrics` (временной ряд ключевых полей состояния — `money`,
`level`, `stamina` и т.д., строка пишется только при изменении значения, момент — `msg.date`) и
`unrecognized` (нераспознанные сообщения игрового чата, `first_line` для быстрого просмотра, флаг
`acked` для разбора). Обе таблицы пишутся в той же транзакции, что и запись сообщения в журнал
(`JournalStore.append`), поэтому не могут разойтись с журналом.

Миграция `0004` добавляет `decisions` (журнал решений планировщика: момент, `act`/`wait`, сценарий и
параметры, причина, `until` ожидания, кандидаты с оценками и причинами отказа) и `scenario_runs`
(запуски сценариев: решение, параметры, начало и конец, итог и его причина).

Миграция `0005` добавляет `metro_runs` (забеги метро, `DbMetroRunStore`, `app/db/metro.py`): запуск
сценария, начало и конец, статус и исход (`finished`, `paused`, `timeout`, `unexpected_screen`, …),
шаги, длительность, время шага, купленные бафы, итог «Получено», карта (клетки и посещённые), путь,
события с координатами, 🔋 и аптечки по шагам и сводка (выход, причина ухода к выходу, сигналы,
жетоны, id сообщения забега).

Пул соединений (`app/db/base.py`) задаёт asyncpg `command_timeout=30` — ни один запрос не висит
дольше 30 секунд; проверка single-instance лока (`SingleInstanceLock.check`) ограничена 5 секундами,
таймаут считается потерей лока.

## Фикстуры

Тесты парсеров игровых сообщений используют реальные записи из `~/pyrobot-research` (выгрузка истории
игровой переписки, собранная прототипами парсеров). Загрузчик фикстур (`tests.fixtures.game()`,
`tests.fixtures.game_msg()`) читает из `tests/fixtures/game/*.jsonl` — JSONL-файлы по семействам
сообщений (profile, battle, activities, и т.д.). Переменная окружения `PYROBOT_RESEARCH` переопределяет
путь к выгрузке (по умолчанию `~/pyrobot-research`).

Добавить новые фикстуры:

```bash
uv run python tools/fixtures.py <семейство> <id> [<id> ...]
```

Команда извлекает сообщения из выгрузки в `tests/fixtures/game/<семейство>.jsonl`, дедублирует и
сортирует по id. По умолчанию берутся входящие сообщения игрового чата; `--chat <id>` — другой чат
(SWINFO в общем чате, канал смузи), `--include-out` — и исходящие (единственный образец инвайта
биржевиков — пересылка самого игрока), `--versions` — каждая правка сообщения из живой записи
отдельной строкой (экран варки смузи меняется после каждого фрукта; `game_versions(семейство, id)`
отдаёт их по порядку, `game()` — последнюю). Правки одной секунды `edit_date` с разным содержимым —
разные версии: вторая и следующие получают порядковый номер `seq` (экран метро правится чаще раза в
секунду: «Идёшь Вниз.» и новое окно). Отправитель сохраняется в поле `from`: разбор SWINFO
пропускает только сообщения пользователя SWINFO. Ожидаемые значения в тестах парсеров берутся
из прогона прототипов на этих же сообщениях; если значение в тесте расходится с текстом
фикстуры, истина — текст фикстуры.

## Парсеры

Входящие сообщения разбирают распознаватели — чистые функции `IncomingMessage → list[Event]` без
I/O, по модулю на семейство в `app/engine/parsing/`. `default_parser(chats)` — маршрутизатор по
чату (`ChatRouter`): у игрового чата свои распознаватели, у общего чата — разбор SWINFO (только
сообщения пользователя SWINFO), у канала смузи — рецепт, у чата инвайтов биржевиков (если задан) —
инвайт; сообщения прочих чатов событий не дают. Семейства игрового чата:

- `profile` — компакт-профиль (`😎Я`, `◀️Назад`): уровень, 💡, 💵, 🔋, 🔥 и таймер её прироста,
  📚 🔩 ⚙️, рюкзак, 🍊, навыки 🔨🎓🐿🐢, «Битва через», цель взлома, «🛌 Через» и текущее занятие
  с остатком (включая сон под мостом или в отеле);
- `battle` — ответ на выбор цели битвы или защиты («Ты решил взломать …», «Ты встал на защиту …»);
  если точка в конце названия компании (⚡️Stark Ind., 🎩Wayne Ent.) слилась с точкой предложения,
  название восстанавливается по списку компаний;
- `activities` — старт и итог дел (добыча, работа, учёба, еда, переработка ⚙️→🔩), отмена дела,
  «🔥Мотивация полностью восстановлена», бонус «🧲Магнит» и экраны цен: ⏳Дела, 🔮Стартап,
  🛠Мастерская, 🔧Профа;
- `refusals` — «❗️Ты занят другим делом ещё …» и отказы игры (нет 🔥, нет 💵, скоро битва,
  кулдауны карты, фастфуда и призовой коробки, нужен level-up и т. п.);
- `sleep` — предупреждение о скором принудительном сне, засыпание (под мостом, в отеле,
  принудительно), меню сна (цена отеля), шаг выбора места после выбора часов (`SleepPlace`: часы и
  цена; кнопки `sleep_Bridge` / `sleep_Hotel`), ответы «Ты потратился на отель…» / «Ты решил не
  тратиться на отель…» (в состояние не идут), пробуждение и драка с грабителем;
- `food` — меню 🍴 (запасы фастфуда, диапазоны 🔋, кулдаун) и съеденный фастфуд;
- `items` — рюкзак (`/inv`: 📒 книги и 💳 карты с таймерами кулдауна «(38 мин.)», 🎁 призовая
  коробка, занятые слоты; строк 📒 и 💳 при нуле игра не выводит — отсутствующая строка считается
  нулём), прочитанная 📒 книга, использованная 💳 карта, экран 🎁 подарков, открытые контейнеры и
  призовая коробка;
- `gorbushka` — экраны 🏛Горбушки (нужен билет, встреча с продаваном, ожидание, все одолены),
  бой с продаваном и уведомления;
- `levelup` — шаги повышения уровня;
- `crew` — экран команды (тег команды, `⚔Побед на фабрике`, открыта ли запись на фабрику), экран битвы за
  фабрику (записан, не записан, запись закрыта), ответы на запись (записан, уже записан, команда
  выиграла прошлую битву и пропускает эту) и личный итог прошлой битвы за фабрику (`/fb`);
- `bulls` — присоединение к бою с биржевиками, итог боя с наградами, отказы (уже побеждал этой
  ночью, битва закончилась, битвы нет); инвайт `join_fight_<11 символов>` — из чата инвайтов по
  кнопке;
- `stocks` — экраны биржи (главный, покупка, продажа: котировки, акции у игрока, 💵, часы работы,
  лимиты «дешевле N нельзя купить», «дороже N нельзя продать», остаток после покупки), итоги покупки
  и продажи (кнопкой «на все» и командой `/buys_<код>_<N>`, `/sells_<код>_<N>` — у команды, пока
  лимит не исчерпан, есть строка «можешь купить/продать от … до …») и дивиденды;
- `smoothie` — экран Смузийной (остатки ингредиентов, текущий бонус — признак, что сегодня уже
  варили), экран варки «🍹Готовлю» (что уже вброшено; отмена), приготовленный смузи (с бонусом или
  «не очень» — неверный рецепт, без бонуса); рецепт из канала — отдельным распознавателем;
- `tangerine` — ответы на `/gt`: адресат не играет, кулдаун с остатком;
- `metro` — одно сообщение на весь забег, которое игра правит: вход «Ты у входа…» (цена в 🔥 и
  мотивация), отказ по кулдауну «До следующего спуска …» (`Refused metro_cooldown`), экран бафов
  (купленные бафы, бафы за 🕳 по кнопкам, жетоны; вместе с ним — итог `metro_entered`: списание
  цены входа), кадр карты (окно 5×5 символами `#` стена, `.` проход, `@` игрок, `E` выход, `?`
  незнакомый символ; 🔋 — бывает выше 100%, аптечки с кнопки `❤️N`, подпись: `entry` «Вход»,
  `going` «Идёшь …» — окно ещё старое, `arrived` «Вниз» и т. п. — единственная подпись хода; на той
  же клетке: `waiting` «Ждёшь» после события, `stayed` «Остался» после отказа выйти,
  `npc_declined` «Не бьёшся», `chest_declined` «Не открываешь», `wall` «Стена» — ход в стену не
  состоялся, `none` после аптечки), лут «Нашёл +N…», слабый и сильный NPC (сильный — только по
  кнопкам `maze_npc_high_*`, живьём не встречен), итог боя, сундук и его исходы (тайник, стрела,
  граната; незнакомый исход не распознаётся), запрос аптечки, найденный выход с «Найдено»,
  досрочный выход кнопкой 🚪 с карты (`MetroEarlyExit`: «Найдено» и «Получишь половину» — с
  округлением вверх) и итог «Получено … Осталось выносливости». Кадр с незнакомой подписью или
  окном не 5×5 не распознаётся. Фикстуры — все правки двух живых забегов (533 и 399 версий);
- `screens` — меню битвы (время следующей битвы), отчёт прошедшей битвы по запросу, первое место в
  рейтинге работников недели, экраны лотереи, ответы, меняющие ресурсы (обмен символа года,
  подарок за 🍊, итог акулы — в формате наград; выигрыш лотереи — ресурсы, 🔥, контейнеры,
  временный навык; утрата лотерейного навыка с компенсацией; экран покупки эфира с остатком 💵),
  донатное мгновенное завершение дела и справочные экраны, которые движку не нужны, но не должны
  считаться нераспознанными (петы, рынок, рейтинги, вирусы, офис, казино, бонусы, `/full` и т. п.).

SWINFO (`swinfo`): анонс записи на фабрику, итог битвы за фабрику (тег победившей команды), сводка
битвы компаний (цена акций каждой компании после битвы), посты лотереи, дневной рейтинг компаний.
Чат инвайтов биржевиков может совпадать с общим чатом: маршруты чата работают независимо, фильтр
транспорта пропускает и сообщения SWINFO, и сообщения с кнопкой `join_fight_*`.

Антифлуд («Ты шлёшь запросы к боту слишком часто») распознаётся всегда, отдельно от семейств.

Итоговые события — старт дела, награды, траты, засыпание, пробуждение, прочитанная книга и т. п. —
помечены признаком `Event.outcome`: редьюсер применяет их к состоянию один раз на
`(чат, сообщение, вид события)`, даже если игра потом правит сообщение. Экраны выдаются только
целиком: частично разобранный экран не даёт событий, чтобы не затереть известное состояние.
Целостность определяется якорями экрана (у рюкзака — заголовок и «Занято N из M»), а не строками,
которые игра при нуле не показывает. Если в игровом чате ни один распознаватель не сработал,
появляется `Unrecognized` с первой строкой текста.

Всплеск нераспознанного (≥5 сообщений за 10 мин) отправляет уведомление уровня `warn` с кодом `unrecognized_spike` и молчит до конца окна; сами нераспознанные сообщения записываются в таблицу `unrecognized`.

Проверка:

1. модульные тесты на реальных сообщениях из фикстур: `uv run pytest tests/engine/parsing -q`;
2. доля распознанных входящих сообщений игры по корпусу: `uv run pytest -m corpus -s`
   (нужен `~/pyrobot-research`); порог — 0.999.

## Состояние

`app/engine/state` строит состояние персонажа (`CharacterState`, `app/engine/state/model.py`) из
потока событий парсера — редьюсер `StateReducer.apply` (`app/engine/state/reducer.py`). Каждое поле —
`Obs[T]`: `value`, `at` (момент снимка — время правки сообщения) и `src`: `screen` — значение с
экрана игры, `derived` — вычислено приращением или производным правилом, `doubtful` — значение не
тронуто, но неизвестно, учитывает ли оно уже произошедшее событие.

Правила `_Patch`:

- **снимок только новее** (`snap`) — новый снимок применяется, только если его момент не раньше
  момента уже известного значения; более старая правка игнорируется;
- **приращение только к известному** (`change`/`delta` через `_increment_mode`: числовые поля,
  счётчик апгрейдов ⚪️🔵🔴 в `rewards`, запас фастфуда `food_stock` после съеденного, навык в
  `skills` после шага level-up — основного и дополнительного, +1 к выбранному) — изменить
  можно только уже известное значение; если приращение уже сделано этим же сообщением или базовый
  снимок старше его создания — применяется (`derived`, либо остаётся `doubtful`, если таким было
  базовое значение); если базовый снимок снят между созданием и правкой сообщения (или в ту же
  секунду) — значение не трогаем, но помечаем `doubtful`: следующий снимок экрана его обновит.
  Необязательный `since` — момент, раньше которого событие произойти не могло (для билета Горбушки —
  момент экрана «нужен билет»): базовый снимок новее `since` мог событие уже учесть, и значение тоже
  становится `doubtful`;
- **итог один раз на сообщение** — события с `Event.outcome=True` применяются один раз на `(чат,
  сообщение, вид события)`, правка того же сообщения повторно не начисляет; горизонт хранения ключей
  `OUTCOME_HORIZON` — 14 дней.

Поля по источникам: компакт-профиль (`😎Я`) — `level`, `exp`, `money`, `stamina`, `knowledge`, `raw`,
`details`, `motivation`, `bag`, `tangerines`, `skills`, `busy`, `battle_at`/`battle_target`,
`sleep_deadline`/`sleep_allowed_at`; ⏳Дела — `stamina`, `sleep_deadline`, `busy` (сон под мостом или в
отеле), цены `job`/`walk`/`rob`; 🔮Стартап — цены `learn`/`confa`; 🛠Мастерская — `money`, `raw`,
`details`, `upgrades`, цены `dconv`/`white_to_blue`/`blue_to_red`; 🔧Профа — цена `harvest`; 🍴Меню —
`stamina`, `food_stock`, `fastfood_ready_at`; `/inv` — `books`, `cards` (строки нет — ноль),
`book_ready_at`/`card_ready_at` (момент экрана плюс таймер «(38 мин.)», без таймера — момент экрана),
`bag`, `bag_cap`, `prizebox`, `prizebox_ready_at`; 🎁Подарки — `containers_small`, `containers_medium`,
`tangerines`; 🏛Горбушка — `gorbushka` (состояние, счёт побед, дедлайн билета, момент следующего боя,
стоимость боя в 🔥), `money`/`knowledge` (экран «нужен билет»), `stamina` (встреча с продаваном и
ожидание), цена `gorbushka_ticket`; покупка билета (переход «нужен билет» → встреча или ожидание с 0
побед) вычитает цену билета из `money`/`knowledge`.

Выводимые таймеры (`derived`, момент правки сообщения плюс фиксированный интервал): кулдаун
фастфуда — 30 минут после съеденного; книга и карта — из ответа игры («через … минут»); таймер
прироста 🔥 (`motivation_next_at`) сбрасывается в `null`, когда мотивация восстановлена полностью;
дедлайн сна и разрешение снова лечь — 72 часа бодрствования и 12 часов после пробуждения; следующий бой Горбушки —
1 час после предыдущего. Допущение: таймеры считают, что у персонажа нет сетов 🧑‍🍳Кулинар (сокращает
КД фастфуда до 15 минут) и 🧸Соня (растягивает принудительный сон до 120 часов) — обе ошибки в
безопасную сторону, бот подождёт фастфуд дольше и ляжет спать раньше, чем позволяют сеты.

Состояние событий фазы 4: `team_tag`, `factory_wins`, `stock_limits`, котировки, акции и
ингредиенты — медленные поля (устаревают через 6 ч, как экраны фазы 2); остальное — метки
момента, по возрасту не устаревают, смысл задаёт момент наблюдения:

- `team_tag`, `factory_wins` — тег и победы команды на фабрике (экран команды); `factory_won_at` —
  момент итога SWINFO, где победила своя команда (следующую битву команда пропускает);
  `factory_signed` — записан ли на
  ближайшую битву за фабрику (экран фабрики и ответ на запись); `factory_skip` — команда выиграла
  прошлую битву и эту пропускает; `factory_call_at` — момент анонса записи SWINFO или (запасной
  сигнал, если SWINFO пропущен) экрана команды с открытой записью;
- `bulls_won_at` — момент победы над биржевиками или отказа «уже побеждал этой ночью»;
  присоединение к бою ставит занятость «bulls» на 5 минут (`derived`), итог боя её снимает и
  начисляет награды;
- `stock_quotes`, `stock_holdings`, `stock_limits` — котировки, акции игрока и лимиты биржи (лимиты
  целиком — только с главного экрана); покупка и продажа обновляют 💵 и число акций компании (если
  портфель известен), дивиденды прибавляются к 💵, сводка битвы SWINFO обновляет котировки;
- `smoothie_ingredients`, `smoothie_bonus` (текущий бонус; `null` — сегодня ещё не варили или
  рецепт был неверным), `smoothie_recipe` — рецепт из канала; экран варки в состояние не идёт (его
  остатки уже без вброшенного), приготовленный смузи отнимает рецепт от остатков экрана;
- `tangerine_ready_at` — когда снова можно слать `/gt` (из отказа по кулдауну),
  `tangerine_not_player` — имя адресата из отказа «пока не играет»;
- `battle_target_set` — какая цель выставлена и на какую битву (время битвы из ответа «Следующая
  Битва через …»); `bulls_invite` — код последнего инвайта биржевиков, момент — время инвайта;
- меню битвы обновляет `battle_at`; ответы, меняющие ресурсы (обмен символа года, подарок за 🍊,
  итог акулы), применяют как награды (один раз) деньги, опыт, знания, детали, сырьё и улучшения
  ⚪️🔵🔴 — прочее из этих ответов (мандаринки, восстановленная мотивация, книги, контейнеры, еда)
  не учитывается и подтянется следующим экраном; выигрыш лотереи ещё прибавляет 🔥, контейнеры и
  навык, утрата лотерейного навыка его отнимает, экран эфира задаёт 💵 снимком, мгновенное
  завершение дела снимает занятость.

Метро: `metro_ready_at` — когда снова можно спуститься (экран входа — «уже можно», момент экрана,
а если 🔥 на нём меньше цены входа — ещё и мотивация: планировщик считал иначе;
отказ «До следующего спуска …» — момент плюс остаток; итог забега — момент выхода плюс 16 часов,
`derived`); `metro_message` — идущий забег (`MetroRunRef`: id сообщения и наблюдение `battle_at`,
известное на первом экране забега, — битва, за 15 минут до которой игра выкинет персонажа; с экрана
бафов и любого экрана забега, момент — последний экран), итог «Получено» ставит `null`; экран бафов после входа списывает 2🔥 один раз на сообщение забега; 🔋 кадров карты,
запроса аптечки, итога боя и ловушки-стрелы (0) — снимок выносливости персонажа (в метро она та же).
Лут и награды боёв идут в копилку забега и начисляются только итогом «Получено» (один раз): 💵, 💡,
📚, ⚙️, 🔩, улучшения ⚪️🔵🔴, фастфуд — к известным запасам `food_stock` (жетоны 🕳 в состоянии не
ведутся).

`activity_stats` — скользящее среднее наград каждого дела (`ActivityStat`: 💡, 💵, 📚, ⚙️, 🔩 без
цены дела, `count` — число учтённых итогов): каждый `ActivityFinished` сдвигает среднее на 10%
(`STATS_ALPHA`) к наградам итога, начиная со стартовых значений корпуса (`DEED_PRIORS`: добыча 203💡,
работа 117💡 + $25.7 + ⚙️2.3 + 🔩0.8, учёба 235💡 + 📚11, переработка 253💡 + 🔩5). Пока экран цен
не виден, цены дел берутся из `DEFAULT_PRICES`.

пир пета, ежедневные задания, платная информация и сезонные ивенты); `strategy` — веса
`weight_xp`/`weight_money`/ `weight_resources`/`weight_team` (1.0/1.0/0.5/0.5), масштабы «типичного
дохода на 1🔥» `exp_scale`/`money_scale`/`resource_scale` (200💡/$30/10 ресурсов) и дела, из которых
выбирает планировщик (`deeds`: добыча, работа, учёба, переработка); `food` — порядок видов фастфуда
(🌭 → 🍕 → 🍔) и неприкосновенный запас бананов (50); `sleep` — длительность сна (7 ч, допустимо 7–12),
за сколько минут до дедлайна ложиться (`lead_min`, 120) и порог денег для отеля
(`hotel_if_cash_after_reserve_ge`, по умолчанию — цена отеля с экрана выбора места);
`levelup.policy` — `balanced`; `engine.paused` — пауза планировщика; `battle` — цель взлома или защита (`target`, по умолчанию
📯Pied Piper; своя компания недопустима) и цели на отдельные битвы по часу битвы по Москве

`metro` — нижняя граница бюджета забега `min_budget_min` (60), запас до битвы на выход игры

аптечках ≥ `chest_min_packs` (2), драться со слабым NPC `npc_low_enabled` (да) и с сильным
`npc_high_enabled` (нет), без аптечек не драться при 🔋 ниже `npc_min_stamina` (30).

**Политика шлюза.** Каждая не-`nav` команда относится к механике (`feature_of_text`/
`feature_of_callback` в `app/engine/commands.py`); если механика выключена в `features`, шлюз
отклоняет команду (`REJECTED "feature_off:<механика>"`) для всех источников, кроме ручного. Пауза
(`engine.paused`) отклоняет не-`nav` команды планировщика и сценариев (`REJECTED "paused"`) — в том
числе очередной шаг сценария, начатого до паузы; срочные и ручные — по флагам
`urgent_while_paused`/`manual_while_paused`. Шаг несертифицированного сценария
(`ActionRequest.simulate`) подавляется в любом режиме (`SUPPRESSED "uncertified"`, в `dry_run` —
`"dry_run"`), `nav` уходит. Ожидание может слушать другой чат (`Expectation.chat_id`): шаги
сценариев всегда ждут ответа в чате игры, даже если команда ушла в чат Tangerine (`/gt`). Если игра
отвечает только на ошибку, ожидание помечается `Expectation.silence_confirms` (сейчас — только
`/gt`): тишина до тайм-аута подтверждает действие (`CONFIRMED "silence"`) без блока трат и сверки.

**Сценарии** (`app/engine/scenarios`) — корутины над `ScenarioContext`: `send`/`click` отправляют шаг
через шлюз от имени `SCENARIO` и ждут семантический предикат (`expect_events` — событие нужного типа
подтверждает, `Refused`/`Busy` — отказ; `expect_button` — сообщение с кнопкой). Многошаговые
сценарии берут аренду шлюза (`lease`) и между шагами проходят безопасную точку (`safe_point`: срочное
действие может пройти, пауза останавливает сценарий). Итог — `ScenarioResult`: `done`; `nothing`
(делать нечего, например Горбушка ждёт следующего продавана); `refused` (отказ игры с причиной);
`suppressed` (`dry_run` или несертифицированный шаг); `failed` (нет ответа, шлюз отклонил, сбой);
`stopped` (остановка в безопасной точке: пауза или неожиданный ответ). Реестр (`registry.py`,
`SCENARIOS`): `refresh` (экран-источник: профиль, рюкзак, меню еды, подарки, Горбушка — те же, что у
сверщика), `book`, `card`, `prizebox`, `container_small`, `container_medium`, `fastfood` (меню
`/to_eat` → кнопка вида; если меню показывает кулдаун фастфуда — `nothing` `fastfood_cooldown` без
нажатия кнопки), `levelup` (`/levelup` → меньший из 🔨/🎓 → меньший из 🐿/🐢), `gorbushka`
(экран → если билета нет, покупка разрешена и ресурсов на самом экране хватает — `gorbushka_new` →
`gorbushka_new_accept`, нехватка после оплаты — отказ `no_money` → бой `gorbushka_fight`; успех боя
подтверждает только его итог, правка встречи «Ты ещё не встретил продавана» приходит при любом
исходе, «проблема с навыками» — отказ), `sleep` (`🛌Спать` → меню с ценой отеля → `sleep_N` → правка
меню с выбором места «Где собираешься спать?» (`SleepPlace`, те же часы и цена отеля) → `sleep_Hotel`,
если деньги из состояния минус резерв билета Горбушки (`ticket_reserve`) не меньше max(цена с экрана,
`hotel_threshold`), иначе `sleep_Bridge`; явный `params.hotel` важнее → засыпание `FellAsleep` правкой
того же сообщения; итог сверяется с выбором (место, часы, не принудительный), иначе отказ
`place_mismatch` и уведомление `sleep_place_mismatch`; отдельный ответ «Ты потратился на отель…» /
«Ты решил не тратиться на отель…» в состояние не идёт — отель списывает только `FellAsleep`; меню с
«❌Тебе не хватает ещё N 💵» вместо сна — отказ `no_money`; `/decline` из ответа сценарии не шлют),
`deed:<дело>`.
Обязательства фазы 4 (`obligations.py`): `battle_target` (`⚔Битва` → кнопка цели из меню),
`stocks_dump` (`/stock` → самая дорогая чужая акция, которую можно купить и продать с запасом до
лимита, `/buys_<код>_<N>` на всё сверх `keep`; комиссия 1💵/шт, биржа закрыта — `nothing`),

`signed`/`already`/`skip`), `bulls_join` (код инвайта текстом → присоединился или отказ с причиной),
`tangerine` (`/gt` ответом на сообщение адресата в чате Tangerine; в личку игра при успехе молчит —
подарок виден только в чате Tangerine, — поэтому шаг ждёт с `silence_confirms` и тишина за время
ожидания — `done "no_error"`; отказом считается только ответ про мандарины), `smoothie` (`/smoothie` → если сегодня варили или не
хватает ингредиентов — `nothing`; `🍹Готовить` → `sm_drop_N` по рецепту, после каждого фрукта —
правка экрана с вброшенным → `smoothie_accept`; неверный рецепт — `done "no_bonus"`), `metro` (см.
«Метро»). Выбор акции и размер покупки — общие для сценария и планировщика (`app/engine/market.py`).
Контекст сценария (`ScenarioContext`) несёт часы (`clock`) и уведомления (`notify`), а шаг может
задать свой таймаут ожидания (`click(..., timeout_s=)`); итог сценария может нести подробности
(`ScenarioResult.details`, у метро — запись забега).

**Сертификация.** Сценарий сертифицирован, если все его переходы пройдены на эмуляторе игры
`FakeGame` (`tests/engine/fakegame.py`: транспорт, который отвечает реальными сообщениями из фикстур
через настоящий конвейер, включая правку сообщения по клику). Такие тесты помечены `@certifies(...)`,
а `tests/engine/scenarios/test_registry.py` проверяет, что у каждого сценария из `CERTIFIED` есть
тест. Сон сертифицирован живой записью 26.09 (меню, выбор места, отель; путь «под мост» — тот же
экран выбора и итог «Ты ушёл спать под мост» из корпуса). Не сертифицированы (ждут живой
досъёмки): `container_medium`, `deed:walk`, `deed:confa`, `deed:rob`.

**Решение** (`app/engine/planner/decide.py`, `decide(state, settings, now, *, certified,
last_refresh, cooldowns, last_done)`; общие помощники — `base.py`, обязательства — `obligations.py`)
— чистая функция: `Act(scenario, params, reason, candidates)` или `Wait(until, reason, candidates)`;
`candidates` — все рассмотренные варианты с оценкой и причиной отказа (`busy`, `no_motivation`,
`no_money`, `battle_window`, `factory_window`, `uncertified`, `cooldown`, `stale:<поле>` и т.д.).
Порядок: level-up → биржевики → цель битвы → 🔋 к битве → слив налички → запись на фабрику → сон →
книга → фастфуд (первый вид по `food.order`, у которого нижняя граница выше текущей 🔋; бананы —
только сверх запаса) → карта → контейнеры → призовая коробка → Горбушка (бой при встрече или по
кулдауну, покупка билета при его отсутствии и достатке 💵/📚, неизвестное состояние — открыть экран) →
мандарин → смузи → метро → дело с лучшей оценкой `(w_xp·💡/exp_scale +
w_money·(💵 − цена)/money_scale +
w_res·ресурсы/resource_scale + w_team·вклад в командное задание) / цена в 🔥` по `activity_stats`;
устаревшая (старше 7 дней) цена дела берётся по каждой составляющей как большее из запомненной и
`DEFAULT_PRICES`. Фастфуд и призовая коробка доступны во время дела, остальное (в том числе level-up
и контейнеры — на них игра отвечает «занят») — только когда персонаж свободен; во сне планировщик
ждёт пробуждения и выставляет только цель битвы. Резервы: 1🔥 под бой Горбушки, если он в ближайший
час; 💵 на билет, пока билета нет; цена отеля за 3 часа до окна сна, если к нему выбран отель, — дела
их не тратят, а билет покупается только из денег сверх резерва на отель. Резерв на отель (и здесь, и
в сливе налички) держится, только если сон будет исполнен: механика включена и в `live` сценарий сна
сертифицирован (сертифицирован). Дело не начинается, если
закончится позже чем за 6 минут до битвы (запрет действует до минуты после её начала) или позже
дедлайна сна. Если нужное поле неизвестно, устарело или сомнительно (`stale_fields`; мотивация — ещё
и после тика регенерации, время битвы — после её начала), решение — обновить его экран (`refresh`),
но не чаще `engine.refresh_min_interval_s` на источник; идущее дело считается известным до своего
`until`.

Время битвы планировщик приводит к началу часа (`battle_hour` в `base.py`): битвы начинаются ровно
в начале часа, а отсчёт «Битва через …» игра округляет вниз (до минуты, от суток — в каникулы — до
часа), поэтому берётся ближайшее начало часа не раньше `battle_at` − 2 мин. Точность видна по длине
отсчёта (`battle_at` минус момент наблюдения): у отсчёта от суток запас — 2 с, иначе отсчёт, снятый
в первые минуты часа, указал бы на час раньше. Состояние хранит наблюдение как есть.

Обязательства (слой 1, время — московское):

- **цель битвы** — перед каждой битвой, в том числе во сне и во время дела: цель из
  `battle.overrides` на час битвы, иначе `battle.target`. Цель уже выставлена, если профиль, снятый
  вместе со временем предстоящей битвы или позже, показывает её, либо (защиту профиль не показывает)
  эта же цель выставлена на эту битву (`battle_target_set`); за минуту до битвы не выставляется;
- **🔋 к битве** — если до битвы ≤ 30 минут и 🔋 на нуле: фастфуд по обычным правилам (`food.order`,
  запас бананов), если он готов или будет готов за 2 минуты до битвы (устаревшие запасы еды и её
  кулдаун сначала обновляются — `refresh` меню еды, а не платное `eat`), иначе — дело `eat`, если
  дела включены и оно закончится не позже чем за 6 минут до битвы;
- **слив налички** — с `battle − dump_lead_min − 10 мин` до минуты до битвы, в часы биржи: если 💵
  минус оставляемое (`cash_floor` + билет Горбушки + на ближайший сон в отеле — большее из цены
  отеля и порога `hotel_if_cash_after_reserve_ge`, чтобы после слива выбор отеля не изменился; но
  не меньше неснижаемого остатка биржи) не меньше `min_dump`, а по котировкам,
  увиденным уже в окне слива (они меняются после каждой битвы), есть подходящая акция;
- **фабрика** — запись с 18:00 до 18:15, если сегодня ещё не записан, не пришёл отказ «пропускаете»
  и команда не выиграла вчерашнюю битву (`factory_won_at`); пока запись нужна, дела, которые
  закончатся после 18:00, не начинаются (`factory_window`);
- **биржевики** — ночью (22:00–08:00) по инвайту не старше 3 минут, если этой ночью ещё не
  побеждал и персонаж свободен;
- **мандарин** — раз в `tangerine.interval_h` от последней успешной отправки (`last_done`, из
  журнала запусков; плюс минута `READY_SLACK` — запуск стартует раньше, чем `/gt` реально уходит),
  не раньше кулдауна из отказа; после отказа «не играет» — пауза на сутки;
- **смузи** — по рецепту из канала, полученному после сегодняшнего сброса (03:00), если сегодня
  ещё не варили (в том числе неудачно — `last_done`) и по известным остаткам хватает ингредиентов;
- **продолжение метро** — первым шагом, до level-up: если `metro_message` указывает на забег,
  последний экран которого не старше 2 часов, а игра его ещё не выкинула (за 15 минут до начала часа
  битвы забега — той, что была известна на его входе; профиль после неё показывает уже следующую), —
  сценарий `metro` с `resume` и моментом битвы забега (без проверок кулдауна, бюджета и 🔥: вход уже
  оплачен). Так забег продолжается после рестарта процесса и после остановки сценария (пауза,
  таймаут — с кулдауном серии неудач);
- **метро** — персонаж не в забеге (до выброса игрой нового входа нет: забег продолжается или, если
  продолжать нельзя — экран старше 2 часов или незнакомый, — ожидание выброса `metro_kick`),
  кулдаун прошёл (`metro_ready_at`; если таймер неизвестен — не раньше 16 ч после
  последнего успешного запуска `metro` из журнала, иначе заход сам покажет экран входа или отказ по
  кулдауну), до битвы (начало её часа, как у всех обязательств) не меньше
  `max(min_budget_min, p90 прошлых забегов × 1.5) + battle_margin_min + extra_margin_min`
  (длительности — из `metro_runs`, `decide(..., metro_durations=)`), забег той же длины не упирается
  в дедлайн сна и в запись на фабрику, персонаж свободен, 🔥 минус резерв Горбушки ≥ 2. Параметры
  сценария — нормированный момент битвы, запас и политики из настроек `metro`. Если спуск станет
  доступен в ближайший час и битва позволит, дела держат 2🔥 на вход;
- **сон** — в ночное окно без битв: с 22:05 (если ждём инвайтов биржевиков и в ту ночь, на которую
  планируется сон, ещё не побеждали — с 00:30) так, чтобы проснуться до 12:45; не раньше разрешения лечь и не позже, чем
  требует дедлайн (`lead_min` до него); сон, накрывающий запись на фабрику, ждёт её конца, если
  после неё до дедлайна остаётся 15 минут. Деньги на отель дела не тратят за 3 часа до начала сна.
Кулдаун рефреша — свой у каждого источника (`refresh:<источник>`): неудачный рефреш профиля не
откладывает рефреш рюкзака. Игровые таймеры выведены из даты сообщения с точностью до секунды, а
итог приходит в момент таймера + 0–1 с, поэтому таймер считается истёкшим с запасом `TIMER_MARGIN`
(3 с): дело идёт до `until` + 3 с, так же отсчитываются бой и возврат в Горбушку и тик 🔥. Кулдауны
книги, карты, фастфуда, коробки, мандарина и разрешение лечь экраны показывают с точностью до минуты
(с округлением вниз), поэтому к ним добавляется ещё минута (`READY_SLACK`); таймер, истёкший уже на
момент снимка (экран без таймера, встреча с продаваном), готов сразу. В `live` выбираются только
сертифицированные сценарии, в `dry_run` — любые (шлюз их всё равно подавит). Если ничего не подходит
— `Wait` до ближайшего таймера плюс `TIMER_MARGIN` (конец дела, кулдауны книги, фастфуда и коробки,
следующий бой или возврат в Горбушку, тик 🔥, окна обязательств (сон, слив налички, запись на
фабрику, мандарин), конец битвы, лимит рефреша, кулдаун сценария).

**Цикл** (`app/engine/planner/loop.py`, `PlannerLoop`, фоновая задача `planner`) просыпается по каждой
доставке шины, по `Wait.until` (не реже раза в 30 минут) и по сигналу фасада. Пока движок не готов
(пауза, kill switch, блок трат, конвейер нездоров, нет лока, Telegram не `ONLINE`), он не принимает
решений, не показывает момент пробуждения (`next_wake` пуст) и проверяет готовность раз в 5 секунд.
Каждое решение пишется в `decisions` (одинаковые ожидания подряд — один раз), каждый запуск
сценария — в `scenario_runs`; момент последнего успешного или прерванного рестартом (исход
неизвестен) запуска каждого сценария цикл берёт из `scenario_runs` при первом решении
(`PlannerStore.last_done`) и обновляет после `done` — по нему считаются период мандарина и смузи раз
в день, в том числе после рестарта. Запись забега метро (`ScenarioResult.details["metro"]`) цикл
сохраняет в `metro_runs` после записи запуска (сбой сохранения только логируется), а длительности
завершённых забегов (последние 20, `MetroRunStore.durations`) берёт при первом решении и дополняет
после каждого `done`, оставляя последние 20, — по ним считается бюджет метро. Отказ «адресат не играет» даёт уведомление
`tangerine_not_player`. Контекст сценария получает `simulate`, если
сценарий не сертифицирован, — независимо от режима, поэтому смена `dry_run` на `live` посреди
сценария не делает его шаг реальным. Итог сценария задаёт кулдаун по ключу — имени сценария, у
рефреша — `refresh:<источник>`: `nothing` и отказ `busy` (конец дела уже известен из отказа) — 1
минута, кроме итогов из `NOTHING_HOLD`, которые скоро не изменятся (закрытая биржа у слива — 30
минут, до конца окна слива; сменившаяся цена входа в метро — 2 часа); прочий отказ — 5 минут, а отказ, общий для всех дел (`battle_soon`, `battle_running`,
`factory_running`, `tired`, `levelup_required`), откладывает на 5 минут все дела; серия неудач
(`failed`/`stopped`) — 5 минут, затем 10, 20 и так далее, но не больше 2 часов, `done` серию
сбрасывает. Первая неудача серии даёт уведомление `scenario_failed`, следующие — нет. Остановка по
паузе неудачей не считается и пишется в журнал как `stopped` с причиной `paused`. Кулдаун ставится до
записи итога в `scenario_runs`: сбой БД не оставляет сценарий без него. Подавленный сценарий
(`dry_run`, несертифицированный шаг) откладывается на 10 минут, подавленное дело — вместе со всеми
делами, а планировщик решает остальное: журнал `dry_run` показывает всё, что бот сделал бы; при
смене `engine.mode` эти отсрочки снимаются. Подавление kill switch или остановкой шлюза
(`kill_switch`, `shutdown`) отсрочки не даёт.

## Метро

**Решатель** (`app/engine/metro/`) — чистый код без I/O, время передаётся аргументом.
`MetroSolver.next(событие, now)` вливает экран в модель и возвращает следующий шаг: `Click(callback,
причина)`, `Done` (итог «Получено») или `Halt(причина)` — дальше без человека нельзя.

- **Карта** (`grid.py`, `Grid`): глобальная сетка в координатах `(строка, столбец)` от входа —
  стена, проход, выход (неизвестное не хранится) и посещённые клетки. Окно 5×5 кадра вливается
  вокруг позиции; позицию двигает подпись прихода («Вниз» — пришли вниз) или экран события на
  новой клетке (лут, NPC, сундук, выход); остальные подписи («Ждёшь», «Остался», «Не бьёшся», «Не
  открываешь», «Стена») — та же клетка. «Стена» в ответ на свой ход в проход по карте — карта
  разошлась с игрой, `Halt("unexpected_wall")`. Экран выхода без ожидаемого хода (ход до рестарта не
  попал в журнал) клетку не трогает: персонаж — на соседнем известном выходе, если он один, иначе
  позицию ищет следующий кадр карты по всей карте. Повторяющиеся окна (прямой коридор) позицию не меняют. Окно,
  противоречащее карте, переобъявляет позицию: единственное место без противоречий с наибольшим
  совпадением (не меньше 12 клеток), при обычном ходе — только среди соседних с ожидаемой клеток
  (ход не состоялся), по всей карте — только для свежего кадра после рестарта (`resync`);
  неоднозначно или далеко — `Halt("lost")`.
- **Обход** (`plan.py`): цель — посетить все достижимые проходы (лут, NPC и сундуки на карте не
  видны). Шаг — к ближайшей непосещённой клетке по известным проходам (на дереве это обход в
  глубину с доведением ветки до конца); выбранная цель держится до прихода (пересчёт на каждом шаге
  качал бы между областями); проход через клетку выхода дороже на 3 шага (диалог «Выходишь?»).
  Известный выход — не цель обхода, ветка выхода откладывается на конец: первыми идут клетки, чьи
  пути ответвляются от пути игрока к выходу ближе к игроку (по дереву кратчайших путей от выхода —
  на графе с циклами порядок ветвей не зависит от точки обзора); на дереве это оптимальный обход с
  концом в выходе. Обходить нечего — идём к выходу.
- **Бюджет** (`budget.py`, `Budget`): от первого кадра карты до битвы минус запас
  (`battle_margin_min` + `extra_margin_min`). Время шага — медиана последних 20 ходов «клик → новый
  кадр» (диалоги событий, очередь между ходами и простой процесса в замер не входят), пока ходов
  меньше 10 — не меньше априорного (5 с с бафом 🏃, иначе 20 с). Выход известен: если путь до него ×
  время шага × 1.5 + запас достигает битвы — обход бросается (`leave deadline`). Выход неизвестен: с
  60% бюджета — режим `frontier` (сначала клетки, шаг в которые открывает неизвестное), с 85% —
  однократный сигнал `late_risk`. Игра выкидывает из метро за 15 минут до битвы с половиной
  найденного (`kick_at`; экрана выброса не видели). Досрочный выход кнопкой 🚪 необратим, поэтому
  решается по оптимистичной оценке: только если за минуту до выброса выход неизвестен или к нему не
  успеть даже при шаге, равном меньшему из недавнего замера и априорного, плюс клик подтверждения
  «Выходишь?». Условие пересчитывается на каждом кадре и ещё раз в диалоге досрочного выхода (не
  нужно — «Остаться»); перед 🚪 решатель долечивается, только если ещё одна аптечка (❤️ и согласие)
  и выход (🚪 и «Выйти») успевают до выброса. Клик с тостом (❤️, «Продолжить») закладывается в 2 с,
  клик без тоста (🚪, «Выйти», «Остаться», согласие на аптечку) — в 6 с: шлюз ждёт ответа на callback
  до `click_answer_timeout_s` (4 с), затем темп 1.6 с; последнему клику цепочки хватает 2 с, чтобы
  дойти до игры.
- **Политики событий** (`Policy`): лут, итог боя и исход сундука — `maze_continue` («Продолжить»
  только на экранах известного типа); аптечка на карте при 🔋 ≤ `heal_at`; в режиме выхода — до 100%
  (`heal_before_exit`), пока есть аптечки; слабый NPC — драться (`npc_low`), сильный — отказ, если
  не включён `npc_high`, но без аптечек при 🔋 ниже `npc_min_stamina` (30) — отказ от любого боя
  (лечиться на экране NPC нельзя); поражение в бою — `Halt("fight_lost")` без «Продолжить»; сундук —
  открыть при аптечках ≥ `chest_min_packs`; выход — отказаться, пока идёт обход, и выйти в режиме
  выхода, но если уход решён на самом экране «Выходишь?» (там лечиться нельзя), а `heal_before_exit`
  включён, аптечки есть, 🔋 < 100 и до выброса успеть «Остаться», аптечки до 100%, шаг с клетки и
  обратно и «Выйти», — так и сделать, иначе «Выйти» сразу; диалог досрочного выхода не по решению
  решателя — «Остаться»; незнакомый экран —
  `Halt("unexpected_screen:…")`.
- Запись забега — `snapshot()` (карта, позиция, путь, события с координатами, 🔋 и аптечки по
  шагам, сигналы). Продолжение после рестарта не нуждается в сохранённой карте: правки сообщения
  забега из журнала повторяются через `replay` (см. сценарий): как `observe`, и режим пересчитывается
  на момент каждого кадра, как его пересчитывал решатель до рестарта, — уход к выходу необратим и
  не сменяется обходом оттого, что путь до выхода стал короче; затем режим пересчитывается на
  текущий момент (`update_mode`). Окно, разошедшееся с картой, сверяется `Grid.locate`.

Воспроизведение всех 533 кадров живого забега через решатель восстанавливает его карту, путь (246
шагов) и выход в точности как в записи исследования (`tests/fixtures/metro/run1.json`); второй
живой забег (399 кадров, решатель прототипа, `run2.json`) — 182 шага, 95 клеток, выход (14, −2) и
итог, с отказами от NPC и сундука, ходом в стену и отказом от досрочного выхода.

**Сценарий** `metro` (`app/engine/scenarios/metro.py`, аренда шлюза на весь забег): `🏢Офис` →
`🚇Метро` → `maze_enter_accept` → бафы за 🕳 из `params.buffs` (по умолчанию все три, покупаются
только предложенные кнопками и пока хватает жетонов; `maze_buf_coins_*` — донат, шлюз их не
пропустит) → `maze_start` → цикл: экран → `MetroSolver.next` → клик. Ответ на `🚇Метро` разбирается
явно: экран входа — дальше, отказ «До следующего спуска …» — `refused metro_cooldown`, незнакомый
экран — сразу `stopped unexpected_screen` с уведомлением `metro_halted`. Если вход стоит не
`ENTRY_COST` (2🔥) или 🔥 меньше цены, «Вхожу» не нажимается: `maze_enter_decline` (ответ на него
живьём не видели, итог от него не зависит) и `nothing` — `entry_cost_changed` с уведомлением
`metro_entry_cost` или `no_motivation`. Каждый клик ждёт новую
правку сообщения забега (`expect_metro`): «Идёшь …» со старым окном не засчитывается, любая другая
правка подтверждает клик, отказ игры отдельным сообщением — отказ шага. Тип экрана разбирается явно
и на входе, и на бафах, и в обходе: незнакомый экран — `stopped unexpected_screen` сразу, без
ожидания таймаута, с уведомлением `metro_halted` (как и любая остановка решателя: поражение,
потерянная позиция, неожиданная стена). Баф, не отмеченный купленным, — уведомление `metro_buff_not_bought`; без 🏃 —
уведомление `metro_slow`, а априорное время шага в бюджете — 20 с. Таймаут тоста клика — не ошибка
(подтверждение — правка сообщения); ожидание кадра без быстрого шага — вчетверо дольше. Перед каждым
кликом — безопасная точка (пауза останавливает забег, срочное проходит); после неё сценарий сверяет
последнюю ревизию сообщения из кэша конвейера с кадром, по которому решал: в обходе сменился кадр
карты — решение пересчитывается (ход не отправлялся, цель и намерение досрочного выхода
сбрасываются), сменился на экран события — остановка `screen_changed`; на входе, бафах и старте
любая смена — остановка `screen_changed`. Каждый клик несёт ревизию и хеш содержимого кадра
(`expect_revision`, `expect_content`): шлюз перед каждой попыткой отправки сверяет их с последней
правкой и не отправит клик, если сообщение уже другое (`stale_revision` / `stale_content` — хеш
различает и правки одной секунды, у kurigram их ревизия одинакова). Сигналы решателя —
уведомления один раз: `late_risk` — `metro_late_risk`, первый незнакомый символ в окне карты
(клетка считается неизвестной) — `metro_unknown_cell`. Параметры: `battle_at` (ISO, момент битвы), `margin_min`
(запас до битвы), `heal_at`, `heal_before_exit`, `chest_min_packs`, `npc_low`, `npc_high`,
`npc_min_stamina`, `buffs`. Итог несёт запись забега (`details["metro"]`: карта, путь, события с
координатами, 🔋 и аптечки по шагам, длительности ходов, бафы, итог «Получено», длительность, время
шага, исход).

С `resume` (id сообщения забега) сценарий не входит заново. Карту, позицию, путь и время начала
восстанавливают записанные правки сообщения из журнала (`ScenarioContext.history` →
`DbJournal.revisions`), прогнанные через решатель с моментами кадров (`replay`, режим — как до
рестарта), а решение принимается только по текущему экрану,
прочитанному прямо из Telegram (`ScenarioContext.reread` → `Transport.fetch`, у kurigram —
`get_messages`): клик до рестарта мог дойти до игры, а его правка — не до журнала, и повторять его
по старому кадру нельзя. Прочитанное проходит конвейер (журнал, состояние) и становится текущей
ревизией (`Pipeline.prime`: после рестарта кэш ревизий пуст, и шлюз отклонил бы клик как
`stale_button`); позиция по этому кадру ищется по всей карте (`resync`). Не прочитать —
`resume_unreadable`, незнакомый экран — `resume_unknown_screen` (оба с `metro_halted`, без кликов);
экран бафов — докупить и стартовать; пустой журнал — остановка. «Идёшь …» — ход ещё идёт:
сообщение перечитывается раз в 2 с, до 10 с, и прочитанное «Идёшь …» входит в повтор (это ход к
текущему кадру); нового окна так и нет — остановка `resume_while_moving`.

позиции после сбоя; на карте живого забега (95 клеток) решатель проходит всё за 162 шага против 246
у жадного BFS исследования.

## Запуск

```bash
uv run alembic upgrade head
uv run python -m app
```

`app/__main__.py` поднимает uvicorn с одним воркером (`workers=1` — единственный процесс держит и
HTTP, и MTProto-клиент, и очередь действий в одном event loop). `create_application` (`app/main.py`)
собирает `Runtime`, порядок старта: настройки → админ (`ensure_admin`, если задан
`PYROBOT_ADMIN_PASSWORD`) → единственный экземпляр (`app/db/lock.py`, `SingleInstanceLock` —
Postgres advisory lock) → если лок не взят, движок не стартует, уведомление `second_instance`,
`/readyz` навсегда 503 для этого процесса → если в БД есть незакрытые обязательства сверки
(`ActionStore.unreconciled()`: строки `outcome_unknown` класса не `nav` без `reconciled_at`, в том
числе переведённые так `mark_unfinished_unknown()` после рестарта), шлюз сразу блокирует траты
(`block_spending("reconcile_required")`) и шлёт уведомление `actions_outcome_unknown` — блок снимает
сам сверщик (`Reconciler`, см. «Шлюз действий»), как только обновит все затронутые экраны, либо
администратор явным `POST /api/v1/engine/reconciled` → шина, конвейер (снимок состояния
восстанавливается из журнала, редьюсер — `StateReducer`, при изменении состояния метрики
(`StateReducer.metrics`) пишутся в ту же транзакцию, что и журнал) → транспорт (`PYROBOT_TRANSPORT=kurigram|fake`) → шлюз действий,
подписанный на шину → `TgAuthManager`
→ сверщик (`Reconciler`) → незавершённые (`running`) запуски сценариев прошлого процесса помечаются
`interrupted` с причиной `restart` (`PlannerStore.close_running`) → планировщик (`PlannerLoop`,
подписан на шину) → фасад → супервизор (`app/engine/supervisor.py`, `Supervisor`) поднимает и
перезапускает с экспоненциальным backoff фоновые задачи конвейера, шлюза, сверки состояния
`reconcile`, планировщика `planner` (если `PYROBOT_PLANNER` не выключен), монитора лага event loop, наблюдателя за локом, чистки истёкших сессий админки
`session-purge` и (для kurigram) пробы сессии Telegram `tg-probe`, уведомляя `task_failed:<имя>` при
падении → `tg.boot()` пытается восстановить существующую сессию Telegram.

Режим по умолчанию — `dry_run` (`settings.engine.mode`): любое действие, кроме `nav`, подавляется
шлюзом ещё до отправки, в игру ничего не уходит. Переключение в `live` — через настройки движка.

`GET /readyz` отдаёт 200, только когда одновременно: лок держится этим процессом, все фоновые задачи
супервизора живы, Telegram в состоянии `ONLINE`, kill switch не активен, блок трат снят и конвейер
здоров. Фоновая задача `lock-watch` каждые 10 секунд перепроверяет, что advisory lock по-прежнему
держит именно текущее backend-соединение — SQLAlchemy может молча переподключиться после разрыва, и
обычный `SELECT 1` прошёл бы на новом соединении, потеряв лок незаметно. При потере —
`kill("lock_lost")` (latch, без сохранения в настройки) и ровно одно уведомление `lock_lost`, после
чего проверка лока не повторяется (задача не завершается и не перезапускается супервизором — она
паркуется, чтобы не слать `lock_lost` повторно на каждом цикле backoff); `/readyz` уходит в 503.
Автоматического восстановления нет, нужен рестарт процесса: `POST /api/v1/engine/unkill` без лока
отвечает 409 `{"detail": "lock_lost"}` и latch не снимает, а шлюз независимо от latch отклоняет
любую отправку, пока лок не держится (предикат `can_send`, см. ниже).

Остановка (`Runtime.stop`) идёт по независимым шагам: остановить планировщик
(`Supervisor.cancel("planner")` — отменить одну задачу и дождаться её; новый шаг сценария не уйдёт
в закрывающийся шлюз, прерванный запуск закроет `close_running` при следующем старте) → закрыть
шлюз → остановить транспорт (новые апдейты больше не приходят) → дождаться, пока конвейер запишет в
журнал всё уже принятое (`Pipeline.drain`, до 10 секунд; если не успел — warning с числом
оставшихся сообщений) → остановить супервизор → освободить lock → закрыть пул БД — сбой одного шага
не мешает остальным.

## Структура

- `app/engine` — движок: типы сообщений, парсеры, реестр команд, конвейер, шлюз действий, транспорт.
- `app/db` — Postgres: модели, миграции, хранилища.
- `app/api` — HTTP API для админки.

Транспорт kurigram (`app/engine/transport/kurigram.py`; зависимость закреплена
`kurigram>=2.2.26,<2.3` — транспорт опирается на внутреннее поведение SDK 2.2.x, например на то, что
`invoke(retries=1)` при таймауте делает ровно одну попытку) держит `workers=1` — апдейты
обрабатываются строго по порядку — и `skip_updates=False`, чтобы при старте догнать пропуски
(сообщение, правленое до догона, приходит как новое: его время события и ревизия — по дате правки,
`created_at` — по дате создания, как у обычной правки);
identity (`get_me`) проверяется до запуска апдейтов, и полученный в `identify()` пользователь
переиспользуется в `go_online()` (при входе по коду `get_me` вызывается один раз там). Исходящие RPC
(`SendMessage`, `GetBotCallbackAnswer`) — одна попытка без сна и повторов SDK, все повторы и паузы
идут только через шлюз действий. Потеря авторизации (401 от Telegram) обнаруживается при отправке
текста, при клике и пробой `probe()` — `updates.GetState` раз в 60 секунд (фоновая задача
`tg-probe`, `Runtime.tg_probe_s`, пробует только в состоянии `ONLINE`). Во всех трёх случаях клиент
принудительно останавливается (ошибки остановки логируются, но не мешают), файл сессии удаляется и
создаётся новый клиент — повторный вход идёт с чистого состояния, после чего вызывается
`on_auth_lost`; отправка и клик дополнительно поднимают `TransportAuthLost`. Прочие ошибки пробы
только логируются. `log_out()` при любом исходе `auth.LogOut` делает ту же очистку: 401 (сессия уже
отозвана) считается успешным выходом, другая ошибка пробрасывается после очистки. `BadRequest` при
клике — `TransportRejected`; если бот не прислал тост (таймаут ожидания ответа или
`BOT_RESPONSE_TIMEOUT` от Telegram — игра часто выполняет действие без тоста), `click()` возвращает
`None`, и исход проверяется ожиданием шлюза, а не считается отказом. Таймаут тоста
`click_answer_timeout_s` — не больше 30 секунд. Фильтр чатов (`ChatFilter`) пропускает: игровой чат
и канал смузи — любые сообщения; чат SWINFO — только от пользователя SWINFO; чат приглашений в бой —
только сообщения с кнопкой `join_fight_<11 символов>` (один текст без кнопки не считается); если чат
приглашений совпадает с общим чатом SWINFO, правила проверяются независимо; всё остальное
отбрасывается ещё до журнала. Наивные даты pyrogram трактуются как локальные и переводятся
в UTC; сообщение помечается `recovered`, если разрыв между получением и датой сообщения больше 60
секунд.

Вход в Telegram (`app/engine/tg_auth.py`, `TgAuthManager`) сериализует все шаги логина одним
`asyncio.Lock`. `boot()` при уже авторизованной сессии проверяет identity **до** запуска апдейтов:
чужой аккаунт получает `log_out()` и состояние `ERROR "unexpected_user"`, апдейты не стартуют. Если
сессию отозвали, пока процесс был остановлен, `connect()`/`identify()` при старте получают 401
(`TransportAuthLost`): клиент сбрасывается так же, как при потере на лету, `boot()` сам переводит
менеджер в `UNAUTHORIZED "session_revoked"` и шлёт уведомление `tg_auth_lost` — не через
`mark_lost()`/`on_auth_lost`, потому что `boot()` в этот момент уже держит свой `asyncio.Lock`, а
`mark_lost()` тот же лок захватывает повторно. Попытка входа
(`start`/`submit_code`/`submit_password`) привязана к `owner` и `attempt_id` с TTL
(`attempt_ttl_s`, по умолчанию 600 с): активную непросроченную попытку другого владельца отклоняет
`AttemptMismatch`, тот же владелец может начать заново, после истечения TTL попытку может подхватить
кто угодно. Коды и пароли никогда не попадают в текст ошибок и логи. `mark_lost()` (колбэк
`on_auth_lost` транспорта) переводит менеджер в `UNAUTHORIZED` с `error="session_revoked"`, если
сессия отозвана извне; при переходе из `ONLINE` отправляется одно уведомление `error` с кодом
`tg_auth_lost` (повторная потеря без нового входа уведомление не дублирует). Шлюз с этого момента
отклоняет отправку (`tg_offline`); восстановление — повторный вход в Telegram через админку
(`/api/v1/tg/login/*`). `on_online()` регистрирует колбэки, вызываемые после успешного входа.

Конвейер входящих (`app/engine/pipeline.py`, `app/engine/bus.py`) обрабатывает обновления строго
последовательно: дедуп по ревизии, журнал и снимок состояния пишутся в одной транзакции, публикация
подписчикам — только после фиксации. Сбой журнала (БД) повторяется с backoff без потери и без
переупорядочивания сообщений; ошибка редьюсера не теряет сообщение. Догнанные старые сообщения
(`recovered`) старше `react_max_age` помечаются `reactable=False` — только журнал и снимки, без
реакций. Подписчики шины не должны ждать результатов действий — только быстро перекладывать доставку
дальше. Публикация идёт по снимку списка подписчиков: подписка, сделанная во время публикации,
начинает получать доставки со следующей. Кэш последних ревизий сообщений (`latest`, для проверки
кнопок) ограничен `latest_capacity` (5000) и вытесняет давно не обновлявшиеся сообщения.

Шлюз действий (`app/engine/gateway`) — единственный путь отправки: любой текст или клик по кнопке
проходит через `ActionGateway`. Команды разбиты на классы (`app/engine/commands.py`): `nav`
(навигация), `action` (игровые действия), `risky` (необратимые), `forbidden`/`donate` (не
отправляются никогда). Любая трата Sw-coin (🌐) — `donate`, включая бафы метро за монеты
(`maze_buf_coins_*`), весенние розыгрыши и смену призов за 🌐 (`spring_roll_coins*`,
`spring_regenerate*`) и весенние призы `/sbN`. Callback метро, сна и весны принимаются только по
белому списку реально встреченных значений (`maze_up`, `maze_exit_accept`, `maze_buf_tokens_*`, …,
`sleep_7`…`sleep_12`, `sleep_Bridge`, `sleep_Hotel`, `spring_roll_smiles`); любое другое значение,
как и неизвестная команда, — `forbidden`. Правила
проверяются при постановке в очередь, при выборе и перед каждой попыткой отправки: отправлять можно
только в разрешённые чаты — игровой, Tangerine и чат приглашений в бой, если он задан
(`settings.chats`), иначе `REJECTED "chat_not_allowed"`; `risky` уходит только при `source=MANUAL` и
подтверждённом `risky_confirmed`, иначе `REJECTED "risky_requires_confirm"`; `action`/`risky` без
`Expectation` отклоняются (`REJECTED "expectation_required"`) — успешный вызов API сам по себе не
подтверждает результат в игре, подтверждает только ответ игры по предикату; только `nav` без
ожидания подтверждается сразу после отправки (`CONFIRMED "sent"`). Kill switch (ручной `kill()` или
`settings.engine.killed`) подавляет всё (`SUPPRESSED "kill_switch"`), `dry_run` подавляет всё, кроме
`nav` (`SUPPRESSED "dry_run"`), блок трат (`block_spending`) отклоняет всё, кроме `nav` (`REJECTED
"blocked:<reason>"`); выключенная механика и пауза отклоняют команду по правилам раздела «Планировщик
и сценарии», шаг несертифицированного сценария подавляется (`SUPPRESSED "uncertified"`). Предикат
`can_send` (из `Runtime`) проверяется там же, где kill switch и
`dry_run`, и отклоняет любую команду, включая `nav`: без single-instance лока — `REJECTED
"lock_lost"`, если Telegram не в состоянии `ONLINE` — `REJECTED "tg_offline"`. Истёкший TTL —
`REJECTED "expired"`, клик по кнопке вне последней ревизии сообщения — `REJECTED "stale_button"`,
несовпадение `expect_revision` — `REJECTED "stale_revision"`, несовпадение хеша содержимого последней
правки с `expect_content` (правка той же секунды) — `REJECTED "stale_content"`; всё это проверяется
и перед каждой повторной попыткой. Пока действует пауза после FloodWait
или антифлуда, шлюз не выбирает действия и не пишет `INTENT`; TTL стоящих в очереди при этом
продолжает истекать, и они разрешаются как `REJECTED "expired"`.

Действие в хранилище (`ActionStore`) проходит `INTENT` (пишется до отправки) → `SENT` → терминальный
статус (`CONFIRMED`/`REFUSED`/`SUPPRESSED`/`OUTCOME_UNKNOWN`/`REJECTED`). Ожидание ответа
регистрируется до отправки вместе с границей журнала (`boundary()` — номер последней записи журнала
на момент отправки): засчитываются только доставки с `journal_id` больше этой границы, с датой не
раньше момента отправки минус 2 секунды, не исходящие и из того же чата. Тайм-аут ожидания даёт
`OUTCOME_UNKNOWN "timeout"` без автоматического повтора, а у ожидания с `silence_confirms` —
`CONFIRMED "silence"`. `MemoryActionStore`
(`app/engine/memory.py`) — реализация для тестов; `DbActionStore` (`app/db/actions.py`) — Postgres,
с уникальным `(account_id, idempotency_key)` для дедупликации повторных отправок и
`mark_unfinished_unknown()` для восстановления после рестарта (незавершённые `INTENT`/`SENT`
переводятся в `OUTCOME_UNKNOWN "restart"`). Если выполнение действия прервано внутренней ошибкой или
остановкой шлюза, строка, уже дошедшая до `INTENT`/`SENT`, сразу закрывается как `OUTCOME_UNKNOWN` с
причиной `internal_error` или `cancelled`; строки `cancelled` при следующем старте считаются
незавершёнными наравне с `INTENT`/`SENT` и так же требуют сверки. TTL, темп отправки и паузы шлюз
считает по инжектированным часам (`Clock.monotonic()`, `SystemClock`).

Неизвестный исход траты (класс не `nav`) сразу блокирует новые траты (`spending_blocked =
"reconcile_required"`) — синхронно, до выбора шлюзом следующего действия, и вызывает хук
`on_uncertain(req, action_id)` шлюза (`ActionGateway(..., on_uncertain=...)`), если он назначен;
исключение хука не мешает блокировке. Само обязательство сверки — строка `actions` со статусом
`outcome_unknown`, классом не `nav` и `reconciled_at IS NULL` (`ActionStore.unreconciled()`); она
хранится в БД и переживает любое число рестартов, пока её не закроет сверщик или пока блок трат не
снимут вручную.

Сверщик (`app/engine/reconcile.py`, `Reconciler`) — фоновая задача `reconcile`, супервизор держит её
постоянно: пока блока трат нет, она только ждёт. Как только блок появляется и движок готов (лок
держится, Telegram `ONLINE`, kill switch не активен), сверщик собирает обязательства
(`ActionStore.unreconciled()` плюс те, что успел сообщить хук `on_uncertain`, но ещё не записал в
БД) и обновляет профиль (`😎Я`) плюс экран каждого затронутого поля: фастфуд и `/eat` — меню еды
(`/to_eat`), `/read_exp`/`/use_card`/`/unbox` — рюкзак (`/inv`), `/unbox_*` — подарки (`/gifts`),
callback `gorbushka_*` — экран Горбушки (`/gorbushka`); прочие действия сверяют только профиль
(`sources_for()`). Все эти команды — класс `nav`, поэтому уходят даже в `dry_run` и при активном
блоке трат. Источник считается обновлённым, только если пришло его событие (например,
`ProfileCompact` для профиля) и все его поля состояния (`RefreshSource.fields`: профиль — `money`,
`motivation`, `stamina`; меню еды — `food_stock`; рюкзак — `books`, `cards`; подарки —
`containers_small`, `containers_medium`; Горбушка — `gorbushka`) сняты не раньше момента запроса
минус 2 секунды (`DATE_SKEW` шлюза) и не помечены `doubtful`. Перед закрытием обязательств поля всех
обновлённых источников проверяются ещё раз: экран, пришедший позже, мог сделать сомнительным поле
уже проверенного источника, и тогда попытка считается неудачной. Когда все нужные источники
обновились и новых обязательств за это время не появилось, сверщик закрывает их
(`ActionStore.mark_reconciled()`), снимает блок и шлёт уведомление `info` `reconciled_auto`; если за
время сверки появилось новое обязательство, блок остаётся, и следующая попытка сверяет уже весь
набор целиком. При неудаче (тайм-аут ответа игры или событие, не учтённое состоянием) сверщик ждёт
`engine.refresh_min_interval_s` (по умолчанию 120с), удваивая паузу с каждой подряд неудачей до
`max_backoff_s` (1800с), и на третьей неудаче подряд шлёт одно уведомление `warn` `reconcile_stuck` —
не повторяя его, пока не случится успех. Запрос, подавленный остановкой шлюза (`SUPPRESSED
"shutdown"`), неудачей не считается: сверщик просто ждёт следующего опроса.

`POST /api/v1/engine/reconciled` — не автоматическое снятие, а явное решение администратора: он
закрывает все открытые обязательства в БД (`reconciled_at`) и снимает блок трат, не проверяя
свежесть состояния. Если за это время шлюз сообщил о новом неопределённом действии, закрываются
только обязательства, известные в начале вызова, а блок трат остаётся до сверки. Автоматическое
снятие блока идёт только через сверщика, описанного выше.

## API

`app/api` (`create_api(container) -> FastAPI`) — HTTP API админки. Авторизация — сессионная cookie
`pyrobot_session` (`Secure` в боевой конфигурации, `HttpOnly`, `SameSite=Strict`), срок жизни 30
дней со скольжением: если с последнего обращения прошли сутки, срок и сама cookie продлеваются
заново при следующем запросе. Пароль хранится как argon2-хэш (`argon2-cffi`), хэширование и проверка
выполняются в threadpool не более чем в 2 параллельных потока (`LoginRateLimiter.slots`). `POST
/api/v1/auth/login` принимает `{login, password}` (логин до 64 символов, пароль до 1024, иначе 422)
и в ответ отдаёт `{login, csrf_token}` вместе с cookie; мутирующие запросы (`POST
/api/v1/auth/logout`, `POST /api/v1/auth/password`) требуют заголовок `X-CSRF-Token` с токеном
текущей сессии, иначе 403. Попытки входа с одного IP сериализуются (`LoginRateLimiter.lock_for`) и
ограничены экспоненциальным backoff: 5 бесплатных попыток, дальше — 429 с заголовком `Retry-After`,
растущим от `base_s` до `max_s`. Счётчик ключа, у которого последняя неудача старше окна `window_s`
(час) и блок истёк, забывается при следующем обращении; при превышении `max_entries` (10 000) ключей
устаревшие записи и свободные блокировки вычищаются целиком. Неверный текущий пароль при смене
пароля троттлится тем же лимитером с ключом по сессии (`session:<id>`) — те же бесплатные попытки и
backoff с 429 и `Retry-After`. Истёкшие `auth_sessions` удаляет фоновая задача `session-purge` раз в
час (`Runtime.session_purge_s`, `AuthRepo.purge_expired`). Смена пароля (`POST
/api/v1/auth/password`, новый пароль не короче 12 и не длиннее 1024 символов, текущий — не длиннее
1024) отзывает все сессии админа, включая текущую. `GET /healthz` — проверка живости, без
авторизации. Swagger UI, ReDoc и `/openapi.json` отключены (404).

`EngineFacade` (`app/engine/facade.py`) — фасад над `ActionGateway`, `Pipeline` и `TgAuthManager`:
`status()` отдаёт режим, kill switch, блок трат, статус Telegram, длину очереди, текущее действие,
бэклог и здоровье конвейера, `lock_ok`/`workers_ok` и лаг event loop (`LoopLagMonitor`,
`app/engine/lag.py`, максимум лага за скользящее окно 60с); `ready()` — истина, когда лок и воркеры
в порядке, Telegram в состоянии `ONLINE`, нет kill switch, нет блока трат и конвейер здоров. `GET
/api/v1/engine/status` (сессия) отдаёт этот статус целиком, включая паузу `paused`, текущий
сценарий планировщика `scenario` и момент его следующего пробуждения `next_wake`. `POST
/api/v1/engine/pause` и `POST /api/v1/engine/resume` (CSRF) сохраняют `engine.paused`, будят
планировщик и пишут аудит `engine_paused`/`engine_resumed` с логином. Успешные `kill`, `unkill` и `reconciled`
пишут аудит-уведомление уровня `info` (`engine_killed`, `engine_unkilled`, `engine_reconciled`) с
логином того, кто это сделал. `POST /api/v1/engine/kill {reason}` (CSRF) сперва латчит
`ActionGateway` и обрывает очередь, затем сохраняет настройку — если сохранение не удалось, latch
остаётся активным. `POST /api/v1/engine/unkill` (CSRF) — в обратном порядке: сначала сохраняет
настройку, затем снимает latch; если сохранение падает, шлюз остаётся выключенным и исключение
уходит наверх; если single-instance лок потерян — 409 `{"detail": "lock_lost"}`, ни настройка, ни
latch не меняются. `POST /api/v1/engine/reconciled` (CSRF) — явное решение администратора: закрывает
все открытые обязательства сверки и снимает блок трат без проверки свежести состояния (см. «Шлюз
действий»); автоматическое снятие блока после проверки — задача сверщика. `GET
/api/v1/tg/status` (сессия) и `POST /api/v1/tg/login/start {phone}`, `.../login/code {attempt_id,
code}`, `.../login/password {attempt_id, password}`, `POST /api/v1/tg/logout` (все — CSRF)
проксируют `TgAuthManager`; несовпадение попытки входа (`AttemptMismatch`) отдаёт 409. Неверный или
истёкший код и неверный пароль 2FA — это 200 с полем `error` (`invalid_code`, `code_expired`,
`invalid_password`). Прочие ошибки входа — наследники `TgAuthError` с кодом: распознанные (например,
`invalid_phone`) — 400 `{"detail": "<код>"}`, сбой Telegram или сети (`TgBackendError`:
`send_code_failed`, `sign_in_failed`, `check_password_failed`) — 502. Отдельно для `send_code`:
`FloodWait` от Telegram — 429 `{"detail": "flood_wait"}` с заголовком `Retry-After`, прочий
`BadRequest` (кроме `invalid_phone`) — 400 с кодом в нижнем регистре из RPC ID Telegram (например
`phone_number_banned`). Сбой `send_code` переводит статус Telegram в `ERROR` с тем же кодом, сбой
`sign_in`/`check_password` оставляет попытку, чтобы код можно было отправить повторно. `GET
/readyz` (без авторизации) — 200 `{"status":"ready"}`, если движок поднят и `ready()` истинна, иначе
503 `{"status":"not_ready"}`.

`GET /api/v1/state` (сессия, CSRF не нужен) отдаёт снимок состояния персонажа: `{"version": int,
"now": ISO-UTC, "state": {...}, "stale": [...]}`. `version` и `state` — из `EngineFacade.state()`
(`Pipeline.version`/`Pipeline.state`), служебное поле редьюсера `applied` (ключи применённых итогов)
в ответ не входит; `stale` — список полей, устаревших по политике свежести
(`stale_fields`, `app/engine/state/model.py`): для «летучих» полей (`money`, `stamina`,
`motivation`, `busy`, `exp`, `knowledge`, `raw`, `details`) — старше `engine.state_stale_after_min`
минут (по умолчанию 15), для «медленных» — старше 6 часов, для таймеров — только если значение
`doubtful`, для цен — старше 7 дней (`prices.<ключ>`). Поле, которое ещё не встречалось на экране
(например `books` до `/inv`), есть в `state` со значением `null` и в `stale` не попадает — это не
устаревшее значение, а ненаблюдавшееся. Без запущенного движка — 503, как `/api/v1/engine/status`.
